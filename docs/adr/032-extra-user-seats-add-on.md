# ADR-032: Extra User Seats — a Paid, Comprobify-Billed, Comprobify-Web-Enforced Add-on

## Status
Accepted

## Date
2026-09-02

## Context

`TIERS[tier].maxUsers` (ADR-031) is a per-tier dashboard-seat cap comprobify only *publishes* — comprobify-web is the only system that enforces it, since comprobify has no user/session concept at all (tenants are the account, the API key is the credential). The ask: let a tenant buy extra seats above `maxUsers`, billed through comprobify's existing manual-review payment pipeline (bank transfer + Payphone), even though comprobify still won't enforce seats — it only bills for them and publishes the resulting entitlement.

Three design questions needed resolving before implementation: how the seat price is stored and kept legally compliant with the 30-day price-change notice clause; how a seat count change interacts with the billing cycle; and whether a renewed subscription bills the plan and the seats separately or together.

## Decision

**A dedicated `seat_prices` table, not a pseudo-tier row inside `tier_prices`.** A flat, non-tiered price seemed like a natural fit for `tier_prices` with `tier = 'EXTRA_SEAT'`, reusing its DRAFT/PUBLISHED/as-of-date resolver and the 30-day notice machinery for free. In practice this doesn't work cleanly: four independent places hard-validate `tier` against the real `TIERS` object — `chk_tier_prices_tier`, `pricing.service.js`'s `assertValidTierAndInterval`, `admin.validator.js`'s tier-price validators, and `tiers.controller.js`'s `Object.entries(TIERS)` loop — and a pseudo-tier would risk leaking into `chk_subscriptions_tier`/`tenants_subscription_tier_check`/`chk_payments_target_tier`, which every tier-transition code path in `subscription.service.js`/`admin.service.js` assumes only ever hold real, sellable tiers. `seat_prices` mirrors `tier_prices`' exact shape minus the `tier` column, and the new resolver functions in `pricing.service.js` (`getCurrentSeatPrice`/`getSeatPriceAsOf`/etc.) mirror the tier functions 1:1 — same as-of-date principle, same DRAFT→PUBLISHED flow, same admin CRUD shape at its own `/v1/admin/seat-prices` path.

**Seat notifications reuse the existing mandatory `PRICE_CHANGE_ANNOUNCED` type**, distinguished by `metadata.seatPriceId` instead of `metadata.tierPriceId` (and the absence of a `tier` key). Adding a 6th email-capable `NotificationTypes` value would mean three more CHECK-constraint widenings, a new catalog entry, and two new email templates for what's semantically identical: "a price on your account is changing, 30 days' notice." `pricing.service.js`'s `notifyPendingPriceChangesForTenant(tenantId)` scans both `tier_prices` and `seat_prices` in the same call — every existing call site (registration, admin verify/status-update, the PAST_DUE→ACTIVE recovery path, the periodic reconciliation sweep) needed zero changes.

**Adding a seat mirrors a same-interval tier upgrade** (prorated against the remaining period, billed, effective immediately); **removing a seat mirrors a same-interval tier downgrade** (free, deferred to `current_period_end`, no refund — the current period is already paid for at the higher count). Unlike tier changes, there is no third "interval change" branch for seats — seats always follow the subscription's own `billing_interval`; a tenant switching cadence does so through `requestTierChange`, whose interval-change branch already reprices any already-active seats at the new interval as part of that same payment.

**Once a tenant has extra seats, the regular renewal bills the seat cost in the same payment as the plan** — one combined invoice per period, not a parallel seat billing cycle. This only touches two existing pricing call sites: `createRenewalReminder` and `requestTierChange`'s billing-interval-change branch, each adding one `effectiveSeatsAtPeriodEnd(subscription) × seatPrice` term. `effectiveSeatsAtPeriodEnd` reads `pending_extra_seats ?? extra_seats` rather than the raw column, because a scheduled seat decrease lands at the exact `current_period_end` a renewal or deferred interval-change payment is priced *for* — pricing off the current (pre-decrease) count would overcharge. `payments.seats_charged` is the audit trail that recovers the per-line breakdown from what is otherwise one combined `amount`: a **delta** on a `SEAT_CHANGE` payment (the count being newly purchased), the **effective total** on a `RENEWAL` or interval-changing `TIER_CHANGE` payment (the count already being carried forward), `0` on `INITIAL` and an ordinary same-interval `TIER_CHANGE` (neither ever includes seat cost).

**A subscription that terminates zeroes its seats.** `applyScheduledTierChanges`' FREE/cancellation branch and `expireSubscription` both reset `extra_seats` to `0` — a cancelled or expired subscription must not keep advertising a paid seat entitlement nobody is paying for.

**The admin job order is seats → tiers → renewals**, not the pre-existing tiers → renewals. `applyScheduledSeatChanges`' due-query is keyed on `current_period_end <= NOW()`, and `applyScheduledTierChanges` rolls that same column forward — running tiers first would make a due seat decrease invisible for a whole extra period. See CLAUDE.md Common Mistake #50.

## Consequences

- Two nearly-identical pricing subsystems now exist in `pricing.service.js` (tier functions and seat functions) rather than one generalized "priced item" abstraction. Accepted: the shapes are similar but not identical (tier+interval key vs. interval-only), and keeping them textually separate means a change to tier pricing can't accidentally regress seat pricing or vice versa — the 30-day notice is a legal requirement on both, and this is the lower-risk way to extend it to a second priced thing.
- Seat count is a real column (`subscriptions.extra_seats`) on a resource comprobify already owns, but the *cap* it raises (`maxUsers`) is still entirely a comprobify-web concept comprobify never reads. comprobify-web is responsible for adding `extraSeats`/`pendingExtraSeats` (surfaced via `GET /v1/tenants/me`, snake_case fields per `authenticate.js`) to whatever number it already enforces against — nothing here changes that responsibility split from ADR-031.
- `refundPayment`'s `applied_from` snapshot now also carries `extraSeats`, but a `SEAT_CHANGE` payment's refund is the only path that restores it — restoring it unconditionally on every refund would wipe out an unrelated, legitimately-scheduled pending seat decrease when refunding e.g. a `RENEWAL`. Pre-migration-095 `applied_from` rows have no `extraSeats` key at all; the restore falls back to the subscription's current value (a no-op) rather than writing `undefined`.
- `docs/agreements/terms-of-service.md`'s 30-day price-change clause named "los precios de los planes de suscripción" — broadened to also name "complementos" (add-ons) so the legal text matches what the mechanism now actually covers, and republished as a new `TERMS` version.
