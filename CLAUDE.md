## Project Overview

**SRI Electronic Invoice API** — Node.js/Express REST API for generating, digitally signing, and submitting electronic invoices (*facturas electrónicas*) to Ecuador's SRI. Full document lifecycle: Generate → Sign → Send → Authorize. PostgreSQL for persistence.

## Architecture

```
Route → Validator → Controller → Service → Model / Builder / Helper
```

**Dependency rule:** each layer calls only the layer below it. Controllers never touch models. Services never touch `req`/`res`.

```
src/routes/        URL definitions + validator chains
src/validators/    express-validator field rules
src/middleware/    asyncHandler, validateRequest, errorHandler, idempotency, authenticate, rate-limit, verify-mailgun-webhook
src/controllers/   thin HTTP handlers — one service call, one response
src/services/      business logic and orchestration
src/services/email/  email provider factory + Mailgun provider + templates
src/models/        PostgreSQL CRUD (parameterised queries only)
src/builders/      XML document construction (builder registry)
src/errors/        AppError → ValidationError / NotFoundError / SriError / ConflictError / QuotaExceededError
helpers/           signer.js (XAdES-BES), access-key-generator.js (Module 11), ride-builder.js (RIDE PDF)
db/migrations/     SQL migration files 001–050
assets/            factura_V2.1.0.xsd + nota_credito_V1.1.0.xsd + xmldsig-core-schema.xsd
```

## CRITICAL RULES

1. **English only** — all identifiers, file names, table names, column names. Spanish only where SRI mandates it (XML element names: `infoTributaria`, `claveAcceso`, SOAP payloads).
2. **Never string-interpolate SQL** — always use `$1, $2` parameterised placeholders.
3. **Never skip layers** — controller → service → model. Never controller → model.
4. **Never read `process.env` directly** — import from `src/config/index.js`.
5. **Validate before signing** — XSD validation runs before the expensive crypto step.
6. **Always log an ERROR audit event before re-throwing** from a SRI service catch block.
7. **No hard deletes** — set `active = false` or update status instead.
8. **Wrap all async route handlers** in `asyncHandler` — never add try/catch in controllers.

## Key Patterns

**Primary keys:** every table's PK is `UUID PRIMARY KEY DEFAULT uuid_generate_v7()` — never `SERIAL`/`BIGSERIAL`. `uuid_generate_v7()` (migration `000_uuid_v7_function.sql`) is a hand-rolled PL/pgSQL implementation (48-bit millisecond timestamp + random bytes, version/variant bits set per RFC 9562) since native `uuidv7()` only ships in PostgreSQL 18+ and the target version here is 14.x minimum — it requires the `pgcrypto` extension (`gen_random_bytes`), also enabled in that same migration. UUIDv7's time-ordered layout means `ORDER BY id` and "everything after id X" cursor queries (e.g. `GET /v1/notifications?sinceId=`) keep working exactly like they did under `SERIAL`, since Postgres's native `uuid` comparison is byte-wise and the leading bytes are the timestamp. Every FK column matches its target's `UUID` type — there is no integer PK anywhere in the schema. Any new migration creating a table must use this same `DEFAULT uuid_generate_v7()` pattern; no Node-side id generation exists or is needed. See ADR-020.

**Sequential numbers:** `SELECT ... FOR UPDATE` inside an explicit transaction — guarantees no duplicate sequential numbers under concurrent load. See `src/services/sequential.service.js`.

**Certificate storage:** private key PEM stored AES-256-GCM encrypted in `issuers.encrypted_private_key`; certificate PEM stored plaintext in `issuers.certificate_pem`. Decrypted at signing time only. Encryption key lives in `ENCRYPTION_KEY` env var.

**Issuer logo:** stored as `BYTEA` in `issuers.logo` (migration 050; replaces the dropped `logo_path` column). Two upload paths: optional `logo` field on `POST /v1/register` (multipart, validated in `registration.controller.js`), or `PATCH /v1/issuers/:id/logo` for an existing issuer (PNG/JPEG/GIF, max 500 KB). The registration multer instance has a 10 MB **whole-request** `fileSize` limit (it must also accommodate the P12 cert upload), so the 500 KB logo cap cannot be enforced by multer there — `registration.controller.js` checks `logoFile.size` manually and throws `INVALID_FILE_UPLOAD` if exceeded. The dedicated logo-upload route's multer instance has no other file fields, so its `limits: { fileSize: 500 * 1024 }` enforces the cap natively. `ride.service.js` reads `issuer.logo` and passes it to `helpers/ride-builder.js`, which renders it in the top-left header of every RIDE PDF (including email attachments).

**Multi-branch support:** one RUC can have multiple issuer rows with different `(branch_code, issue_point_code)` pairs. When creating a branch, supply `sourceIssuerId` instead of a P12 file — the service copies `encrypted_private_key`, `certificate_pem`, `cert_fingerprint`, `cert_expiry` from the source row. Self-service endpoint is `POST /v1/issuers` (omit `sourceIssuerId` to inherit from the tenant's first existing issuer). Creating a branch does NOT mint a new API key — the tenant's existing key covers every branch via the `X-Issuer-Id` header. New branches inherit the tenant's current environment (sandbox or production).

**Issuer lifecycle management:** `PATCH /v1/issuers/:id` edits `tradeName`/`branchAddress` only — `businessName`, `mainAddress`, and `ruc` stay permanently tied to the RUC registration and have no edit path. `DELETE /v1/issuers/:id` soft-deletes (`active = false`), refusing if it's the tenant's last active issuer (`LAST_ISSUER_CANNOT_BE_REMOVED`) or if `documentModel.existsByIssuerId()` finds any document for it in either the `public` or `sandbox` schema (`ISSUER_HAS_DOCUMENTS`) — an issuer with history can never be reused. `PATCH /v1/issuers/:id/activate` reverses the soft-delete, but re-runs the exact same branch/issue-point plan-limit checks `createBranch` does (via `tenantModel.countIssuePointsByBranch`/`countBranchesByTenantId`), so a tenant can't dodge their tier's cap by deactivating one issuer and reactivating another.

**Pausing new document issuance:** `issuers.can_issue` (migration 089, `BOOLEAN NOT NULL DEFAULT true`) lets a tenant stop an issue point from creating new documents without deactivating it — deactivation (`active = false`) is unavailable once an issuer has history (`ISSUER_HAS_DOCUMENTS`, see above), so this is the only way to pause a stale-but-historied branch or issue point (e.g. one being decommissioned) while its past documents keep working. `PATCH /v1/issuers/:id/can-issue` (`{ canIssue: boolean }`, `issuerService.setCanIssue()`) toggles it — either direction is always allowed on an active issuer, no additional business rule. The guard itself lives only at the two document-mutation entry points that start a fresh SRI submission — `document-creation.service.js`'s `create()` and `document-rebuild.service.js`'s `rebuild()` (a rebuild re-signs and re-submits under the same access key, the same risk as a fresh create) — both throw `403 ISSUER_ISSUING_PAUSED` at the very top before doing any other work. `resolve-issuer.js`/`issuerModel.findById()` deliberately do **not** filter on `can_issue` — they're shared by every issuer-scoped route including PDF/email/read endpoints, which must keep working regardless of the flag; `req.issuer` picks up `can_issue` automatically since `findById()` already does `SELECT *`. Not touched by promotion (`tenant.service.js`'s `promote()`) — issuers are a single row shared across sandbox/production (only `api_keys` and sequentials are per-environment), so `can_issue` carries over with no promotion-time code needed.

**Manual sequential management:** `GET /v1/issuers/:id/sequentials` reports the current and next counter value per active document type, for both `sandbox` and `production` side by side. Because `sequential_numbers` has RLS (per-issuer, per-schema), the two environments cannot be read in one query — `sequential.service.js`'s `getCounters()` issues two separate `db.queryAsIssuer(..., sandbox)` calls (one per schema) and merges the results in JS. `PATCH /v1/issuers/:id/sequentials/:documentType` (`setNext()`) locks the row with `SELECT ... FOR UPDATE` inside the same transaction as the write (mirroring `getNext()`'s locking), so it cannot race a concurrent `POST /v1/documents` and produce a duplicate sequential; rejects with `SEQUENTIAL_CANNOT_DECREASE` if `nextSequential` does not exceed the current value.

**Tenant model:** `tenants` is the root billing entity. One tenant owns one RUC with one or more branches and issuing points (limited by tier). Fields: `email`, `subscription_tier` (FREE/STARTER/GROWTH/BUSINESS), `status` (PENDING_VERIFICATION/ACTIVE/SUSPENDED), `sandbox` (boolean, default `true`), `document_count`, `document_quota`, `preferred_language` (default `'es'`). Tenants are NOT user accounts — no password, no session. The API key IS the credential. `src/constants/subscription-tiers.js` defines per-tier `documentQuota`, `maxBranches`, `maxIssuePointsPerBranch`, and rate limits. `PATCH /v1/tenants/language` updates the preferred language after registration. `GET /v1/tenants/me` resolves identity for a holder of an API key with no other context (e.g. a third-party app linking an existing account) — it returns `req.tenant` as-is, with no DB call, since `authenticate` middleware has already resolved it from the key. The route also runs `requireMatchingEnvironment` (same check `resolveIssuer` uses) so a key minted for one environment cannot resolve identity while the tenant is active in the other — see `src/middleware/require-matching-environment.js`.

**Email localisation:** outgoing emails are localised using `src/locales/` — a cross-cutting layer shared by email templates and (in future) API responses. `getTranslations(lang)` returns the locale object for the given language code, falling back to `'es'`. Each locale file exports a plain object keyed by domain (`email.verifyEmail.*`, `email.invoiceAuthorized.*`). Templates own HTML structure; locales own strings. `SUPPORTED_LANGUAGES` exported from `src/locales/index.js` is the single source of truth for accepted language codes — used by validators on `POST /v1/register` and `PATCH /v1/tenants/language`. The invoice-authorized email is localised using the **issuer's tenant** `preferred_language` (there is no buyer-language field — `email.service.js` resolves it via `issuer.tenant_id` → `tenantModel.findById`), not the buyer's.

**Self-service registration (frontend-only, ADR-035):** `POST /v1/register` — creates tenant + issuer + sandbox API key in one call. **Not public** despite having no `Authorization` header: `requireInternalService` (mounted first, before `registrationLimiter`) requires a valid `X-Internal-Service-Secret`, so only comprobify-web's own server-side BFF can call it — a direct API caller gets `403 INTERNAL_SERVICE_ONLY` before any other work runs. Tenant starts PENDING_VERIFICATION. A verification email is sent (fire-and-forget). The returned API key is shown once. **Verification is split into a non-consuming check and a consuming confirm**, not a single `GET`: `GET /v1/verify-email/check?token=xxx` (still public, read-only, no internal-service gate — it creates/activates nothing) looks up the token with the same expiry filter `activate()` uses but never calls it — safe to call repeatedly, including by automated email link-scanners (e.g. Microsoft Defender/Safe Links on Outlook addresses) that prefetch every link in an email with a plain `GET` before the user clicks. `POST /v1/verify-email` (`{ token }` body, gated behind `requireInternalService` same as `register`/`recover`) is the actual consuming action — it activates the tenant, and being `POST`-only means a scanner's `GET` prefetch can never trigger it even before this gate existed. The original combined check-and-consume `GET /v1/verify-email?token=xxx` is **removed** — it existed only as a fallback "reachable for a direct API caller bypassing a first-party frontend," which is exactly the scenario ADR-035 disallows; every verification email now always links to the frontend's own page instead. All remaining paths share the same underlying `activate()`/`findByVerificationToken()` logic in `tenant.model.js`; `registration.service.js`'s `verifyEmail(token)` (consuming) and `checkVerificationToken(token)` (non-consuming) are the two service-layer entry points. Unverified tenants can use sandbox but cannot promote to production. `verificationRedirectUrl` is now a **required** field (there's no API-hosted verification page to fall back to any more) that redirects the email link to a frontend page (e.g. `https://app.example.com/verify?token=xxx`) — stored on the tenant row and used for all subsequent verification emails including resends. Token TTL is configurable via `VERIFICATION_TOKEN_TTL_HOURS` (default 24h). `POST /v1/resend-verification` (also gated behind `requireInternalService`) enforces a 60-second server-side cooldown (checked against `tenants.verification_email_sent_at`) in addition to the IP rate limit. `register()` is for new accounts only — if the email already exists it always rejects with `409 CONFLICT`, regardless of tenant status, pointing the caller at `POST /v1/recover`; see "Account recovery" below.

**Account recovery:** `POST /v1/recover` (frontend-only, gated behind `requireInternalService` same as `register` — ADR-035) — regains API key access when it's been lost. Requires the same P12 cert used at registration; `registration.service.js`'s `recover()` parses the uploaded cert and compares its fingerprint against `issuer.cert_fingerprint` before doing anything else. Deliberately anti-enumeration: an unregistered email, a tenant with no issuer, and a fingerprint mismatch all return the exact same generic `{ ok: true, message: ... }` response (mirrors `resendVerification()`'s existing "don't leak whether email exists" pattern) — only a genuine match, the same ownership bar fresh registration accepts, does anything observable. On a match: the API key for the tenant's **actual current environment** is revoked and reissued synchronously (`tenant.sandbox ? 'sandbox' : 'production'` — a promoted tenant recovers their production key, not a useless sandbox one). **Extra validation (forced re-verification):** the tenant is also durably demoted to `PENDING_VERIFICATION` with a fresh token (`tenantModel.demoteToPendingVerification()`, the `activate()` counterpart) — a matching certificate proves possession of the P12, but not control of the registered email inbox, so recovery now requires clicking a fresh verification link before the account regains `ACTIVE`-gated privileges (branch creation, promotion, starting a subscription, minting additional named keys — see the `tenant.status !== ACTIVE` gates in `issuer.controller.js`, `tenant.service.js`, `subscription.service.js`, `api-key.service.js`). The reissued key still works immediately for sandbox document creation in the meantime, same as any freshly-registered `PENDING_VERIFICATION` tenant. The demotion happens even when `EMAIL_PROVIDER=none` (no way to ever click the link) — recoverable via the existing admin override, `POST /v1/admin/tenants/:id/verify`. The email itself is durably enqueued (see "Async worker: pending_effects outbox") reusing the exact same verification redemption machinery (`GET /v1/verify-email/check` + `POST /v1/verify-email`) as `resendVerification()` rather than a parallel mechanism. Suspended accounts are only ever told they're suspended (`403 ACCOUNT_SUSPENDED`) after a matching certificate is presented — a caller with the wrong cert already got the generic response and learns nothing about account status. See ADR-021 for the original design rationale (including why a simpler synchronous flow was chosen over a two-step token/confirm design) and its addendum for the forced-re-verification change.

**Legal documents and tenant acceptance (ADR-018):** Two-layer design — a template store (`agreements`, migrations 057/059) and per-tenant personalized snapshots (`tenant_agreements`, migration 061).

`agreements` stores the Markdown source for `TERMS`/`PRIVACY`/`DPA`. Content comes from `docs/agreements/*.md` read at publish time by default, or from an optional `contentMarkdown` field in the same `POST /v1/admin/agreements` body (`{ documentType, version, contentMarkdown? }`) — passing `contentMarkdown` lets an admin publish an edited version directly from the DB without touching the filesystem or redeploying (the file-read fallback still exists for any document type never edited through the API). Either source goes through the same `stripDraftHeader()` (a no-op for admin-submitted text, which never carries the git draft banner) and `substitutePlaceholders()` calls, so `{{token}}` resolution and the resulting HTML rendering are identical regardless of origin. `GET /v1/admin/agreements/versions/:id` fetches one specific version's full `content_markdown` by its row id — `agreements.id` is a global primary key, not scoped per `document_type`, so no `:type` is needed to disambiguate — letting a UI pull existing content into an editor before resubmitting via `publish()`. Public `GET /v1/agreements` lists current versions; `GET /v1/agreements/:type` serves rendered HTML via `markdown-it` with a disclaimer notice prepended (not stored in content). Supports `{{token}}` placeholder substitution: `{{operador.*}}` (`nombre`/`ruc`/`domicilio`/`email`) and `{{soporte.email}}` are resolved once at **publish time** by `publish()` (same value for every tenant); `{{cliente.razonSocial}}`/`{{cliente.ruc}}` are resolved later, per tenant, at **generation time** by `tenant-agreement.service.js`'s `generateForTenant()`. **Two distinct contact emails, two distinct purposes:** `{{operador.email}}` names the legally responsible party's identity (used only in the DPA's opening "Encargado" clause) and must never be swapped for the support inbox. `{{soporte.email}}` (resolved from `ADMIN_NOTIFICATION_EMAIL`, falling back to `OPERATOR_EMAIL` if unset so a published document never bakes in a blank contact) is for every "write to us" invitation — account termination, "para consultas," exercising data rights — used throughout Terms of Service and Privacy Policy. `agreement.service.js`'s `buildDisclaimer()` (the "questions about this content? contact us before accepting" notice, prepended outside the stored content, not a `{{}}` token) follows the same `ADMIN_NOTIFICATION_EMAIL`-first reasoning independently, since it's evaluated at render time rather than publish time. `buildDisclaimer()` is shared by both `GET /v1/agreements/:type` (public, generic) and `GET /v1/tenants/agreements/:type` (tenant-facing, personalized) — same disclaimer either way. Both routes also wrap their final body (disclaimer + rendered markdown) with `agreementService.wrapDocumentHtml(documentType, body)`, which returns a complete, self-contained `<!DOCTYPE html>` page (serif typography, justified paragraphs, a styled `<h1>`/`<h2>`/`<h3>` hierarchy, a centered "paper" container, a `<title>` tag derived from a `DOCUMENT_TYPE_TITLES` map) — the raw markdown-it fragment on its own has no page chrome and renders as unstyled plain text if opened directly in a browser.

`tenant_agreements` stores one **personalized, immutable** Markdown snapshot per `(tenant_id, document_type, template_version)` — all `{{}}` tokens are resolved at generation time (DPA includes the Client's actual `business_name` and `ruc`). Status: `PENDING` (generated, not yet accepted) or `ACCEPTED`. Generation happens: (a) at registration as a fire-and-forget background call once the issuer row exists; (b) lazily when `GET /v1/tenants/agreements` or `GET /v1/tenants/agreements/:type` is called and the tenant has no row for the current template version — so publishing a new template surfaces automatically without any admin job. `UNIQUE (tenant_id, document_type, template_version)` with `ON CONFLICT DO NOTHING` makes all generation calls idempotent.

`POST /v1/register` does not take or check a `termsVersion` field — nothing is being accepted yet at registration, since the tenant's `tenant_agreements` rows don't even exist until the fire-and-forget `TENANT_AGREEMENT_GENERATE` effect runs afterward (still `PENDING` at that point). `termsVersion` is validated in exactly one place: `POST /v1/tenants/agreements` (`{ termsVersion }`, `tenantAgreementService.validateTermsVersion()` against the current `TERMS` template) accepts all `PENDING` instances at once, recording `accepted_at`/`ip`/`user_agent` on each row. Old ACCEPTED rows survive every re-acceptance — full history is preserved. `tenants.agreement_accepted_at`/`agreement_version` are a denormalized cache, stamped only by that same acceptance call (`tenantModel.updateAgreementAcceptance`) — never at registration, so the cache can't claim a tenant accepted something before they actually did.

`GET /v1/tenants/agreements` returns per-type drift detection (`{ needsAcceptance, outdated: [{ documentType, currentVersion, acceptedVersion, status, url }], hasPublishedAgreements }`) — third-party integrators should poll this periodically to know when their tenant needs to re-accept updated documents. `hasPublishedAgreements` (`tenant-agreement.service.js`'s `getStatus()`) disambiguates the two ways `needsAcceptance` can be `false`: nothing has ever been published (`agreementService.listCurrent()` is empty — a fresh/pre-launch environment where no admin has run `POST /v1/admin/agreements` yet) versus everything published has already been accepted. Without it a caller can't tell "nothing to show yet" apart from "all caught up" — this was a real bug: `comprobify-web`'s "Documentos legales" settings card rendered three dead links that all 404'd with `AGREEMENT_NOT_FOUND` on a pre-launch environment. `GET /v1/tenants/agreements/history` lists all instances (history); `GET /v1/tenants/agreements/:type` renders the tenant's personalized HTML (the stored snapshot — no substitution at read time, already baked in) with the disclaimer prepended.

`POST /v1/tenants/promote` is **gated** on all three document types being `ACCEPTED` (`hasAllAccepted()` → `403 AGREEMENT_ACCEPTANCE_REQUIRED` if not) — **unless `AGREEMENTS_ENABLED=false`**, see "Disabling agreements" below. Admin override: `POST /v1/admin/tenants/:id/agreements` generates instances for pre-existing tenants (admin-created tenants have no self-service registration step, so they never get the fire-and-forget generation `register()` triggers). `docs/agreements/*.md` holds the source templates (Spanish, entity info filled in, `{{cliente.*}}` tokens awaiting per-tenant substitution).

**Disabling agreements (`AGREEMENTS_ENABLED`):** the whole legal-document feature can be switched off, so the product can launch before Terms/Privacy/DPA have been reviewed. Defaults to **enabled** (`process.env.AGREEMENTS_ENABLED !== 'false'`) so an existing deployment can never silently lose its acceptance gate, and so an empty value from an unset CI variable fails *closed* — the opposite of `IVA_RATE`'s hazard (see `docs/terraform-digitalocean-setup.md`). The flag is implemented as a gate on exactly two functions in `agreement.service.js` — `getCurrent()` (throws `AGREEMENT_NOT_FOUND`) and `listCurrent()` (returns `[]`) — because every tenant-facing consumer funnels through one of them, so the rest cascades with no further branching: `GET /v1/agreements` empties, `GET /v1/agreements/:type` 404s, `getStatus()` reports `hasPublishedAgreements: false` (plus an explicit `agreementsEnabled: false`, which is what lets a frontend tell "switched off" apart from "nothing published yet"), `generateForTenant()` creates nothing, and `validateTermsVersion()` no-ops via its existing `AGREEMENT_NOT_FOUND` catch. `tenant.service.js`'s `promote()` additionally checks the flag **explicitly** rather than relying on that cascade — a legal gate should state its own condition, not inherit it from another module's emergent behaviour — and `registration.service.js` skips enqueuing `TENANT_AGREEMENT_GENERATE` so a disabled deployment doesn't queue one no-op effect per signup. **Admin publish/activate paths are deliberately left working** (`publish()`, `activateVersion()`, `getById()`, `listVersionsByType()` don't route through the two gated reads), so documents can be prepared and reviewed while the flag is off. Nothing is deleted: re-enabling restores whatever was already published and accepted, since `agreements` and `tenant_agreements` rows are untouched.

**User-facing promotion:** `POST /v1/tenants/promote` (authenticated) — checks tenant is ACTIVE, checks all agreements are `ACCEPTED` (`403 AGREEMENT_ACCEPTANCE_REQUIRED` if not), flips `tenants.sandbox = false`, seeds production sequentials for all issuers × document types, revokes all sandbox API keys, and creates matching production keys (one per revoked sandbox key, same label). If the tenant already has an `ACTIVE` subscription (activated pre-promotion while in sandbox), the billing period is **reset to the promotion date** via `subscriptionService.resetPeriodOnPromotion()` — the paid period should count production usage time, not sandbox testing time. Returns `{ apiKeys: [{ label, apiKey }] }` — all tokens shown once, store immediately. This is one-way. Admin override: `POST /v1/admin/tenants/:id/promote` (skips both ACTIVE status and legal acceptance checks).

**Admin API:** `ADMIN_SECRET` env var (64-char hex) protects all `/v1/admin/*` routes via `src/middleware/authenticate-admin.js` (constant-time comparison) with a 20 req/min IP-based rate limiter. Admin tenant routes: create (status ACTIVE, no verification), list, update tier, update status (activate/suspend), manual verify, promote (override — skips both ACTIVE status and legal acceptance checks), event log. Admin issuer routes: create (requires `tenantId`), list, certificate renewal. Admin key routes: create, list, get daily usage, revoke. `POST /v1/admin/tenants/:id/api-keys` defaults `environment` to the tenant's *current* active environment (`tenant.sandbox ? 'sandbox' : 'production'`) when the body omits it — it does not hardcode `'sandbox'`, so creating a key for an already-promoted tenant without specifying `environment` yields a production key. Since migration 102, it also accepts `scopes`/`isReserved`/`replaceKeyId` for minting/rotating comprobify-web-internal (reserved) keys — see "Entry-tier gating and reserved keys/endpoints" above. `POST /v1/admin/tenants/:id/webhook-endpoints` (new, migration 102) mirrors it for reserved webhook endpoints — there's no admin deactivate route for these, unlike api keys: the tenant-facing `PATCH`/`DELETE /v1/webhooks/:id` already allow toggling a reserved endpoint's `active` flag directly, since that's not a credential the way a key is — see "Entry-tier gating and reserved keys/endpoints" below for why.

**Tenant-scoped API keys (ADR-013):** API keys belong to a tenant, not an issuer. One tenant can mint multiple named keys (e.g. `frontend-prod`, `erp`, `mobile-app`) via `GET / POST / DELETE /v1/keys`. Each key carries an `environment` column (`'sandbox'` or `'production'`). The `authenticate` middleware sets `req.tenant` + `req.apiKey` + `req.keyHash` and does NOT set `req.issuer` (issuer resolution is delegated to the next middleware) — it no longer rejects SUSPENDED tenants itself; see "Suspension" below.

**API key plan limit (ADR-031):** `TIERS[tier].maxApiKeys` caps how many active keys a tenant can hold at once — `apiKeyModel.countActiveByTenantId()` checked against it in both `api-key.service.js`'s `createKey()` (self-service) and `admin.service.js`'s `createApiKey()` (admin override; admin does not bypass this, mirroring `createIssuer()`'s branch-limit precedent), `402 API_KEY_LIMIT_REACHED` on breach. `null` means unlimited (ENTERPRISE).

**Entry-tier gating and reserved (comprobify-web-internal) keys/endpoints (ADR-034, superseded by migration 102):** FREE/SOLO/LITE have `maxApiKeys: 0` and `maxWebhookEndpoints: 0` — self-service keys and webhooks are a STARTER+ feature, the same upgrade-by-capability lever already used for multi-branch (STARTER+) and credit notes (GROWTH+), since these entry tiers' quotas alone are too generous relative to Ecuadorian competitors to ever force an upgrade on volume. `0` means genuinely zero: `api_keys`/`webhook_endpoints` both carry an `is_reserved` column (migration 102), and every tenant-facing count/list (`countActiveByTenantId`, `findActiveByTenantId`'s default) excludes reserved rows entirely — they don't just sit outside the *advertised* number, they're excluded from `effectiveApiKeyLimit(tier)`/`effectiveWebhookEndpointLimit(tier)` (`subscription-tiers.js`) at the query level, which are now a plain passthrough of the tier's own `maxApiKeys`/`maxWebhookEndpoints` with no addition on top. `api-key.service.js`'s `createKey()`, the non-reserved branch of `admin.service.js`'s `createApiKey()`, and `webhook-endpoint.service.js`'s `create()` all check this; `GET /v1/keys`/`GET /v1/webhooks` return a `limit: { max, used }` block that now equals the tier's own value exactly, so `GET /v1/tiers` no longer publishes a separate `reservedForFrontend` field — there's nothing left to explain.

Reserved (comprobify-web-internal) rows — the master key, per-role keys, comprobify-web's own webhook subscription — are minted only through two privileged, never-tenant-facing paths, never through `POST /v1/keys`/`POST /v1/webhooks`: (1) `registration.service.js`'s `register()` (always `isReserved: true` — the key is always claimed internally by the frontend, never shown to a tenant) and `recover()` (an `isReserved` param the caller passes, since only comprobify-web ever calls this `requireInternalService`-gated endpoint and already knows whether this is the mainstream already-linked case (`true`) or the "hand back to a human to link" case (`false`)); (2) the extended `POST /v1/admin/tenants/:id/api-keys` / new `POST /v1/admin/tenants/:id/webhook-endpoints`, `ADMIN_SECRET`-gated, which comprobify-web calls directly (it already holds `COMPROBIFY_ADMIN_SECRET`) for routine per-role key minting and incident-response rotation — `isReserved: true` skips the tenant-limit check entirely (reserved rows never compete for a tenant's budget) and is instead capped by a generous sanity ceiling (`countReservedByTenantId` on both the api-key and webhook-endpoint models, checked against `RESERVED_API_KEYS_FOR_FRONTEND`/`RESERVED_WEBHOOK_ENDPOINTS_FOR_FRONTEND`, bug-detection only, `409 RESERVED_KEY_LIMIT_REACHED` past it); `replaceKeyId`/`replaceEndpointId` atomically revokes one specific row and mints its replacement inside a transaction, unlike the older blanket `revokeExisting` flag (which still exists for its original, unrelated use case).

A reserved row is invisible through every tenant-facing surface, not just unlisted — `api-key.service.js`'s `revokeKey()` and `webhook-endpoint.service.js`'s `update()`/`deregister()` all throw a generic not-found for a reserved row's *id*, exactly as if it didn't exist, even if a tenant somehow learned it. This closes what ADR-034 originally accepted as a trade-off — "a direct API caller on an entry tier can technically self-mint up to the reserved amount" — which stopped being acceptable once "Free/Solo/Lite must never have API access" became a hard requirement rather than a soft one.

**Untouchable is not quite the same guarantee for a webhook endpoint as it is for an API key, and that's deliberate.** `revokeKey()` treats a reserved key as fully off-limits — no exceptions — because a key *is* a credential; there is no tenant-safe subset of "let me modify my own reserved key." A webhook endpoint's `active` flag isn't a credential, it's a delivery on/off switch, so `update()`/`deregister()` allow toggling `active` on a reserved row (deregister is just `update(id, { active: false })`) while still rejecting any change to `url`/`eventTypes` on one — retargeting comprobify-web's own in-app notification receiver is the operation that actually needs blocking, not flipping delivery on or off. There's deliberately no admin-gated deactivate route for reserved webhook endpoints (unlike api keys, which do have `DELETE /v1/admin/api-keys/:id`) — the tenant-facing route already covers it safely.

**Promotion key mirroring mirrors every key, reserved included — visibility in the response is what's gated, not mirroring itself.** `admin.service.js#promoteTenant`/`tenant.service.js#promote` both call `apiKeyModel.findActiveByTenantId(tenantId, true)` (include reserved) before revoking every sandbox key and mirroring all of them into production, preserving each key's own `is_reserved` flag. `tenant.service.js#promote` takes a `callerIsReserved` argument (from `req.apiKey.isReserved`, threaded through by `tenant.controller.js`) — a mirrored key's plaintext is only pushed into the response's `apiKeys` array when it's non-reserved OR the caller's own authenticating key is itself reserved. In practice this means comprobify-web's own promote calls (always made with the tenant's master/reserved key — `tenant:promote` scope is never granted to any narrower per-role key on the frontend side) see every mirrored key including their own new reserved one, with **zero extra frontend work required** — production access just keeps working after every promotion, exactly as it did before reserved keys existed as a concept. The rarer case — a tenant self-minted a key with `tenant:promote` scope and calls promote directly — still gets their own reserved key(s) mirrored into production (so comprobify-web's dashboard access for that tenant isn't broken), just never shown in *that* response, consistent with every other tenant-facing surface. `admin.service.js#promoteTenant` (the `ADMIN_SECRET`-gated admin override) has no such gate at all — admin is already the highest trust boundary in the system, so every mirrored key, reserved or not, is always returned.

**API key usage tracking:** `api_key_daily_usage` (migration 083, one row per `(api_key_id, usage_date)`) is the single source of truth for every usage stat a key has — rate limiting is already per-`keyHash`, but that's in-memory-per-window and answers nothing about "is this key still in use," "how much traffic does the ERP integration generate," or "show me a chart of its usage over time." On every successful `apiKeyModel.findByKeyHash` lookup, `authenticate` middleware fires `apiKeyModel.touchUsage(row.key_id)` fire-and-forget (not awaited, so it never adds latency to the hot auth path) — **exactly one write per request**, an `INSERT ... ON CONFLICT (api_key_id, usage_date) DO UPDATE SET request_count = request_count + 1, last_used_at = NOW()` upserting today's row — with a `.catch()` that logs via `logger.service.js` rather than risking an unhandled rejection (unlike `attemptTrackerService.recordEvent()`'s other unawaited call in the same middleware, a raw `db.query()` can actually reject). Deliberately not a separate lifetime counter on `api_keys` alongside the daily table — that would be two things to keep in sync on every request for no benefit, since a lifetime total is trivially an aggregate query over the daily rows.

**Tenant-scoped API key permissions:** `api_keys.scopes` (migration 084, widened+split by 085, widened again by 096, `TEXT[]`, DB-`CHECK`-constrained against the same 10-value vocabulary as `src/constants/api-key-scopes.js`'s `ApiKeyScopes`/`ALL_SCOPES`) lets a tenant mint a key narrower than "do everything this tenant can do" — e.g. a read-only key for a dashboard that pulls stats, or one key per user role in a frontend's own RBAC (the driving use case for the 085 split — comprobify-web's 5 roles need 1:1 mapping onto API scopes, not a coarser bundling). Vocabulary:
- `documents:write` — all document mutations under `documents.routes.js`, plus `GET /:accessKey/authorize` (it fires a live SRI call and can send the authorization email, so it's gated like a write, not a read, mirroring its existing `requireNotSuspended`/`requireNotPastDue` per-route treatment) and `POST /v1/tenants/retry-failed-documents` (operates on documents, not account settings, despite living under `tenants.routes.js`).
- `documents:read` — every other `GET` under `/v1/documents`.
- `documents:void` — `POST /:accessKey/void` only, split out from `documents:write` rather than folded in — see "Voiding a document" below. Voiding presumes the tenant already cancelled the document in SRI's own portal, a higher-stakes, harder-to-reverse action than an ordinary document mutation, so it gets its own scope the same way `tenant:promote` was split out from `tenant:manage`.
- `issuers:read` / `issuers:write` — `issuers.routes.js`'s `GET`s vs. its `POST`/`PATCH`/`DELETE`s, split per-route (mirrors `documents:read`/`write`) rather than one bundled scope — every role needs to see issuers/branches/cert-expiry, only some need to mutate them.
- `keys:manage` — the entire `api-keys.routes.js` router (`GET`/`POST`/`DELETE /v1/keys`). Gating key management behind its own scope (not bundled with anything broader) means `requireScope` alone only proves "this key can touch the tenant's key set" — it does **not** prove the resulting key won't be over-privileged, which is why `api-key.service.js`'s `createKey()` separately enforces **privilege containment**: a new key's `scopes` can never include anything the requesting key doesn't itself hold (`403 SCOPE_ESCALATION_FORBIDDEN` otherwise), and omitting `scopes` entirely defaults to *cloning the requesting key's own scopes*, not a blanket full-access default — the latter would silently let a `keys:manage`-only key mint a broader key just by leaving the field out. This check lives in the service, not the route, since it depends on comparing two different scope sets (the request body's vs. the caller's), not just "does the caller have scope X."
- `billing:manage` — `subscriptions.routes.js` and `payments.routes.js` in full (including their reads — bundled the same way `issuers:read`/`write` still bundle each router's whole surface per direction, since there's no separate `billing:read`). Since ADR-035's addendum, holding this scope is necessary but not sufficient for the 9 mutation routes in these two routers — they additionally require `requireInternalService`, so a tenant's own directly-held key can never call them regardless of scope; only comprobify-web's BFF (using a reserved-for-frontend key) can. The 3 reads (`GET /v1/subscriptions/me`, `GET /v1/payments/:id/proofs`, `.../proofs/:proofId`) stay reachable on scope alone.
- `webhooks:manage` — `webhook-endpoints.routes.js` in full. A key without it must not be able to register a *new* webhook endpoint and start receiving the tenant's event fan-out — that's a real exfiltration path, not just an inconvenience.
- `tenant:manage` — `PATCH /v1/tenants/language`, `POST /v1/tenants/agreements` (accepting legal terms).
- `tenant:promote` — `POST /v1/tenants/promote` only, deliberately split out from `tenant:manage` rather than folded in — it mints/revokes every one of the tenant's API keys and flips sandbox→production irreversibly, a much larger blast radius than a language change or accepting a terms update.

`tenants.routes.js`'s reads (`GET /me`, `/agreements`, `/agreements/history`, `/agreements/:type`, `/events`) stay scope-exempt — `GET /me` in particular is basic identity/tier resolution any key needs regardless of scope, mirroring why it's also exempt from `requireMatchingEnvironment`'s sibling checks. `notifications.routes.js`/`catalogs.routes.js` stay fully scope-exempt (notification preferences are low-stakes; catalogs are static reference data, not tenant-specific).

`src/middleware/require-scope.js`'s `requireScope(scope)` is the only **factory** middleware in the codebase (every other gate — `requireNotSuspended`, `requireNotPastDue` — is a bare function) since each route family needs a different scope; it reads `req.apiKey.scopes` (set by `authenticate.js` from the `findByKeyHash` row) and throws `403 INSUFFICIENT_SCOPE` on a miss. **Two different "no explicit scopes" cases, two different outcomes — do not conflate them:** every key that existed before scopes shipped was migrated to hold all 10 (085's backfill, extended by 096 when `documents:void` was added — that's what a full-access key already implicitly had), and every tenant's very first key (minted automatically at registration, outside `POST /v1/keys` entirely) also always gets all 10. But omitting `scopes` on a *new* `POST /v1/keys` call does **not** carry that same blanket default — see `keys:manage`'s entry above, it clones the calling key's own scopes instead.

**Every non-HTTP call site that mints or copies an API key must pass `scopes` explicitly** — `apiKeyModel.create()`'s `scopes` column is `NOT NULL` with no SQL-level default applied when the column is named in the INSERT (which every call site does), so omitting the field throws a DB constraint violation, not a silent fallback. This bit `registration.service.js` (both the initial-signup key and the account-recovery key — either one would have 500'd every call, since neither passed `scopes` — a real, previously-shipped bug from 65d1b47 caught by testing migration 085 against a real DB rather than trusting mocked unit tests), `admin.service.js`'s `createApiKey` (admin-minted keys), and the sandbox→production key-mirroring loops in both `admin.service.js`'s `promoteTenant` and `tenant.service.js`'s `promote` (each iterates a tenant's active sandbox keys and calls `apiKeyModel.create` once per key). The two mirroring call sites pass `scopes: key.scopes` — the **sandbox key's own scopes**, not `ALL_SCOPES` — so promotion preserves whatever scoping a key already had rather than silently upgrading every mirrored key to full access. `registration.service.js`/`admin.service.js`'s direct mints (no prior key to mirror) pass `ALL_SCOPES`. Only `api-key.service.js`'s `createKey()` (the one path with a real "requesting key" in context) uses the containment-checked, clone-yourself-by-default logic described above.

Two read shapes, one table: `apiKeyModel.findActiveByTenantId` (used by both the tenant-facing `GET /v1/keys` and the admin-facing `GET /v1/admin/tenants/:id/api-keys`) `LEFT JOIN LATERAL`s a per-key `SUM(request_count)`/`MAX(last_used_at)` aggregate — surfaced as `lastUsedAt`/`requestCount` through the shared `apiKeyService.formatKey` (the `SUM` comes back as a numeric string, cast to `Number()` there — safe well past any realistic lifetime volume). `apiKeyModel.findDailyUsage(apiKeyId, days)` backs the actual chart: `GET /v1/keys/:id/usage` (tenant) and `GET /v1/admin/tenants/:id/api-keys/:keyId/usage` (admin), both `?days=` 1–365, default 30. It's a `generate_series` LEFT JOINed against the table so the response is always **zero-filled** — exactly `days` entries whether or not the key was used that day — so a frontend chart never has to backfill gaps itself. Ownership is checked via the existing `findByIdAndTenantId` (not filtered to `active` keys), so a revoked key's usage history stays queryable — useful for a post-revocation post-mortem. No sandbox-schema mirroring needed (same precedent as `api_keys` itself — a key's own `environment` column already distinguishes sandbox/production within one table). At realistic scale (a large tenant might reach ~50 keys × 10 years ≈ 180k rows) this needs no retention/pruning for the foreseeable future.

**Suspension reason:** `PATCH /v1/admin/tenants/:id/status` requires a `suspensionReasonCode` from `src/constants/suspension-reasons.js` (`PAYMENT_REVERSED`, `FRAUD_SUSPECTED`, `TERMS_VIOLATION`, `VOLUNTARY_CLOSURE`, `UNPAID_BALANCE`, `OTHER`) whenever the target status is `SUSPENDED` — validator-whitelisted **and** service-re-checked, exactly like `reviewPayment`'s `rejectionReasonCode`, `400 INVALID_SUSPENSION_REASON` otherwise. It replaced a free-text `reason` field: `GET /v1/tenants/events` passes `tenant_events.detail` through verbatim, so whatever an operator typed was readable by anyone holding that tenant's API key — the same problem migration 068 fixed for `payments.rejection_reason`. Written to **both** `tenants.suspension_reason_code` (current state, cleared on any non-`SUSPENDED` transition, surfaced on `GET /v1/tenants/me` via `apiKeyModel.findByKeyHash`'s tenant join) and the `STATUS_CHANGED` event detail as `reasonCode` (history survives reactivation) — the same denormalized-cache-alongside-audit-trail pattern as `tenants.agreement_accepted_at`/`agreement_version`. Localization is the frontend's job. `VOLUNTARY_CLOSURE` is not punitive — the product has no separate "closed" status, so an account-closure request (terms-of-service.md §10) lands in `SUSPENDED` too and must not be worded like a sanction. See ADR-027.

**Suspension:** a `SUSPENDED` tenant is not blocked outright — `src/middleware/require-not-suspended.js` (403 `ACCOUNT_SUSPENDED`) is applied selectively so a suspended tenant can still see what already exists (their own documents/RIDE/XML, subscription and payment-proof history, account status/agreements/events) while every write, and a couple of specific reads that amount to *using* the Service rather than just viewing it, stay blocked. `issuers.routes.js`, `api-keys.routes.js`, `catalogs.routes.js`, `notifications.routes.js`, and `webhook-endpoints.routes.js` have no such exception — `router.use(requireNotSuspended)` right after `router.use(authenticate)` blocks the whole router, same as before this split existed. `documents.routes.js`, `subscriptions.routes.js`, `tenants.routes.js`, and `payments.routes.js` apply it per-route instead, explicitly on each write (and on `GET /:accessKey/authorize`, excluded from the exception because it makes a live SRI call and can fire the authorization email — not passive viewing). A new router with authenticated routes must explicitly decide which pattern it needs; there is no default.

**`PAST_DUE` (ADR-025) is a separate status from `SUSPENDED`, not a reuse of it** — `SUSPENDED` stays exclusively admin-lifted (fraud, ToS violation, voluntary closure); `PAST_DUE` is purely automated (assigned by `subscriptionService.expireSubscription()` when a renewal grace period lapses, see "Recurring renewals" below) and **self-resolving**. `src/middleware/require-past-due.js` (403 `ACCOUNT_PAST_DUE`) is structurally identical to `require-not-suspended.js` and mounted at every single one of its call sites (same routers, same per-route vs. blanket pattern) — a `PAST_DUE` tenant is blocked from the same surface a `SUSPENDED` tenant is, **except** `POST /v1/subscriptions` and `PATCH /v1/payments/:id/proof` are deliberately exempted from `requireNotPastDue` alone (still gated by `requireNotSuspended`) — starting a fresh subscription and paying for it is the actual self-service recovery mechanism. A new router mounting `requireNotSuspended` must mount `requireNotPastDue` alongside it at the same point unless there's a specific, documented reason not to (mirrors Common Mistake #30's existing judgment call, now doubled).

Recovery is "start a brand-new subscription," not "resurrect the expired one" — the old subscription is already `EXPIRED` (excluded from "in-flight" by Common Mistake #31), so `createSubscriptionForTenant`'s existing in-flight check already lets a `PAST_DUE` tenant start again with no special-casing; its status gate only rejects `PENDING_VERIFICATION` now, not "anything non-`ACTIVE`." `applyVerifiedPayment` gains one step at the end of its INITIAL path: if the tenant is `PAST_DUE` when that fresh subscription's first payment is verified, flip to `ACTIVE` and log `STATUS_CHANGED` (`reason: 'payment_recovered'`) — same `STATUS_CHANGED` tenant-event type every other status transition already uses, no new type needed.

**Per-request issuer resolution:** every authenticated document-endpoint request must include an `X-Issuer-Id` header. The `resolveIssuer` middleware (mounted on `/v1/documents/*`) fetches the issuer, validates `issuer.tenant_id === req.tenant.id` (403 ISSUER_FORBIDDEN if not), validates `req.apiKey.environment === (issuer.sandbox ? 'sandbox' : 'production')` (401 on mismatch), and sets `req.issuer`. Issuer-management routes (`/v1/issuers/:id/...`) bypass this middleware and instead read the issuer from `:id` in the URL with an inline ownership check.

**Document quota enforcement:** usage tracking is decoupled from `tenants` entirely — `tenant_quotas` (migration 073, `billing_interval` added by migration 094) holds one row per tenant per period (`period_start`/`period_end`, `document_quota`, `document_count`, `billing_interval`), with an `is_current` flag mirroring `agreements`' per-type versioning pattern (exactly one current row per tenant, enforced by a partial unique index). At the start of every **production** document creation transaction (`!issuer.sandbox`), `document-creation.service.js` calls `tenantQuotaService.consumeOne(client, issuer.tenant_id)`, which runs `UPDATE tenant_quotas SET document_count = document_count + 1 WHERE tenant_id = $1 AND is_current = true AND (document_quota IS NULL OR document_count < document_quota) RETURNING id` atomically inside the caller's transaction — a `NULL` cap (ENTERPRISE, genuinely unlimited as of migration 094, see "Unlimited tiers" below) never blocks, `document_count` still increments for visibility/reporting only. If the row doesn't return, a `QuotaExceededError` (402 QUOTA_EXCEEDED) is thrown and the transaction rolls back. Sandbox documents skip this block entirely — testing against SRI pruebas never consumes a tenant's paid quota. `POST /v1/admin/jobs/quota` (external cron, daily cadence) calls `tenantQuotaService.resetDuePeriods()`, which rolls over every period whose `period_end` has passed — anchored to the OLD `period_end`, never "now" (mirrors `subscription.service.js`'s `addBillingPeriod()` philosophy, Common Mistake #26), sizing the new cap from the tenant's current `subscription_tier` **and** the row's own `billing_interval` (read straight off `tenant_quotas`, not re-derived from `subscriptions` — see "Yearly billing" below for why a period can be a 12-month pool, not always 1 month). A **mid-cycle, same-period** tier/interval change (an immediate upgrade applying within the current billing period, a scheduled downgrade taking effect, expiry to FREE, a sandbox tier change, or a refund's rollback) updates the current period's cap, `billing_interval`, and `period_end` together via `tenantQuotaService.setCap(tenantId, tier, billingInterval)` — `document_count` and `period_start` are never touched, so already-consumed documents this cycle still count against whatever the new cap is.

**Quota period alignment with the subscription's billing period:** for a tenant with an ACTIVE subscription, `tenant_quotas.period_start`/`period_end` are kept in lockstep with `subscriptions.current_period_start`/`current_period_end` — this was **not** always true (see ADR-029's addendum) and used to be a real, shipped bug: the two tables ran on independent clocks, so a quota period could stay anchored to a stale timestamp (e.g. registration, pre-promotion sandbox time) indefinitely, resetting up to a day early/late relative to the actual renewal, or during the unpaid grace window before an actual renewal payment ever verified. Fixed by `tenantQuotaService.syncPeriod(tenantId, periodStart, periodEnd, tier, billingInterval)` — called with the **exact same dates** `subscriptions.current_period_start`/`current_period_end` were just set to (never independently recomputed via `addMonths()`) — at every point a subscription's period genuinely rolls to a new one: `applyInitialPayment` (first activation), `resetPeriodOnPromotion` (sandbox → production — sandbox documents never consumed quota in the first place, so a period still anchored there was measuring nothing real), `applyRenewalPayment` (a verified renewal, precisely — not up to a day later via the cron), and `applyScheduledTierChanges`'s deferred billing-interval-change branch. Unlike `setCap()`, `syncPeriod()` **does** reset `document_count` to 0 (via `tenantQuotaModel.rollover()`, the same one-row-per-period mechanism `resetDuePeriods()` uses) — a genuinely new period starting is exactly when a fresh count is correct, as opposed to a same-period cap resize. `POST /v1/admin/jobs/quota` additionally runs `tenantQuotaService.resyncFromSubscriptions()` (idempotent, safe every run) — a one-time catch-up for any row that drifted before `syncPeriod()` existed on every call site, correcting only `period_start`/`period_end`/cap on the CURRENT row in place (`tenantQuotaModel.resyncPeriod()`, never `rollover()`) since it's a data correction to the *same* ongoing period, not a new one — `document_count` must not be wiped by a bug fix. `resetDuePeriods()`'s independent daily-cron rollover remains the only mechanism for a FREE-tier tenant (no subscription ever drives their quota period) and a safety net for anything that falls behind. `src/models/api-key.model.js`'s `findByKeyHash` (the query behind `authenticate` middleware and `GET /v1/tenants/me`) `LEFT JOIN`s the tenant's current `tenant_quotas` row — LEFT, not INNER, so a tenant somehow missing a quota row degrades to `documentCount`/`documentQuota: null` rather than breaking authentication.

**Unlimited tiers (ADR-029):** `TIERS.ENTERPRISE.documentQuota` is `null`, the same "unlimited" convention `maxBranches`/`maxIssuePointsPerBranch` already use — not the large sentinel (`100000`) it used to be. `tenant_quotas.document_quota` is nullable as of migration 094 specifically so this could stop being a sentinel: `tenantQuotaService.capForTier(tier, billingInterval)` returns `null` straight through for a tier whose `documentQuota` is `null`, and every write path (`incrementIfWithinCap`, `updateCapAndInterval`) treats a `NULL` cap as "never block". `capForTier`/the `documentQuota` computation in `admin.service.js`'s `createTenant` both resolve a tier via `TIERS[tier] || TIERS.FREE`, never `TIERS[tier]?.documentQuota ?? TIERS.FREE.documentQuota` — the latter's `??` would collapse ENTERPRISE's legitimate `null` back down to FREE's cap, since `??` treats `null` and `undefined` identically; the fallback-to-FREE is only for a genuinely unrecognized tier string.

**Tier-aware rate limiting (ADR-026):** `writeLimiter` and `readLimiter` in `src/middleware/rate-limit.js` read `req.tenant.subscriptionTier` and return the tier's limit dynamically. `adminLimiter` is an IP-based limiter on all admin routes that counts **only requests whose `ADMIN_SECRET` did not check out** (`skipSuccessfulRequests: true` plus `requestWasSuccessful: (req) => req.adminAuthenticated === true`, the flag `authenticate-admin.js` sets on a valid secret). It is mounted *before* `authenticateAdmin`, so its job is brute-force protection on the secret, not throttling the operator — counting both against one budget meant the attacker case set the ceiling for everyone, and since comprobify-web is a server-side BFF every admin request arrives from a single IP, exhausting the old fixed 20/min within a couple of page renders. `ADMIN_RATE_LIMIT_MAX` (default 20) is the failed-attempt ceiling. Deliberately *not* the default `status < 400` definition of "successful": an authenticated operator hitting a 404 or a validation error is not a guessing attempt. Accepted trade-off: because the limiter precedes auth, an IP that spends its failure budget is refused for the rest of the window even with a valid secret — a service misconfigured with the wrong secret locks out its own IP until the window rolls. All four limiters (`writeLimiter`/`readLimiter`/`adminLimiter`/`registrationLimiter`) are backed by a **shared Redis store** — `buildStore(prefix)` returns a `RedisStore` (via `src/services/redis.service.js`'s singleton `ioredis` client) when `REDIS_URL` is configured, or `undefined` (express-rate-limit's own in-memory store, correct only for a single API instance) otherwise. Each limiter uses its own key prefix (`rl:write:`, `rl:read:`, `rl:admin:`, `rl:registration:`) so their counters never collide in the same Redis keyspace. `REDIS_URL` is optional — absent means degraded-but-functional, not startup-blocking (same precedent as `SENTRY_DSN`), correct for today's single-`api`-instance topology; it becomes load-bearing the moment more than one `api` instance runs, since otherwise each instance enforces its own independent counter and a tenant can burst to roughly `limit × N`. Every limiter also sets `passOnStoreError: true` — a Redis outage fails **open** (allows the request, `console.error`-logs the store error) rather than 500ing every rate-limited request; a Redis outage would otherwise be strictly worse than the multi-instance under-limiting problem this store exists to fix.

**Repeated-attempt detection (ADR-026):** `src/services/attempt-tracker.service.js`'s `recordEvent(eventType, key)` is a small, reusable **detection** mechanism (not prevention — every secret at every call site below is already high-entropy and computationally infeasible to guess) for a repeated-attempt pattern against the same `(eventType, key)` pair. Reuses `src/services/redis.service.js`'s shared client rather than a second connection — a no-op (`recordEvent` returns `false` immediately) when `REDIS_URL` is unset, same optional-degrades-gracefully treatment as the rate limiters. Implementation: `INCR` on `attempt:{eventType}:{key}`, `PEXPIRE` to `config.attemptTracker.windowMs` only on the first hit (`count === 1` — the atomicity of `INCR` makes this race-safe), returns `count >= config.attemptTracker.threshold`. One shared threshold/window across every event type (`ATTEMPT_TRACKER_THRESHOLD`/`ATTEMPT_TRACKER_WINDOW_MS`, defaults 5 within 15 minutes), not per-type — revisit only if a concrete false-positive/negative problem shows up. On the exact count that crosses the threshold (once per window, not on every subsequent request past it), fires both a `console.warn` and `Sentry.captureMessage(message, { level: 'warning', tags: { eventType }, extra: { key, count } })` — `Sentry.captureMessage` mirrors `workers/worker.js`'s existing precedent of calling Sentry explicitly outside its normal auto-5xx-capture path (`require('../../instrument')`, the module that actually calls `Sentry.init()`), and is what makes a crossing visible immediately (an alert), as opposed to the "Structured request logging" entry below, which makes it independently queryable after the fact — the `console.warn` line is kept too, both for local dev without `SENTRY_DSN` and because it's picked up by the same structured-logging pipeline once shipped through it. See `docs/guides/repeated-attempt-detection.md` for where alerts actually surface and how to respond to one. The whole call is wrapped in try/catch and fails open on any Redis error — this must never gate or slow down the auth/recovery flow it's embedded in. Four wired call sites, each described in `src/constants/attempt-event-types.js`'s `AttemptEventTypes`: `RECOVERY_SUCCESS` (`registration.service.js`'s `recover()`, keyed by `tenant.id` — records the *successful* match, not a failure, since the endpoint's anti-enumeration design makes every non-match look identical already), `API_KEY_AUTH_FAILURE` (`authenticate.js`, keyed by the attempted `keyHash`), `ADMIN_AUTH_FAILURE` (`authenticate-admin.js`, keyed by `ipKeyGenerator(req.ip)`), `MAILGUN_WEBHOOK_INVALID_SIGNATURE` (`verify-mailgun-webhook.js`'s signature-mismatch branch only, keyed by `ipKeyGenerator(req.ip)`). The two already-`async` call sites (`recover()`, `authenticate`) `await` the call; the two synchronous middleware (`authenticate-admin.js`, `verify-mailgun-webhook.js`) fire-and-forget it (no `await`, no signature change) since `recordEvent` never throws.

**Subscription + payment pipeline (ADR-017, activation clause superseded by ADR-027, mutations frontend-gated by ADR-035's addendum):** `subscriptions` and `payments` tables track a tenant's paid-tier billing. Every mutation described below (`POST /v1/subscriptions`, `.../change-tier`, `.../seats`, `DELETE /v1/subscriptions`, `DELETE /v1/payments/:id`, `PATCH /v1/payments/:id/proof`, `DELETE /v1/payments/:id/proofs/:proofId`, and both Payphone endpoints) requires `requireInternalService` on top of the normal tenant-API-key `authenticate` + `billing:manage` chain — only comprobify-web's own BFF can call them, the same shape as ADR-035's account-lifecycle gate but for a different reason (UX consistency, not anonymous-abuse prevention — see the ADR's addendum). The 3 reads (`GET /v1/subscriptions/me`, `GET /v1/payments/:id/proofs`, `.../proofs/:proofId`) stay reachable with just the tenant's own key. **A verified payment alone grants access — a subscription reaches `ACTIVE` the moment its payment is verified, with no wait on the operator's self-billed invoice.** ADR-017 originally gated activation on that invoice being SRI-`AUTHORIZED`; ADR-027 removed the gate, because it made the *customer* absorb an *operator*-side obligation (a tenant whose money was already captured sat locked out through any SRI outage) while never actually detecting anything. The invoice obligation is now tracked by an operator work queue instead — see "Operator invoicing queue" below. Tier selection can happen two ways: tenant-initiated via `POST /v1/subscriptions` (`{ tier, billingInterval }`, gated on `tenant.status === ACTIVE` only — works while still in sandbox, since paid-tier grants don't depend on sandbox status either, see below), or at **promotion** — `POST /v1/tenants/promote` (tenant-facing) still accepts the same optional `tier`/`billingInterval` fields for a tenant who didn't pre-subscribe. Promotion itself (sandbox flip, key rotation) always proceeds immediately regardless of billing state. `tenant.service.js`'s `promote()` checks `subscriptionModel.findActiveOrPendingByTenantId()` first — any subscription not `CANCELLED`/`EXPIRED` (`PENDING_PAYMENT` or `ACTIVE` in practice; `PAYMENT_RECEIVED`/`INVOICE_PROCESSING` are legacy values nothing writes any more), not just `ACTIVE`: if one already exists (e.g. started pre-promotion via `POST /v1/subscriptions`), any `tier`/`billingInterval` passed to `promote` is ignored entirely and the response surfaces that existing subscription instead of starting a new one; only when no such subscription exists does a supplied `tier` kick off the pipeline in the background. `resetPeriodOnPromotion()` still only fires when that existing subscription's status is already `ACTIVE` — a still-`PENDING_PAYMENT` subscription has no period yet to reset. Both tenant-facing entry points funnel into the same `subscriptionService.createSubscription()` — `createSubscriptionForTenant()` is just the `POST /v1/subscriptions` wrapper that adds the ACTIVE-tenant-status gate (the admin route `POST /v1/admin/tenants/:id/subscriptions` calls `createSubscription` directly, bypassing that gate, since admin-created tenants are already `ACTIVE` by construction).

Flow: subscription created (`PENDING_PAYMENT`) + a `payments` row priced from `pricingService.getCurrentPrice(tier, billingInterval)` (see "Price history + 30-day change notice" above; response includes `bankTransfer` instructions from `config.bankTransfer`) → the **tenant** (their own API key, not admin) uploads proof of the SPI transfer via `PATCH /v1/payments/:id/proof` (multipart, ownership-checked against `req.tenant.id` inside `subscriptionService.submitPaymentProof` — accepts 1–5 files per request, see "Payment proof files" below) → moves the payment to `REPORTED` → the **operator** reviews the uploaded files (`GET /v1/admin/payments/:id/proofs` to list them, `.../proofs/:proofId` to view one, mirrors the RIDE PDF `res.send(buffer)` pattern) and calls `PATCH /v1/admin/payments/:id/review` (`{ decision: "VERIFIED" | "REJECTED", rejectionReasonCode }` — one endpoint, not two, since it's one decision). `rejectionReasonCode` is a **predefined enum** (`src/constants/rejection-reasons.js`: `AMOUNT_MISMATCH`, `TRANSFER_NOT_FOUND`, `WRONG_ACCOUNT`, `ILLEGIBLE_PROOF`, `DUPLICATE_SUBMISSION`, `OTHER`), not free text — **required and validator-whitelisted** when rejecting (400 `INVALID_REJECTION_REASON` otherwise, re-checked at the service layer too) — so a frontend can map the stable code to its own localized message instead of displaying whatever an admin typed. Stored as `payments.rejection_reason_code` (migration 068, replaces the old free-text `rejection_reason` column entirely). A `REJECTED` payment can be re-submitted via the same `PATCH /v1/payments/:id/proof` (adds more files without touching the ones already uploaded, clears `rejection_reason_code`, moves back to `REPORTED`) — `submitPaymentProof` only refuses once a payment is `VERIFIED`.

**`VERIFIED` is where everything happens.** `reviewPayment()`'s VERIFIED branch calls `subscriptionService.applyVerifiedPayment(payment, subscription)` — the single place a verified payment becomes access, replacing the deleted `activateIfLinked`/`applyTierChangeIfLinked`/`applyRenewalIfLinked`/`applyPendingInvoiceLinks` quartet (all four existed only to react to invoice authorization). It dispatches on `payment.purpose`: `INITIAL` → subscription `ACTIVE`, period opened anchored to "now" (correct here — first cycle, one of the two documented exceptions to Common Mistake #26), `tenantModel.updateTier` **paired with** `tenantQuotaService.setCap` (#38), `SUBSCRIPTION_ACTIVATED` logged, plus the `PAST_DUE` → `ACTIVE` self-service recovery step (ADR-025); `TIER_CHANGE` → immediate tier flip, or `scheduleDowngrade` when `target_billing_interval` is set (deferred interval change, unchanged — and deliberately leaves `period_start` unstamped, since that's what marks the payment still-unapplied); `RENEWAL` → period extended anchored to the **old** `current_period_end`, never "now" (#26). It also records `payments.applied_from`, the rollback snapshot the refund endpoint restores (see "Refunds and reversals" below).

**Card payments (ADR-028).** A tenant can pay any `payments` row by card instead of by SPI transfer, via Payphone's Cajita de Pagos widget: `POST /v1/payments/:id/payphone-session` mints the widget config (amounts converted to integer cents, with `amountWithTax` **derived** as `amount - tax` rather than independently rounded, since Payphone enforces `amount = amountWithoutTax + amountWithTax + tax + service + tip` and rounding both halves separately can break it by a cent), and `POST /v1/payments/payphone/confirm` — called by comprobify-web's return page — captures the charge server-side and calls the same `applyVerifiedPayment` a verified transfer does. **Payphone auto-reverses any charge not confirmed within 5 minutes**, which is why the return page must confirm on load rather than behind a click. `payphone_transactions` records **one row per attempt** (`PENDING`/`APPROVED`/`CANCELLED`/`EXPIRED`/`DUPLICATE`/`ERROR`), claimed `FOR UPDATE` across the vendor call so a replayed return page makes no second confirm. Three things are deliberate and easy to get wrong if touched: a **transport failure leaves the attempt `PENDING`**, never terminal (an unresolved charge must not look like a decline); the vendor outcome **commits before** the apply runs, so `applied_at` marks the second phase and `POST /v1/admin/jobs/payphone-reconciliation` re-applies anything `APPROVED` with `applied_at IS NULL`; and a **duplicate charge** (two tabs) is marked `DUPLICATE` and never applied, only alerted, since applying twice would double-extend a period. **`resolveOutcome`'s `catch` block persists `payphone_transaction_id` on its own, best-effort, whenever the outcome-write itself throws** (mirrors the same defensive persist already done on the transport-failure path) — without it, a charge Payphone actually captured but whose result we failed to save (for any reason — the reason found in production was `card_brand`/`authorization_code` exceeding their then-`VARCHAR` widths, migration 100, both now `TEXT` since there's no length guarantee from Payphone's side to size a `VARCHAR` against) would look identical to a return page that never arrived, and `findStalePending()` gives up on those without ever retrying. Three guards on `createSession`, each found by testing against the live vendor rather than by reasoning: **charges under $1.00 are refused** (`400 PAYPHONE_AMOUNT_BELOW_MINIMUM` — Payphone's `errorCode 107`, undocumented by them, reachable via a small prorated upgrade); **at most 10 unresolved attempts per payment** (`409 PAYPHONE_TOO_MANY_ATTEMPTS` — attempts are never reused, since a `PENDING` row with no vendor id can't be told apart from one Payphone is holding a charge for); and the `reference` carries `os.hostname()` outside production, since `APP_ENV` is `staging` both locally and on the droplet. `PAYPHONE_TOKEN`/`PAYPHONE_STORE_ID` are optional (`REDIS_URL` pattern) — unset means `503 PAYMENT_GATEWAY_NOT_CONFIGURED` and SPI is untouched. Full operational detail, including the "I paid but nothing happened" diagnostic path, is in `docs/guides/payphone-payments.md`.

**Operator invoicing queue.** `GET /v1/admin/invoicing/pending` returns `{ count, items }` — every `VERIFIED` payment with `invoiced_at IS NULL`, carrying the amounts, the period being billed, and the buyer's legal identity (`business_name`/`ruc`/`main_address`, resolved from the tenant's oldest active issuer via a `LEFT JOIN LATERAL`, since `tenants` itself carries only `email`) so an admin UI can prefill an invoice form. The operator self-bills through their own issuer, then calls `PATCH /v1/admin/subscriptions/:id/link-invoice` (`{ accessKey }`), which is now **pure bookkeeping** — it triggers no state transition whatsoever. It resolves which payment the invoice settles via `paymentModel.findOldestUninvoicedBySubscriptionId` (409 if none), records `subscriptions.initial_invoice_document_id` for an `INITIAL` payment or `payments.invoice_document_id` otherwise (never both — Common Mistake #37), stamps `invoiced_at`, and logs `INVOICE_LINKED`. **`invoiced_at`, not `invoice_document_id`, is the queue signal**: a sandbox-linked document sets neither FK (both reference `public.documents`; `sandbox.documents` is an independent id sequence that can collide with it), so the FK would report an already-invoiced sandbox payment as pending forever — see Common Mistake #35. There is deliberately no operator notification email: the operator is the one calling `review`, so they already know an invoice is owed the moment they verify.

**Tenant-initiated payment cancellation:** `DELETE /v1/payments/:id` (`subscriptionService.cancelPayment()`, migration 098) lets a tenant back out of a payment they created by mistake — e.g. picked the wrong tier or seat count and doesn't want to pay for it — before ever transferring anything. Deliberately a third, distinct terminal state from the two that already existed: `REJECTED` means an operator reviewed *submitted* proof and found it wanting (has its own resubmit path via `PATCH /v1/payments/:id/proof`); `REFUNDED` means money already moved and is being reversed (see "Refunds and reversals" below). `CANCELLED` (added to `chk_payments_status` by migration 098, alongside a `payments.cancelled_at` column) means neither happened — only a still-`PENDING` payment qualifies (`409 PAYMENT_NOT_CANCELLABLE` otherwise), since once proof is uploaded (`REPORTED`) the tenant is claiming a transfer already happened and that claim needs an operator's eyes, not a silent self-cancel. `RENEWAL` payments are excluded from self-cancellation too, even while `PENDING` — the renewal/grace-period machinery (`processDueRenewals`) assumes one open payment per due cycle, and cancelling it here would leave nothing to replace it until the next scheduled reminder pass. Cancelling an `INITIAL` payment additionally cancels its still-`PENDING_PAYMENT` subscription in the same call — that's the only payment such a subscription will ever have, and leaving the subscription behind would keep it blocking a fresh `POST /v1/subscriptions` forever (`findActiveOrPendingByTenantId` matches anything not `CANCELLED`/`EXPIRED`, regardless of the payment's own status). `TIER_CHANGE`/`SEAT_CHANGE` cancellations need no such step — the subscription was already `ACTIVE` throughout and stays untouched; the guard queries (`findPendingTierChangeBySubscriptionId`/`findPendingSeatChangeBySubscriptionId`, both filtered to `status IN ('PENDING','REPORTED','VERIFIED')`) simply stop matching a `CANCELLED` row, immediately freeing the tenant to request the correct tier/seat count. Logs `PAYMENT_CANCELLED` (and `SUBSCRIPTION_CANCELLED` too, for the `INITIAL` case).

**Refunds and reversals.** Detecting a reversal is inherently manual — an SPI reversal appears only on a bank statement, and no rail notifies the API. Responding to one could not be left to `PATCH /v1/admin/tenants/:id/tier`, which writes only `tenants.subscription_tier` + the quota cap and **never touches `subscriptions.tier`** — a hand-rolled downgrade left the subscription claiming the reversed tier, and `createRenewalReminder` prices the next renewal off `subscription.tier`, so the tenant would be billed for an upgrade they never paid for. `PATCH /v1/admin/payments/:id/refund` (`{ reason? }`) restores `payments.applied_from` — `{ tier, billingInterval, periodStart, periodEnd, subscriptionStatus, tenantTier, extraSeats }` (the last added by ADR-032), captured by `applyVerifiedPayment` immediately *before* it changed anything — marks the payment `REFUNDED` (a value that had sat unused in `chk_payments_status` since migration 052), and logs `PAYMENT_REFUNDED`. **Rolling back is not "downgrade to FREE"**: a reversed `TIER_CHANGE` returns to the *previous paid tier*, a reversed `RENEWAL` rolls the period back without touching tier at all, a reversed `SEAT_CHANGE` restores `extra_seats` alone (and only a `SEAT_CHANGE` refund touches it — restoring it on every refund would wipe out an unrelated, legitimately-scheduled pending seat decrease), and only a reversed `INITIAL` ends at FREE (and cancels the subscription rather than restoring its `PENDING_PAYMENT` snapshot status, which would look payable while its only payment is refunded). `tenantTier` is snapshotted separately from the subscription's own tier because they legitimately differ — an `INITIAL` payment's subscription already reads `STARTER` at creation while the tenant is still `FREE`. Refuses with `400 PAYMENT_NOT_REFUNDABLE` when `applied_from` is absent (a payment applied before migration 090) rather than guessing, and `409` when the payment isn't `VERIFIED`. Deliberately does **not** auto-suspend — whether a reversal warrants `SUSPENDED` (fraud) or nothing (an honest duplicate charge) is a separate operator judgement.

`PATCH /v1/admin/tenants/:id/tier` (the direct admin override, bypassing this whole pipeline) logs a `TIER_CHANGED` tenant event. `GET /v1/subscriptions/me` (tenant-facing) returns the tenant's full subscription history with payments nested (proof files are never inlined — see "Payment proof files" below) — this plus `GET /v1/tenants/me` (for the resulting tier/quota) is how a tenant finds out a review happened. The schema deliberately has **no payment-gateway-specific columns** — no vendor references exist until a gateway is actually decided and built; those land in their own dedicated migration at that point (see NEXT_STEPS.md's "Payment Gateway Integration" item).

**Payment proof files:** proof-of-transfer files live in their own append-only `payment_proofs` table (migration 069), one row per uploaded file — not columns on `payments` (the original `proof_file`/`proof_filename`/`proof_mime_type` columns from migration 053 were dropped). `PATCH /v1/payments/:id/proof` accepts up to 5 files per request (`multer.array('proof', 5)`, same field name repeated per file — the standard multipart convention for an array); `subscriptionService.submitPaymentProof()` additionally caps the *cumulative* active count per payment at `MAX_ACTIVE_PROOFS_PER_PAYMENT` (10), across every upload attempt combined, rejecting with `400 PROOF_FILE_LIMIT_REACHED` past that — this stops repeated resubmission from growing the file list unboundedly. Nothing is ever overwritten: a resubmission after `REJECTED` only *adds* rows, so every file from every attempt (including rejected ones) stays visible for audit purposes. "Delete" (`DELETE /v1/payments/:id/proofs/:proofId`, tenant-facing, blocked once `VERIFIED`) is a **soft** delete (`payment_proofs.active = false`, never a hard `DELETE` — CLAUDE.md rule #7) — a tenant who deletes a file loses their own access to it (`GET /v1/payments/:id/proofs` and `.../proofs/:proofId` both filter to `active = true` for the tenant), but the admin equivalents (`GET /v1/admin/payments/:id/proofs` list, `.../proofs/:proofId` download) always show/serve every row regardless of `active`, so the audit trail survives tenant-side deletion. `src/models/payment-proof.model.js` owns all of this — `createMany`, `findActiveByPaymentId`/`findAllByPaymentId`, `findByIdAndPaymentId`, `countActiveByPaymentId`, `softDelete`. Uses plain `db.query()`, same precedent as `payments`/`subscriptions` (not issuer-scoped, no RLS). `PATCH /v1/payments/:id/proof` also requires a `referenceNumber` body field (max 50 chars, validated in `payments.routes.js`) — the SPI transfer's own reference/confirmation number from the tenant's bank, distinct from `payment.id`. It's stored per file row (`payment_proofs.reference_number`, migration 071 — nullable in the DB since it postdates the table, required at the API layer for every new submission) rather than on a separate submission-level record, since every file uploaded in the same request shares one value and the table has no other concept of "submission." Surfaced back via `formatPaymentProof()`'s `referenceNumber` field (both the tenant list/download responses and the admin equivalents, since both read through the same presenter) and included in the operator-facing `sendPaymentProofSubmitted` email so the operator can cross-reference it against their bank statement.

**Payment code (pre-transfer, not to be confused with `referenceNumber` above):** `payments.payment_code` (migration 097) is a short, hand-typable identifier — e.g. `CB-4K7N9QRT`, 8 characters from a 31-symbol alphabet that excludes lookalikes (`0`/`O`, `1`/`I`/`L`) — generated at row-creation time by a DB function, `generate_payment_code()`, set as the column's `DEFAULT`. No application code generates it: same "let Postgres own the id" precedent as `uuid_generate_v7()` (see "Key Patterns" above), just without the retry-loop concern — at Comprobify's billing volume (subscriptions/payments, not documents), an 8-char/31-symbol space needs no collision handling. Where `referenceNumber` is the tenant's own bank-issued confirmation number, entered *after* the transfer as part of proof submission, `payment_code` exists *before* the transfer — the tenant is meant to write it into the transfer's own description/glosa field, so the operator can search for it directly in their bank portal without waiting for proof to be uploaded. Since `payments` has no presenter layer (every read is `SELECT *`/`RETURNING *`, per the table's own precedent), it needs zero route-level plumbing to appear in every payment-returning response — `POST /v1/subscriptions`, `.../change-tier`, `.../seats`, `GET /v1/subscriptions/me`, and both admin payment listings pick it up automatically. Two places do carry it further: `notificationService.createSubscriptionRenewalDue()`'s metadata (since a renewal payment is created by a cron job, not returned synchronously to an HTTP caller — the code only reaches the tenant via the `SUBSCRIPTION_RENEWAL_DUE` email) and `payment-proof-submitted.js`'s operator email (a second cross-reference alongside `referenceNumber`).

**Tier and billing-interval changes:** `POST /v1/subscriptions/change-tier` (`{ tier, billingInterval? }`, tenant-facing) lets a tenant with an `ACTIVE` subscription move to a different paid tier and/or switch cadence (e.g. monthly STARTER → yearly GROWTH, or monthly GROWTH → yearly STARTER as a downgrade). `billingInterval` is optional — omitting it targets the subscription's current interval, so tier-only callers behave exactly as before. No automated billing gateway exists (see NEXT_STEPS.md's "Payment Gateway Integration" item), so this rides the same manual proof/review pipeline as initial promotion rather than charging anything automatically. `requestTierChange` picks one of four paths:
- **Same-interval upgrade** (target tier's `priceMonthlyUsd`/`priceYearlyUsd` higher than the current tier's, interval unchanged) takes effect immediately, gated on payment. Prorates the difference by the fraction of the current `current_period_start`–`current_period_end` window remaining, and creates a `payments` row (`purpose: 'TIER_CHANGE'`, `target_tier`) on the **existing** subscription — not a new subscription row, since the subscription itself doesn't change until the upgrade is paid for. The tenant uploads proof via the same `PATCH /v1/payments/:id/proof` used for initial payments (no new upload endpoint). Admin reviews it the same way (`PATCH /v1/admin/payments/:id/review`), then calls the same `PATCH /v1/admin/subscriptions/:id/link-invoice` — `linkInvoice` records the invoice against the **payment's** `invoice_document_id` instead of the subscription's (`subscriptions.initial_invoice_document_id` — named for what it is: the invoice that funded the subscription's *original* activation, stays exactly as set then and is never overwritten by a later upgrade). `applyVerifiedPayment` applies it at payment-verification time (ADR-027 — no invoice involved); since `payment.target_billing_interval` is null for this path, it flips `subscriptions.tier` to `target_tier` immediately, calls `tenantModel.updateTier()`, and stamps the payment's `period_start`/`period_end` to match the (unchanged) subscription period — the upgrade takes over the remainder of the same cycle, it does not start a fresh one. If the prorated amount rounds to `$0` (~no time left in the current period), `requestTierChange` skips the payment/proof step entirely and applies the upgrade immediately — a tenant can't submit proof of a $0 transfer, and there's nothing to collect.
- **Same-interval downgrade** (lower price, interval unchanged) is scheduled, not immediate, and needs no payment — the current period is already paid for at the higher tier. `requestTierChange` just sets `subscriptions.pending_tier`; the tenant's tier/quota stay untouched until `current_period_end`.
- **Cross-interval upgrade, MONTHLY → YEARLY only (ADR-033):** if the switch is a genuine upgrade by **monthly-equivalent price** (`yearlyPrice / 12` for the target tier `>` the current tier's monthly price) — e.g. STARTER MONTHLY → ENTERPRISE YEARLY — it applies **immediately with a prorated credit**, the same shape as a same-interval upgrade: `credit = currentMonthlyPrice × remainingFraction`, charged `= targetYearlyPrice + seats×seatPrice − credit`. This is the *one* interval-change direction where an immediate credit can never mathematically exceed the new charge (at most one month's credit from the cheaper old plan, against a full year at the pricier new rate — the charge is always at least ~11× the maximum possible credit), which matters because **this codebase has no mechanism to pay money back to a tenant** (see "Refunds and reversals" below) — any proration scheme that could produce a negative amount (a credit owed) is unsafe, which every other interval-change direction risks. `requestTierChange` creates the `payments` row with `interval_change_immediate: true` (migration 099) — a flag decided once at request time and persisted, not re-derived from (possibly since-changed) pricing data at verification time. `applyVerifiedPayment` → `applyTierChangePayment` checks this flag first: if set, it applies the tier **and** starts a genuinely **new** period right now (`applyImmediateIntervalUpgrade`: `subscriptionModel.applyTierChange` + `updateStatus` with a fresh `current_period_start`/`current_period_end` + `tenantQuotaService.syncPeriod`, **not** `setCap` — this is a new period, not a mid-cycle cap resize) — unlike the same-interval case below, which keeps the existing cycle's dates. If the prorated amount rounds to `$0` (mathematically near-unreachable given the safety margin above, but handled defensively the same way the same-interval upgrade's `$0` case is), it applies directly via the same helper with no payment created.
- **Any other billing-interval change** — same tier, a tier downgrade, or a MONTHLY → YEARLY switch that *isn't* a monthly-equivalent upgrade (e.g. GROWTH MONTHLY → STARTER YEARLY) — is deferred to `current_period_end` and billed at the new tier+interval's **full sticker price, never prorated**: the potential credit for unused time in the old plan can be large relative to the new charge (up to a full year's worth, switching away from an expensive YEARLY plan), and this codebase has no way to refund the difference if a credit ever exceeded it — so the current period simply runs out as already paid for, and the new cadence starts its own fresh, fully-paid period, with no proration math needed at all. `requestTierChange` creates a `payments` row (`purpose: 'TIER_CHANGE'`, `target_tier`, `target_billing_interval`, `interval_change_immediate` left `false`) exactly like the upgrade path, but `applyVerifiedPayment` checks `payment.target_billing_interval` first — if set (and `interval_change_immediate` is `false`), it does **not** flip the tier immediately; instead it calls `subscriptionModel.scheduleDowngrade(id, target_tier, target_billing_interval)` (setting both `pending_tier` and `pending_billing_interval`) so the change waits for `current_period_end` like a free downgrade, just now paid-for in advance.
- `POST /v1/admin/jobs/subscriptions` (external cron, daily cadence is enough — unlike the minute-level notification job) calls `subscriptionService.applyScheduledTierChanges()`, which finds every `ACTIVE` subscription with a `pending_tier` past its `current_period_end` — this now covers both free same-interval downgrades and paid deferred interval changes, since both end up setting `pending_tier`. It flips `tier` (and `billing_interval`, via `applyTierChange`'s optional third argument, if `pending_billing_interval` was set), clears both pending columns, grants the new quota, and **rolls `current_period_start`/`current_period_end` forward using the new interval** (`subscription.pending_billing_interval || subscription.billing_interval` — using the *old* interval here would mis-size the new period once interval can change via a pending change). If the change was a paid interval switch, it also stamps `period_start`/`period_end` onto the funding `TIER_CHANGE` payment for per-cycle history, same as `applyVerifiedPayment` does for its own funding payment.
- All four paths reject with `409 NO_ACTIVE_SUBSCRIPTION` if the tenant has no `ACTIVE` subscription, `400 TIER_CHANGE_NO_OP` if both `tier` and the resolved `billingInterval` match the current subscription, `400 INVALID_BILLING_INTERVAL` if `billingInterval` is supplied but not `MONTHLY`/`YEARLY`, and `409 TIER_CHANGE_ALREADY_PENDING` if a change is already scheduled or a payment is already in flight — only one tier/interval change can be outstanding at a time. All log a tenant event (`TIER_CHANGE_REQUESTED` when a payment is created, `TIER_CHANGE_SCHEDULED` for a free downgrade at request time or a paid interval change once it's scheduled after authorization; the eventual flip logs `TIER_CHANGED`, the same event type the direct admin override already uses) — event `detail` includes `fromBillingInterval`/`toBillingInterval` alongside `fromTier`/`toTier` so the tenant event log (see below) shows the full history of both dimensions changing over time.
- **While `tenant.sandbox === true`, none of the above four paths apply** — `requestTierChange` branches into `requestSandboxTierChange` instead, right after the shared guards. Sandbox has no meaningful `current_period_end` to prorate against or defer a change to: `resetPeriodOnPromotion` (called from `tenant.service.js`'s `promote()`) discards whatever period was running in sandbox entirely, resetting `current_period_start`/`end` to the moment of promotion regardless of what came before. So every sandbox tier/interval change is priced as the **difference against the tier already paid for** — no time-proration, since there is no real period, but crediting the previous payment so the overlap isn't charged twice, and applies **immediately** once the payment is verified, never deferred to a period boundary that's about to be thrown away — `applyTierChangePayment` defers only for non-sandbox tenants, and passes `target_billing_interval` through on the immediate path so a sandbox interval change actually lands. A downgrade still owes nothing (that's about "you already paid for this," not period math) but also applies immediately rather than being scheduled — so sandbox `pending_tier`/`pending_billing_interval` are never set at all, which incidentally means there's nothing left for `resetPeriodOnPromotion` to worry about clearing at promotion time. Sandbox paths don't build a `pricing_breakdown` (see below) — they're a testing-only mode, out of scope for the frontend-facing breakdown feature.

**Pricing breakdown:** every proration-capable path in `requestTierChange` (the same-interval upgrade, the cross-interval immediate upgrade, and the deferred fallback) and `requestSeatChange`'s increase branch builds a `breakdown` object — returned synchronously alongside `payment`/`subscription` from the request, and persisted on the payment itself as `payments.pricing_breakdown` (`JSONB`, migration 101) so it can be shown again later exactly as computed, rather than recomputed from (possibly since-changed) pricing data. `INITIAL`/`RENEWAL` payments never set one — a flat sticker price needs no breakdown. Shape varies by `breakdown.model`, a discriminator the frontend/email code switches on:
- `SAME_INTERVAL_UPGRADE`: `{ currentTierPrice, newTierPrice, priceDifference, remainingFraction, proratedBase }` — `proratedBase = priceDifference × remainingFraction`, matching the upgrade's own "only pay the incremental difference for the remaining days" model.
- `CROSS_INTERVAL_UPGRADE`: `{ newTierPrice, seatsCount, seatPrice, seatsCost, fullPrice, previousPlanPrice, remainingFraction, credit, proratedBase }` — `fullPrice = newTierPrice + seatsCost`, `proratedBase = fullPrice − credit`.
- `DEFERRED_FULL_PRICE`: `{ newTierPrice, seatsCount, seatPrice, seatsCost, fullPrice, proratedBase: null, credit: 0 }` — `proratedBase` is explicitly `null` (not `0`) to signal "no proration happened here" rather than "prorated to zero."
- `SEAT_INCREASE`: `{ seatDelta, seatPrice, remainingFraction, proratedBase }`.

Consumed in two places: `notificationService.createPaymentReviewed()` copies `payment.pricing_breakdown` into the `PAYMENT_VERIFIED`/`PAYMENT_REJECTED` notification's `metadata.pricingBreakdown`, and `notification-email-template.service.js`'s `formatPricingBreakdown(breakdown, language)` renders it into one localized, newline-joined text block (the per-language heading lives *inside* this string, not as separate static template text — so a payment with no breakdown renders nothing at all, never an empty heading over a blank list) substituted as `{{breakdownText}}` into both the `PAYMENT_VERIFIED`/`PAYMENT_REJECTED` email templates (wrapped in a `white-space: pre-line` element in the HTML body, since `substituteHtml()` would otherwise escape any raw `<br>`/`<table>` markup passed as a value). The operator-facing `payment-proof-submitted.js` template (English-only, no locale system) mirrors the same model-to-lines logic independently, reading `payment.pricing_breakdown` directly since it isn't localized through the DB-template pipeline.

**Extra user seats (ADR-032):** `POST /v1/subscriptions/seats` (`{ extraSeats }`, tenant-facing, absolute target count not a delta) lets a tenant with an `ACTIVE` subscription buy seats above `TIERS[tier].maxUsers` — a cap comprobify never enforces itself (no user/session concept exists here at all, see "Tenant model" above and ADR-031); this only bills for the entitlement and publishes it (`extraSeats`/`pendingExtraSeats` on `req.tenant`, via a `LEFT JOIN subscriptions ... AND status = 'ACTIVE'` in `apiKeyModel.findByKeyHash`) for comprobify-web to enforce. `subscriptionService.requestSeatChange` has only two branches — unlike tier changes, there's no interval-change branch, since seats always follow the subscription's own `billing_interval`:
- **Increase** — immediate, prorated exactly like a same-interval tier upgrade (same `remainingFraction` formula), priced via `pricingService.getCurrentSeatPrice(subscription.billing_interval)` ("now" — the as-of principle). Creates a `payments` row (`purpose: 'SEAT_CHANGE'`, `target_extra_seats` = the new total, `seats_charged` = the delta) if the prorated amount is `> $0`, else applies immediately for free (same `$0`-proration escape hatch as a tier upgrade). `applyVerifiedPayment`'s `SEAT_CHANGE` case is **always** the immediate flavor — a decrease never opens a payment, so there is no deferred sub-case the way `TIER_CHANGE` has one — and deliberately does **not** call `tenantModel.updateTier`/`tenantQuotaService.setCap` (seats affect neither tier nor quota; Common Mistake #38 doesn't apply here).
- **Decrease** — free, scheduled at `current_period_end` via `subscriptionModel.scheduleSeatDecrease` (sets `pending_extra_seats`), exactly like a same-interval tier downgrade. `POST /v1/admin/jobs/subscriptions` calls `subscriptionService.applyScheduledSeatChanges()`, which applies every due decrease — **unlike** `applyScheduledTierChanges`, it never rolls the period forward (a seat decrease owes nothing and doesn't touch the renewal cycle).
- **Guards:** `409 NO_ACTIVE_SUBSCRIPTION`, `400 SEAT_CHANGE_NO_OP`, `409 CANCELLATION_ALREADY_PENDING` (a scheduled cancellation already blocks new seat requests), `409 SEAT_CHANGE_ALREADY_PENDING` (a scheduled decrease or an in-flight increase payment), and `409 TIER_CHANGE_ALREADY_PENDING` if a billing-interval change is pending or in flight — an interval switch has already priced next period's seats at the old count, so letting the count move underneath it would leave that payment wrong. `requestTierChange` and `scheduleCancellation` gained the mirror-image guard: an in-flight `SEAT_CHANGE` payment blocks either action too (a paid seat increase applied moments before a cancellation zeroes it, or before an interval-change payment reprices seats at a stale count, wastes the tenant's money or corrupts the next invoice).
- **Combined billing, not a parallel cycle:** once `extra_seats > 0`, the regular renewal bills the seat cost in the **same** payment as the plan — `createRenewalReminder` and `requestTierChange`'s billing-interval-change branch both add `effectiveSeatsAtPeriodEnd(subscription) × seatPrice` to their total and stamp `seats_charged`. `effectiveSeatsAtPeriodEnd` reads `pending_extra_seats ?? extra_seats`, not the raw column — a scheduled decrease lands at the exact `current_period_end` these payments are priced *for*, so pricing off the pre-decrease count would overcharge (Common Mistake #51). `payments.seats_charged` is the audit trail recovering the per-line split from what's otherwise one combined `amount`: a **delta** on `SEAT_CHANGE`, the **effective total** on `RENEWAL`/interval-changing `TIER_CHANGE`, `0` on `INITIAL`/same-interval `TIER_CHANGE`.
- **Termination zeroes seats:** `applyScheduledTierChanges`' FREE/cancellation branch and `expireSubscription` both reset `extra_seats` to `0` — a cancelled/expired subscription must not keep advertising a paid entitlement nobody is paying for.
- **Pricing (`seat_prices` table, not a pseudo-tier in `tier_prices`):** flat, non-tiered — one `PUBLISHED` row per `billing_interval`, same DRAFT→PUBLISHED/as-of-date shape as `tier_prices` but with no `tier` column, resolved via `pricingService.getCurrentSeatPrice`/`getSeatPriceAsOf`/etc. (mirrors the tier functions 1:1). Admin CRUD lives at its own `/v1/admin/seat-prices` (sibling of `/v1/admin/prices`, not a rename). The 30-day notice reuses the existing mandatory `PRICE_CHANGE_ANNOUNCED` notification type (see "Idempotency" below) rather than adding a 6th email-capable type. `refundPayment` restores `extra_seats` **only** for a `SEAT_CHANGE` payment (`snapshot.extraSeats`, added to `applied_from` by `snapshotState`) — restoring it unconditionally on every refund would wipe out an unrelated, legitimately-scheduled pending decrease when refunding e.g. a `RENEWAL`.
- Sandbox mirrors `requestSandboxTierChange`: no period to prorate against, a decrease applies immediately free, an increase is priced as the net difference against what's already paid for.

**Recurring renewals:** every `ACTIVE` subscription's `current_period_end` is a real recurring billing date, not just a one-time activation timestamp — `subscriptionService.processDueRenewals()` (called by the same `POST /v1/admin/jobs/subscriptions` job as the downgrade step above, **always after it** in the same tick — see ordering note below) handles the cycle:
- **Reminder + payment.** `subscriptionModel.findDueForRenewalReminder(7)` finds every `ACTIVE` subscription within 7 days of `current_period_end` with no `pending_tier` (a scheduled downgrade already rolls its own period forward for free, see above — it doesn't need a renewal payment too) and no renewal payment already open for this cycle. For each, `createRenewalReminder()` opens a `payments` row (`purpose: 'RENEWAL'`, priced via `pricingService.getPriceAsOf` plus any active extra seats' cost, see ADR-032 above), logs a `RENEWAL_DUE` tenant event, and calls `notificationService.createSubscriptionRenewalDue()` (`SUBSCRIPTION_RENEWAL_DUE` notification type — creates the row, fans out to webhooks, and dispatches the DB-backed email, ADR-024) — this is how a tenant actually finds out they need to renew, since nothing else would tell them.
- **Past-due warning (ADR-025).** `subscriptionModel.findDueForSuspensionWarning(5, 7)` finds every `ACTIVE` subscription partway through the grace window below (`SUSPENSION_WARNING_DAYS = 5`, must stay `< RENEWAL_GRACE_DAYS`) with no `pending_tier` and no `SUBSCRIPTION_PAST_DUE_WARNING` notification already sent this cycle (dedup via `notifications` directly, ADR-023's precedent — `created_at >= current_period_end` naturally resets every renewal). `notificationService.createSubscriptionPastDueWarning(subscription, suspendsAt)` fires — a distinct, more urgent notice from the renewal-due reminder, ahead of the tenant actually being marked `PAST_DUE`.
- **Completion.** The tenant uploads proof via the same `PATCH /v1/payments/:id/proof`, admin reviews and self-bills the same way, then `PATCH /v1/admin/subscriptions/:id/link-invoice` — `linkInvoice` records the invoice against the **payment's** `invoice_document_id`. The renewal itself was already applied when its payment was verified (`applyVerifiedPayment`'s RENEWAL path) — it extends `current_period_start`/`current_period_end` by one billing interval **anchored to the OLD `current_period_end`, never "now"** (`addBillingPeriod()`, shared with `applyScheduledTierChanges` and `applyVerifiedPayment`'s INITIAL path), so an early or late admin review can't drift the billing date — periods stay back-to-back with no gap or overlap. Logs `SUBSCRIPTION_RENEWED`.
- **Expiry.** `subscriptionModel.findExpiredPastGrace(7)` finds every still-`ACTIVE` subscription whose `current_period_end` passed more than 7 days ago with no renewal ever completing (a completed renewal always re-stamps `current_period_end` into the future, so a row this far past it genuinely never renewed). `expireSubscription()` downgrades the tenant to FREE, flips `subscriptions.status` to `EXPIRED` (already a valid value since migration 052), logs `SUBSCRIPTION_EXPIRED`, fires a matching notification + email, and (ADR-025) also flips `tenants.status = 'PAST_DUE'` + logs `STATUS_CHANGED` (`reason: 'unpaid_renewal'`) — idempotent, skipped if the tenant is already `SUSPENDED` or already `PAST_DUE` — a tenant should never be silently downgraded with zero communication or consequence. See "Suspension" above for the `PAST_DUE` recovery path.
- **Ordering matters:** `admin.controller.js`'s `runSubscriptionJobs` runs `applyScheduledSeatChanges()` → `applyScheduledTierChanges()` → `processDueRenewals()`, in that order, every tick. Seats before tiers: `applyScheduledTierChanges()` rolls `current_period_end` forward, and `applyScheduledSeatChanges()`'s due-query is keyed on `current_period_end <= NOW()` — running tiers first would make a due seat decrease invisible for a whole extra period (Common Mistake #50). Tiers before renewals: a downgrade that just got applied also just rolled its period into the future, so by the time the past-due-warning/expiry checks run, they correctly no longer look past-grace — reversing that pair would flag every subscription downgrading today as freshly warned/expired.
- This is a manual-pipeline-only concept — once a real payment gateway (see NEXT_STEPS.md's "Payment Gateway Integration" item, no vendor chosen yet) exists, it owns the recurring charge schedule natively and this cron-driven reminder/grace/expire cycle becomes gateway-specific automation territory, not a redesign.

**Payment review notifications:** `subscriptionService.reviewPayment()` applies the payment via `applyVerifiedPayment` on a `VERIFIED` decision (ADR-027 — straight to `ACTIVE`, no `PAYMENT_RECEIVED` stopover; see Common Mistakes #36). It then calls `notificationService.createPaymentReviewed()` once, covering every payment purpose (`INITIAL`, `TIER_CHANGE`, `RENEWAL`, `SEAT_CHANGE`) uniformly — only the wording adapts (a `SEAT_CHANGE` payment names the seat count, e.g. "your extra seats payment (2 seats)," instead of "for the GROWTH plan" — `payment.target_tier` is null on that purpose, so naming a plan would be misleading). That single call creates the `PAYMENT_VERIFIED`/`PAYMENT_REJECTED` notification row (INFO/WARNING severity) and internally durably enqueues both `WEBHOOK_FANOUT` and (since both types support the EMAIL channel) `NOTIFICATION_DISPATCH` — see "Notification and webhook system" above for the full dispatch flow, and "Notification email templates" for where the email content itself lives now. It includes the rejection reason when rejected — resolved from `payment.rejection_reason_code`, once via `notification-email-template.service.js`'s per-language `REJECTION_REASON_LABELS` map (for the email) and once via `notification.service.js`'s own hardcoded English `REJECTION_REASON_LABELS` (for the in-app message, never localized) — `metadata.rejectionReasonCode` on the notification also carries the raw code for consumers that want to do their own mapping (e.g. a webhook receiver localizing to the tenant's UI language). Both payment-display surfaces (`notification-email-template.service.js`'s value builder and `notification.service.js`'s `metadata`) show `payment.target_tier || subscription.tier`, `payment.target_billing_interval || subscription.billing_interval`, and `payment.total_amount` — never the subscription's own (stale, for a `TIER_CHANGE` payment) tier/interval, and never `payment.amount` (the pre-IVA base) — see Common Mistakes #28. Separately, `submitPaymentProof()` fires `emailService.sendPaymentProofSubmitted()` — an **operator**-facing email (not a `notifications` row; the operator isn't a tenant, there's no webhook/preference concept for them) telling whoever holds `ADMIN_NOTIFICATION_EMAIL` that a proof is waiting for review. That env var is optional — unset means the email is silently skipped (mirrors the `SENTRY_DSN` optional pattern), since it's an operational convenience, not something tenant-facing behavior depends on.

**Price history + 30-day change notice (ADR-023):** `priceMonthlyUsd`/`priceYearlyUsd` no longer live in `TIERS` (`src/constants/subscription-tiers.js`) — they're resolved from the `tier_prices` table (migration 076) via `src/services/pricing.service.js`. A price is created as a `DRAFT` row (`POST /v1/admin/prices`), optionally edited (`PATCH /v1/admin/prices/:id`), and only starts its notice clock on confirm (`POST /v1/admin/prices/:id/publish`) — which stamps `effective_at = now + noticeDays` (floor enforced by `config.priceChangeMinNoticeDays`, default 30, per `docs/agreements/terms-of-service.md`'s "at least 30 days" clause) and notifies every currently-`ACTIVE` tenant. "The current price for tier X as of date D" is always the newest `PUBLISHED` row whose `effective_at <= D` (`pricingService.getPriceAsOf`/`getCurrentPrice`) — no promotion job needed, exactly mirroring how `agreements`' "current version" is just "newest row." **The as-of-date principle:** every real billing call site in `subscription.service.js` (`createSubscription`, `requestTierChange`'s direction-check/proration/deferred-interval-change paths, `createRenewalReminder`) resolves price as of the date the resulting period actually starts — "now" for anything immediate (a new subscription, an upgrade proration, a sandbox change), `subscription.current_period_end` for anything deferred (a renewal, a deferred billing-interval change). This is what makes a renewal or deferred change due before a new price's `effective_at` automatically bill the old price — a data/query guarantee, decoupled from whether the notification email was ever delivered. Since ADR-032, `seat_prices` is a second table under this exact mechanism (own `getCurrentSeatPrice`/`getSeatPriceAsOf`/`createSeatPriceDraft`/`publishSeatPrice`/etc. in `pricing.service.js`, own `/v1/admin/seat-prices` admin CRUD) — flat/non-tiered (no `tier` column) rather than a pseudo-tier row inside `tier_prices`, since `tier` is hard-validated against the real `TIERS` object in three independent places (the DB CHECK, `assertValidTierAndInterval`, and the admin validators) that a fake tier value would need to either pass or bypass.

**`PRICE_CHANGE_ANNOUNCED` is "mandatory"** — `src/constants/notification-catalog.js` marks it `mandatory: true`, so a tenant cannot opt out of the 30-day price-change notice on any channel: `GET/PATCH /v1/notifications/preferences` reject it outright (never appears in the preference list, `PATCH` 400s if asked to set one). ADR-023 originally shipped this as a one-off special case (skipping a since-removed per-type preference gate); ADR-024 generalized "creation is unconditional" to every notification type, so `PRICE_CHANGE_ANNOUNCED` today is just one `mandatory: true` catalog entry among the 10, not a bespoke code path — see "Notification and webhook system" above.

**Idempotency: `notifications`, not a dedicated table.** `pricingService.notifyPendingPriceChangesForTenant(tenantId)` finds every `PUBLISHED` price still inside its notice window this tenant has no `PRICE_CHANGE_ANNOUNCED` notification for yet (`tierPriceModel.findUnnotifiedPendingForTenant` — `NOT EXISTS` against `notifications` filtered on `tenant_id`/`type`/`metadata->>'tierPriceId'`) and, for each, calls `notificationService.createPriceChangeAnnounced` — same synchronous-creation-then-`dispatchNotification` pattern every other type now uses (see "Notification and webhook system" above), no longer a special case. Since ADR-032 the same function also scans `seat_prices` the same way (`seatPriceModel.findUnnotifiedPendingForTenant`, keyed on `metadata->>'seatPriceId'` instead) and calls `notificationService.createSeatPriceChangeAnnounced` for each — same `PRICE_CHANGE_ANNOUNCED` type, distinguished purely by which metadata key is present (never both), so every existing call site of `notifyPendingPriceChangesForTenant` picked up seat-price notices with zero changes. The synchronous creation matters: it closes the gap a queued-effect approach would leave between "checked as pending" and "marked as handled," which the periodic reconciliation sweep (every 5 minutes, see below) would otherwise race and double-enqueue. `previousPriceUsd` is computed once here and carried in the notification's `metadata` (read later by `notification-email-template.service.js`'s value builder when the `NOTIFICATION_DISPATCH` effect actually renders the email) rather than recomputed at send time, so the email can't disagree with what the in-app notification already said if another price becomes effective in between. **Reactivation catch-up:** a tenant `SUSPENDED`, `PAST_DUE`, or still `PENDING_VERIFICATION` at publish time would otherwise never be told — the same idempotent function is called by every place a tenant's status transitions to `ACTIVE` (`registration.service.js`'s `verifyEmail`, `admin.service.js`'s `verifyTenant`/`updateTenantStatus`, `subscription.service.js`'s `applyVerifiedPayment` for the `PAST_DUE` → `ACTIVE` self-service recovery path, ADR-025). Not strictly required for any of these — the periodic reconciliation sweep below would catch a missed tenant within ~5 minutes regardless — but every reactivation point notifies immediately rather than leaning on the sweep, for consistency. **Periodic reconciliation:** `pricingService.reconcilePendingPriceChangeNotifications()` re-scans every `ACTIVE` tenant on the same cadence as `POST /v1/admin/jobs/notifications` (`notification-scheduler.service.js`'s `runAll()`, step 3) — a safety net for an `ACTIVE` tenant silently skipped during the publish-time bulk loop (e.g. a transient failure), since nothing else ever revisits a tenant who doesn't change status. `IVA_RATE` is deliberately **not** part of this mechanism — see its own entry below. `GET /v1/tiers` exposes `upcomingPriceMonthlyUsd`/`monthlyPriceEffectiveAt`/`upcomingPriceYearlyUsd`/`yearlyPriceEffectiveAt` (null when nothing pending) so a published-but-not-yet-effective change is visible to prospective tenants too.

**Yearly billing:** `priceYearlyUsd` = `priceMonthlyUsd × 10` (2 months free, the standard SaaS discount convention) for STARTER/GROWTH/BUSINESS — a convention enforced at price-creation time, not a computed constant, since both are independent `tier_prices` rows. `GET /v1/tiers` (public, no auth) exposes the full catalog — quota, both prices, overage rate, document types, limits — for a future pricing page to read from instead of hardcoding the same numbers a second time. `billing_interval` changes payment cadence/amount (`current_period_end` is +1 year instead of +1 month) exactly as before.

**Yearly quota pooling (ADR-029):** `documentQuota` in `subscription-tiers.js` is a per-month figure, but a YEARLY subscriber's `tenant_quotas` period itself pools the whole year up front — `document_quota = documentQuota × 12`, consumable unevenly across the year (e.g. 0 documents in January, 480 in December for a tier with `documentQuota: 40`), not reset every 30 days. This reverses the original design (a YEARLY payer used to get the same flat monthly cap as a MONTHLY payer, refreshed on the same 30-day clock regardless of having paid for a full year up front) — see ADR-029 for why. Mechanically: `tenant_quotas.billing_interval` (migration 094) is the period's own record of which mode it's in, kept in sync by every `tenantQuotaService.setCap(tenantId, tier, billingInterval)` call rather than re-derived from `subscriptions` at read time (a still-`ACTIVE` subscription mid-year could otherwise disagree with a `tenant_quotas` row seeded before the interval last changed). `capForTier(tier, billingInterval)`/`periodMonthsForTier(tier, billingInterval)` (`tenant-quota.service.js`) are the two functions that apply the × 12 multiplier for `billingInterval === 'YEARLY'`, with two guards: ENTERPRISE's `null` cap short-circuits before any multiplier is applied (still unlimited either way — see "Unlimited tiers" above), and FREE never pools annually even if a stale YEARLY interval is passed through (there is no live YEARLY+FREE subscription in practice — `createSubscription` rejects FREE outright — but a downgrade-to-FREE call site may still pass whatever `billingInterval` the just-abandoned subscription had). `setCap()` resizes `period_end` immediately (via the shared `addMonths()` helper, anchored to the period's own unmoved `period_start` — **never** raw SQL date arithmetic, which reintroduces the exact month-end overflow bug `addMonths()` exists to prevent, Common Mistake #26) rather than waiting for the next `resetDuePeriods` sweep, so a tenant who just went YEARLY gets the full pooled cap the moment their payment applies, not up to a month later. `document_count` is never touched by `setCap()` — already-consumed documents this cycle still count against the resized cap either direction. Overage billing (letting a tenant opt into exceeding quota and paying the difference, `overagePerDocumentUsd`) is still unbuilt — see NEXT_STEPS.md's "Overage Billing" item.

**Certificate parsing:** extracted to `src/services/certificate.service.js` — used by both `registration.service.js` and `admin.service.js`.

**XSD validation:** `src/services/xml-validator.service.js`'s `validate(xmlString, documentType)` shells out to the `xmllint` CLI (via `execFile`, promisified) against a per-document-type schema — `XSD_PATHS['01'] = assets/factura_V2.1.0.xsd`, `XSD_PATHS['04'] = assets/nota_credito_V1.1.0.xsd`. Must run before signing (signing is expensive; fail fast). `xmllint` must be installed on the server. Adding a new document type's builder means adding its own `XSD_PATHS` entry too, per `docs/guides/coding-guidelines.md`'s "Adding a new document type" checklist.

**Retry logic:** `fetchWithRetry` in `sri.service.js` — retries only on `fetch` throws (network), never on HTTP-level SRI responses.

**Async worker: pending_effects outbox (ADR-019 Phase 1 / ADR-022 Phase 2 / ADR-024 consolidation):** `POST /:key/send` and `GET /:key/authorize` never call SRI synchronously — both always queue and return `202`; there is no sync fallback. **Postgres is the only source of truth; RabbitMQ is purely a confirmed-dispatch signal, never the record.** Phase 1 (ADR-019) tracked dispatch directly on `documents` (`send_dispatch_attempted_at`/`authorize_dispatch_attempted_at`). Phase 2 (ADR-022) replaced that with one generic outbox table, `pending_effects` (migration 075), and moved every other async side effect that used to be an unawaited fire-and-forget promise (notifications, webhook fan-out, subscription hooks, transactional emails) onto the same mechanism. ADR-024 later consolidated 7 type-specific notification `*_NOTIFICATION`/`*_EMAIL` effect types into one channel-neutral `NOTIFICATION_DISPATCH` (migration 078) — **9 effect types today**, SRI send/authorize included. (Subscription activation/tier-change/renewal reconciliation deliberately does **not** use this mechanism — see the "Not one of the 8" note below the catalogue.)

A new `PENDING_SEND` status still sits between `SIGNED` and `RECEIVED`/`RETURNED` on `documents` (`documents.status` CHECK constraint and the DB-level `enforce_document_state_transition()` trigger — migration 027, updated by migration 074 alongside the JS state machine; the DB trigger hardcodes the same transition graph independently and does not derive it from JS) — this part is unchanged by Phase 2; only *how dispatch is tracked* moved off `documents` and onto `pending_effects`.

`pending_effects` columns: `tenant_id` (NOT NULL, FK — every effect type has exactly one owning tenant available at enqueue time; unlike `notifications`/`tenant_events`/`webhook_deliveries`, which added their `tenant_id` from day one, this table has it from the start too, added deliberately so admin tooling can filter "everything pending for tenant X" without parsing per-type JSONB shapes), `effect_type` (9 values, CHECK-constrained), `payload` (JSONB, ids only — handlers re-fetch fresh rows, never trust serialized data), `dedup_key` (nullable; only `SRI_AUTHORIZE` uses it), `notification_type` (nullable; only `NOTIFICATION_DISPATCH` populates it — a denormalized snapshot of `notifications.type`, migration 080, same "admin/debug filter without parsing JSONB" reasoning as `tenant_id`; purely informational, the `NOTIFICATION_DISPATCH` handler still re-fetches the real `notifications` row rather than trusting it), `status` (`PENDING → DISPATCHED → DONE`, or `→ FAILED` once `attempt_count` reaches `config.pendingEffects.maxAttempts`, default 5), `dispatch_attempted_at`, `attempt_count`, `last_error`. Never hard-deleted (rule #7) — `DONE`/`FAILED` rows are the audit trail. Not issuer-scoped, no RLS — same precedent as `notifications`/`tenant_events`/`webhook_deliveries`.

Every producer call site follows the same shape: `const effect = await pendingEffectService.enqueue(EffectTypes.X, tenantId, payload); pendingEffectService.dispatch(effect);` (`src/services/pending-effect.service.js`). `enqueue()` is a durable, awaited insert — the effect intent survives a crash even if `dispatch()` never runs. `dispatch()` attempts a broker-confirmed publish (`publishConfirmed`, amqplib confirm channel, 3s timeout) and is best-effort — a failed/timed-out publish never fails the caller's request, mirroring the original `queueSend` behavior; the row is simply left for reconciliation.

Three RabbitMQ queues, not one — `sri.send`, `sri.authorize` (unchanged names/topology from Phase 1), and `app.effects` (new, carries the other 12 types). `src/constants/effect-types.js`'s `routingKeyForEffectType()` maps `SRI_SEND`→`send`, `SRI_AUTHORIZE`→`authorize`, everything else→`effects`. This split matters: `channel.prefetch(n)` is per-*consumer* in RabbitMQ despite being set on the channel, so a burst of slow `WEBHOOK_FANOUT` deliveries (10s HTTP timeout each) can never delay `sri.send`/`sri.authorize` message delivery — merging everything into one queue would have put the highest-stakes part of the pipeline behind side-effect latency.

`workers/worker.js` (renamed from `workers/sri-worker.js` in Phase 2 — the role broadened past SRI-only) is the single background worker process (`npm run worker`, its own container in `deploy/docker-compose.yml` alongside the API on the same droplet) consuming all three queues on one shared confirm channel, three independent `channel.consume()` registrations. Every message is just `{ effectId }`; `pendingEffectService.process(effectId)` does the actual work identically regardless of which queue delivered it:
- `SELECT ... FOR UPDATE` claims the row — this is what makes RabbitMQ's at-least-once redelivery safe: a duplicate delivery blocks until the first attempt's transaction resolves, then sees the row already `DONE`/`FAILED` and no-ops.
- Looks up the handler via `src/effects/index.js`'s registry (mirrors the `src/builders/index.js` "registry keyed by a type string" idiom — `getHandler(effectType)` is the `getBuilder(documentTypeCode)` equivalent).
- Handler resolves normally → row marked `DONE`.
- Handler resolves with `{ requeue: true }` → row left exactly as-is (not `DONE`, `attempt_count` untouched). **Only `SRI_AUTHORIZE`'s handler ever does this** — SRI's authorization can take time, and "still processing" is neither success nor failure; it just needs checking again later, indefinitely, until SRI decides. `checkAuthorization()`'s `result.pending` branch returns this instead of the document.
- Handler throws a `400 AppError` (a state-machine violation — another delivery already advanced the document past this state, expected under at-least-once redelivery) → treated as benign, marked `DONE` anyway (same `isBenignStateError` reasoning Phase 1 already used).
- Handler throws anything else → `attempt_count++`, `last_error` recorded, `status` flips to `FAILED` once `attempt_count >= maxAttempts`, otherwise left as-is for reconciliation to retry; the error is rethrown so the worker `nack`s the message (`requeue: false` — RabbitMQ never retries a message itself, only Postgres-driven reconciliation does).

`SRI_SEND`/`SRI_AUTHORIZE` are one-shot like every other type, with one wrinkle: `sendToSri` (the `SRI_SEND` handler) durably enqueues an `SRI_AUTHORIZE` row the instant a document becomes `RECEIVED` — but does **not** dispatch it yet, guaranteeing every `RECEIVED` document eventually gets an authorize-check even if the client never calls `GET /:key/authorize`. `queueAuthorizationCheck` (the HTTP-facing side, called from `documents.controller.js`) finds-or-creates that same row via `dedup_key = 'sri-authorize:'+documentId` (the one effect type that needs dedup — a document's own state machine already prevents `SRI_SEND` duplicates, and the other 12 types are each created from a single call site per real-world event) and dispatches it immediately, skipping the delay a client's explicit request shouldn't wait through.

**Reconciliation** (`queue-reconciliation.service.js`'s `reconcilePendingEffects()`, `POST /v1/admin/jobs/queue-reconciliation`, same external-cron pattern as the other `/v1/admin/jobs/*` endpoints, runs every 5 minutes on staging's self-hosted droplet cron — see `docs/terraform-digitalocean-setup.md`): one `SELECT ... FOR UPDATE SKIP LOCKED` sweep against `pending_effects` — no more `public`/`sandbox` schema split, since `pending_effects` isn't schema-scoped (this replaces what used to be up to 4 query executions — 2 functions × 2 schemas — with 1). It **re-publishes a fresh message, never runs a handler itself** — keeping "do the work" a single responsibility of the worker so a fallback processor can't drift out of sync with it. Two timing regimes, both evaluated in the one query:

| What needs dispatch | Condition | Config |
|---|---|---|
| `SRI_AUTHORIZE` rows | first attempt: `created_at` older than the delay window; re-attempts: `dispatch_attempted_at` older than the stale window | `authorizeCheckDelayMinutes` / `authorizeStaleMinutes` |
| Every other effect type | `dispatch_attempted_at` NULL or older than the stale window | `effectStaleMinutes` |

**The 9 effect types** (`src/constants/effect-types.js`): `SRI_SEND`, `SRI_AUTHORIZE`, `INVOICE_AUTHORIZED_EMAIL` (enqueued from `document-transmission.service.js`'s `checkAuthorization` the moment a document becomes `AUTHORIZED` — the handler in `src/effects/index.js` also owns the `email_status`/`document_events` bookkeeping that used to be inline in `checkAuthorization` itself; emails the document's **buyer**, unrelated to the tenant notification system below), `TENANT_AGREEMENT_GENERATE`/`VERIFICATION_EMAIL_SEND` (from `registration.service.js`'s `register()`/`recover()`/`resendVerification()` — 3 call sites collapse onto 1 `VERIFICATION_EMAIL_SEND` handler), `WEBHOOK_FANOUT` (from `notification.service.js`'s `dispatchNotification`, enqueued unconditionally after every notification create/update — `webhookDeliveryService.fanOut()` itself gained a dedup guard against `webhookDeliveryModel.findByNotificationId()` so a redelivered `WEBHOOK_FANOUT` effect can't double-send to an endpoint that already got it), `PAYMENT_PROOF_SUBMITTED_EMAIL` (operator-facing, from `subscriptionService.submitPaymentProof`), and `NOTIFICATION_DISPATCH` — the one channel-neutral effect covering whatever async dispatch any tenant notification still needs (today: email, for the 5 types that support it). ADR-024 collapsed 7 old type-specific `*_NOTIFICATION`/`*_EMAIL` types (`DOCUMENT_AUTHORIZED_NOTIFICATION`, `PAYMENT_REVIEWED_NOTIFICATION`/`_EMAIL`, `SUBSCRIPTION_RENEWAL_DUE_NOTIFICATION`/`_EMAIL`, `SUBSCRIPTION_EXPIRED_NOTIFICATION`/`_EMAIL`, `PRICE_CHANGE_EMAIL`) into this single type — see "Notification and webhook system" above for the full dispatch flow. `NOTIFICATION_DISPATCH` is an `EffectTypes` value (drives `pending_effects.effect_type`) — distinct from and unrelated to `NotificationTypes` (drives `notifications.type`); one `NotificationTypes` event may cause a `NOTIFICATION_DISPATCH` effect to be enqueued, but the two enums are orthogonal.

**Not one of the 8 — subscription activation/tier-change/renewal reconciliation:** `SUBSCRIPTION_ACTIVATE_IF_LINKED`/`_APPLY_TIER_CHANGE_IF_LINKED`/`_APPLY_RENEWAL_IF_LINKED` were originally planned here, firing unconditionally on every document authorization system-wide and checking internally whether the document happened to be a subscription-funding invoice. Cut before shipping: a real deployment only ever links an already-`AUTHORIZED` invoice (`linkInvoice`'s own immediate-apply check handles that case synchronously, no queue involved), so firing 3 RabbitMQ messages per authorized document *for every tenant* to cover the rare reverse-ordering case wasn't worth it. ADR-027 then removed the reason they might ever have been needed: a document authorizing no longer changes any subscription at all, since `applyVerifiedPayment` does that at payment-verification time and `linkInvoice` is pure bookkeeping. `applyPendingInvoiceLinks()` (also since removed) — the periodic scan that briefly stood in for them — is gone with it. See ADR-022's addendum and ADR-027.

`RABBITMQ_URL` is required at startup (`src/config/validate.js`) — without it nothing can ever dispatch. Deployed as a single shared CloudAMQP instance rather than one per system, isolated by vhost/credentials, not by provisioning a separate broker per app.

**Error responses:** all `4xx`/`5xx` responses use RFC 7807 Problem Details (`Content-Type: application/problem+json`) with `type`, `title`, `status`, `code` (stable SCREAMING_SNAKE_CASE i18n key), `detail`, and `instance` (request URL). `AppError` derives `code`/`type`/`title` from the HTTP status automatically; an optional third constructor argument overrides `code` with a domain-specific value (e.g. `new AppError(msg, 400, ErrorCodes.CERTIFICATE_EXPIRED)`). All stable codes live in `src/constants/error-codes.js` — always import from there, never hard-code strings. `ValidationError` and `SriError` subclasses override with domain-specific values (`VALIDATION_FAILED`, `SRI_SUBMISSION_FAILED`). Field-level errors in `ValidationError.errors[]` each carry a `code` derived from the field path with array indices stripped. See ADR-011 and `docs/site/errors/index.md` for the full code catalogue.

**Audit trail:** every lifecycle transition → `document_events` row. Event types: `CREATED`, `SENT`, `STATUS_CHANGED`, `ERROR`, `REBUILT`, `EMAIL_SENT`, `EMAIL_FAILED`, `EMAIL_DELIVERED`, `EMAIL_TEMP_FAILED`, `EMAIL_COMPLAINED`, `EMAIL_SKIPPED` (email intentionally not sent, e.g. no `buyer_email` — distinct from `EMAIL_FAILED`, which means a send was attempted and failed).

**Tenant event log:** `tenant_events` mirrors the document audit trail for tenant-level lifecycle events — registration/verification, and the full subscription/payment/tier-change pipeline (see above). Written by `registration.service.js`, `mailgun-webhook.service.js`, `subscription.service.js`, `tenant.service.js`, `issuer.service.js`, and `admin.service.js`. Uses `db.query()` directly — tenants are not issuer-scoped. Adding a new event type requires updating the `chk_tenant_events_event_type` CHECK constraint in a migration. Read back via `GET /v1/tenants/events` (tenant-facing, `tenant.service.js`'s `getEvents()`) and `GET /v1/admin/tenants/:id/events` (admin-facing, `admin.service.js`'s `listTenantEvents()`) — both map rows through the shared `src/presenters/tenant-event.presenter.js` (`{ id, eventType, detail, createdAt }`) and both 404 if the tenant doesn't exist. `tenantEventModel.findByTenantId` existed since migration 036 but had no route reading it back until these two endpoints shipped. `PATCH /v1/admin/tenants/:id/status` (`admin.service.js`'s `updateTenantStatus()`) logs a `STATUS_CHANGED` event (`{ from, to, reason }`, migration 070) — previously silent, so suspending or reactivating a tenant left no audit trail at all, unlike `TIER_CHANGED` on the tier-override endpoint. `reason` (optional, max 200 chars) is what distinguishes *why* a tenant landed in `SUSPENDED` — the product deliberately has no separate "terminated"/"closed" status (see "Suspension" and "Account recovery" above: `SUSPENDED` already blocks writes while letting a tenant keep viewing their own historical documents/payments, which is the correct behavior for a voluntarily closed account too, not just a punitive one) — so `reason` is the only signal that tells a voluntary closure request (`docs/agreements/terms-of-service.md` §10) apart from a fraud/non-payment suspension in the audit trail. **Certificate changes** (migration 086) log `CERTIFICATE_UPLOADED` (`{ issuerId, certFingerprint, certExpiry }`) at every call site that parses and stores a genuinely new P12 — `registration.service.js`'s `register()`, `issuer.service.js`'s `createBranch()`, and `admin.service.js`'s `createIssuer()` — and `CERTIFICATE_RENEWED` (same shape) at the two in-place renewal call sites — `issuer.service.js`'s `renewCertificate()` and `admin.service.js`'s `renewIssuerCertificate()`. `createBranch()`/`createIssuer()` deliberately skip the event on their copy-from-source-issuer path (no `p12Buffer` supplied) — that certificate was already audited when it was first uploaded to the source issuer, so copying it to a new branch isn't a certificate *change*. A certificate is what makes a signed invoice legally valid, so "when was this cert replaced, with what fingerprint/expiry" needed to be in the audit trail rather than only inferable from `issuers.updated_at`.

**Builder registry:** `src/builders/index.js` maps document type codes to builder classes. Adding a new document type = new builder + one registry entry. `SUPPORTED_TYPES` (exported from `src/builders/index.js`) is derived from the registry keys and used by validators and `issuer.service.js` to enforce type eligibility. When adding a new builder, `SUPPORTED_TYPES` automatically includes it — no manual update needed.

**Issuer document types:** `issuer_document_types` table records which document types each issuer is allowed to use. Defaults to `['01']` at registration/admin create. Checked at document creation time — attempting to create a disallowed type returns 400. Managed via `GET/POST /v1/issuers/:id/document-types` and `DELETE /v1/issuers/:id/document-types/:code` — the latter refuses with `LAST_DOCUMENT_TYPE_CANNOT_BE_REMOVED` if the issuer has only one active document type left, mirroring `removeIssuer`'s `LAST_ISSUER_CANNOT_BE_REMOVED` guard (an issuer must always be able to issue at least one document type). At promotion, production sequentials are seeded for all active types (using `initialSequentials` values if provided, otherwise 1). Adding a new document type to the system requires a new builder, not a migration — and adding it to the appropriate tiers' `allowedDocumentTypes` in `src/constants/subscription-tiers.js`, or it ships unreachable on every plan.

**Document type tier gating:** `TIERS[tenant.subscriptionTier].allowedDocumentTypes` (`subscription-tiers.js`) restricts which document types a tenant can newly *enable* — checked in `issuerService.addDocumentType()` and in `createBranch()`'s `documentTypes` field (402 `DOCUMENT_TYPE_NOT_IN_TIER` if not allowed). This only gates adding a new type, never removing one or creating documents of an already-active type — a tenant who downgrades keeps using types already active on their issuers (grandfathered); they just can't activate further gated types until they upgrade again.

**Tier limit scope: API vs WEB (ADR-031):** not every key in a `TIERS[tier]` entry is enforced by this API. `src/constants/tier-limit-scope.js`'s `TIER_LIMIT_SCOPE` classifies each one as `API` (comprobify owns enforcement — `documentQuota`, `maxBranches`, `maxIssuePointsPerBranch`, `maxWebhookEndpoints`, `maxApiKeys`, rate limits, `allowedDocumentTypes`, `overagePerDocumentUsd`) or `WEB` (comprobify-web owns enforcement — currently only `maxUsers`, a dashboard team-seat cap this API has no table to check, since there is no user/session concept here at all — see "Tenant model" above). `GET /v1/tiers` returns this map as `limitScopes` alongside the per-tier values so the frontend can group its own limits from the API's without hardcoding which keys are which. Every key added to a `TIERS[tier]` entry needs exactly one `TIER_LIMIT_SCOPE` entry — nothing enforces this at runtime, so a missing entry silently ships a cap with no declared owner. `maxUsers` itself became billable in ADR-032 — see "Extra user seats" below.

**Credit note balance lookup:** `GET /v1/documents/:accessKey/credit-notes` returns the sum of all `AUTHORIZED` credit notes (`document_type = '04'`) already issued against a given document, plus a `remaining` balance, so the caller can enforce "this credit note can't exceed the original's remaining balance." There is no foreign key linking a credit note to the document it credits — `document-creation.service.js` only stores the raw request body in `request_payload` — so the lookup reconstructs the original's own `NNN-NNN-NNNNNNNNN` number from `issuer.branch_code` + `issuer.issue_point_code` + the zero-padded `sequential`, then matches credit notes whose `request_payload->'originalDocument'->>'number'` and `->>'documentType'` equal it (see `documentModel.findCreditNotesByOriginalDocument`). Only `AUTHORIZED` credit notes count toward consumed balance — `SIGNED`/`RECEIVED` (still pending) and `RETURNED`/`NOT_AUTHORIZED` (rejected) are excluded. Deliberately does not hardcode the original document's type as `'01'` — SRI permits other document types to be credited too. The `request_payload` JSONB path query has no supporting index; fine at current volume, but would need one if `documents` grows large. Known race: two credit notes created back-to-back before the first authorizes won't see each other in this sum — accepted, not solved by locking.

**Voiding a document:** SRI has no SOAP service to cancel an already-`AUTHORIZED` document — that only happens on SRI's own portal, outside this API entirely. `POST /:accessKey/void` (`document-void.service.js`, scope `documents:void`) is a manual, tenant-attested action: it requires `confirmedSriVoid: true` in the body (`400 DOCUMENT_VOID_CONFIRMATION_REQUIRED` otherwise) — an explicit attestation that the tenant already voided the document in SRI's portal, since this API has no way to verify that itself — plus a free-text `reason` (max 500 chars, audit-only; free text is fine here since the tenant is both the author and the only reader of their own reason, unlike an admin-typed suspension/rejection reason a *different* party reads). `VOIDED` is a second terminal state reachable only from `AUTHORIZED` (`document-state-machine.js` and the `enforce_document_state_transition()` DB trigger both updated by migration 096, per Common Mistake #39) — a `400 DOCUMENT_NOT_AUTHORIZED` covers both "not authorized yet" and "already voided" with one check (400, not 409 — matches the existing `ride.service.js`/`document-email.service.js` precedent for this code). Logs a `VOIDED` `document_events` row with `{ reason }`. Deliberately **not** reflected in `tenant_quotas.document_count` or `document-query.service.js`'s `getStats()` `issued`/`authorized_total` figures — a voided document already consumed its quota slot and still counts as issued; voiding corrects SRI's books, it doesn't undo the fact that a document was created. RIDE/XML/email are untouched — they still serve the frozen record of what SRI actually authorized, same reasoning as "RIDE PDF generation" above.

**Idempotency key:** `POST /v1/documents` accepts an optional `Idempotency-Key` header. The key and a SHA-256 hash of the request body are stored in `documents.idempotency_key` / `documents.payload_hash`. A duplicate key with the same payload returns the existing document (200). A duplicate key with a different payload throws `ConflictError` (409). Concurrent races are handled by catching `23505` in the transaction rollback path. See `src/middleware/idempotency.js` and ADR-006.

**Email delivery:** when a document becomes `AUTHORIZED`, `emailService.sendInvoiceAuthorized()` is called fire-and-forget. It generates the RIDE PDF and XML on the fly and sends both as attachments via Mailgun. The Mailgun message ID (angle brackets stripped) is stored in `documents.email_message_id`. Per-document status tracked in `documents.email_status` (`PENDING` → `SENT` / `FAILED` / `SKIPPED`). Failed sends retried via `POST /email-retry` (batch) or `POST /:key/email-retry` (single, add `?force=true` to resend an already-sent email). Provider swappable via `EMAIL_PROVIDER` env var + new file in `src/services/email/providers/`. **Sender display name:** invoice/document emails use `"${issuer.business_name} via Comprobify <EMAIL_FROM_DOCUMENTS>"` — the issuer's own business name appears as the sender because the email is sent on behalf of the business that issued the invoice. All other transactional emails (verification, payment reviewed, renewal, expiry) use `"Comprobify <EMAIL_FROM>"` — the display name is hardcoded to "Comprobify" since these are platform-level notifications, not tenant-issued documents. `EMAIL_FROM_DOCUMENTS` is an optional, separate sender address for invoice/document emails only (e.g. `facturas@` vs `notificaciones@`) — it falls back to `EMAIL_FROM` when unset (`config.email.fromDocuments`), so a deployment that only sets `EMAIL_FROM` behaves exactly as before. **Staging banner:** when `config.appEnv === 'staging'`, `email.service.js`'s `applyStagingBanner()` prepends a bold, localized "TEST ENVIRONMENT" / "ENTORNO DE PRUEBAS" notice to every outgoing email's `text` and `html` body, uniformly across all 6 `send*` functions — applied centrally in the service rather than in each template, since template HTML structure isn't consistent (some are full `<html><body>` documents, some are bare fragments; the banner is inserted right after `<body>` when present, otherwise prepended). This mirrors the `ambiente` distinction CLAUDE.md documents for SRI routing, applied to outgoing email. **Do-not-reply notice:** every template's `disclaimer` string in `src/locales/es.js`/`en.js` includes "no responder / do not reply" wording — these are one-way transactional notifications.

**Mailgun webhook:** `POST /v1/mailgun/webhook` receives Mailgun delivery events and updates `email_status`: `delivered` → `DELIVERED`, `failed`+`permanent` → `FAILED`, `failed`+`temporary` → status unchanged + `EMAIL_TEMP_FAILED` event (Mailgun retries), `complained` → `COMPLAINED`. All requests verified with HMAC-SHA256 via `verify-mailgun-webhook.js` middleware (`MAILGUN_WEBHOOK_SIGNING_KEY` config key). Lookup is by `email_message_id` — `findByEmailMessageId` searches **both** `public.documents` and `sandbox.documents` via `UNION ALL` and returns a `sandbox` boolean on the row. That flag is passed to `updateEmailStatus` and `documentEventModel.create` so the update and audit event land in the correct schema. See ADR-010.

**Rate limiting:** per-API-key request rate limits prevent abuse and quota exhaustion. Applied via `src/middleware/rate-limit.js` using `express-rate-limit`. Keyed by `req.keyHash` (SHA-256 token hash). Returns RFC 7807 `429 TOO_MANY_REQUESTS` response. `writeLimiter`/`readLimiter`'s window is configurable via `RATE_LIMIT_WINDOW_MS` (default: 60000ms) — shared by both. Their actual request-count ceiling is **not** an env var; it's read per-request from `TIERS[req.tenant.subscriptionTier].writeRateLimit`/`.readRateLimit` (`src/constants/subscription-tiers.js`), falling back to `TIERS.FREE`'s values (10 write / 60 read per minute) for an unrecognized tier — see "Tier-aware rate limiting" below for the Redis-backed store this is layered on. See `docs/site/errors/too-many-requests.md` for client retry guidance.

**Structured request logging:** `src/services/logger.service.js` is a single shared `winston` instance — a `Console` transport always runs, plus a Betterstack transport (`@logtail/winston`'s `LogtailTransport`) added only when `BETTERSTACK_SOURCE_TOKEN` is set, same optional/no-op-when-unset treatment as `SENTRY_DSN`/`REDIS_URL`. `BETTERSTACK_INGESTING_HOST` is a second, also-optional var passed through as the `Logtail` client's `endpoint` override — Betterstack assigns each source its own regional ingesting host (shown on the source's setup page), and without this override every sync attempt 401s against `@logtail/node`'s hardcoded shared-default host if your source doesn't use it. The Console transport gets its own `winston.format.printf` format — `LEVEL: {...same JSON...}` — so a terminal / `docker compose logs` stream is scannable at a glance; the shipped (Logtail) transport stays on the logger-level `winston.format.json()` default, since Betterstack parses/indexes fields from real JSON, not a prefixed string. `defaultMeta: { hostname: os.hostname() }` merges a `hostname` field into every entry regardless of which consumer logs — the only way to tell apart log lines from different machines (local dev vs. the staging droplet, or staging vs. production once that exists) when they all ship to the same Betterstack source. Needs no config: locally it's your real machine name; on the droplet it's `deploy/docker-compose.yml`'s explicit `hostname: comprobify-api-${APP_ENV}` (interpolated from the deployed `.env` Compose auto-loads from its own directory) rather than Docker's default opaque per-container id. Two consumers:
- **Per-HTTP-request** — `src/middleware/request-id.js` (mounted first, generates `req.requestId` via `crypto.randomUUID()`, echoes it as the `X-Request-Id` response header, and tags it onto Sentry's current request-isolated scope via `Sentry.setTag('requestId', ...)` — this is what ties a captured Sentry exception back to its exact structured log line, since the two systems otherwise share no common identifier; safe to call unconditionally even with `SENTRY_DSN` unset, same no-op-when-unconfigured behavior as every other Sentry call in this codebase) then `src/middleware/request-logger.js` (mounted second, both ahead of `helmet`/`cors`/routes so every request gets a line regardless of whether it ever authenticates) — an `express-winston` `logger()` middleware wired to the shared instance. **Security-critical:** express-winston's default `requestWhitelist` includes `headers` and `originalUrl`/`query` — logging those as-is would ship the raw `Authorization: Bearer <token>` header and query-string secrets (e.g. `GET /v1/verify-email/check?token=...`) straight to a third-party SaaS. `request-logger.js` never relies on those defaults: `requestWhitelist`/`responseWhitelist` are emptied out, `headerBlacklist: ['authorization', 'cookie']` is kept as defense in depth, and every logged field is built explicitly by `buildLogMeta(req, res)` (exported separately from the configured middleware, alongside `buildLogMessage`, purely so they're directly unit-testable without exercising express-winston's internals — mirrors `rate-limit.js` exporting `buildStore`/`keyGenerator` for the same reason). Fields: `timestamp`, `method`, `path` (`req.path`, **never** `req.originalUrl`/`req.url` — that's what strips the query string), `statusCode`, `durationMs` (`res.responseTime`, set by express-winston itself before `dynamicMeta` runs), `ip`, `requestId`, and `keyHash`/`apiKeyId`/`tenantId`/`issuerId` (each `null` until `authenticate`/`resolveIssuer` populate them — since `dynamicMeta` runs when the response actually finishes, not when the middleware is invoked, mounting ahead of `authenticate` doesn't prevent these from being correctly populated when they exist). `statusLevels: true` maps the winston `level` to the response: `>=500` → `error`, `>=400` → `warn`, else `info` — without it every request logs at a fixed `info` regardless of outcome, making `level:error`/`level:warn` useless as a Betterstack filter.
- **Per-async-effect** — `pending-effect.service.js`'s `process()` (the single function every one of the 9 effect types funnels through, including `SRI_SEND`/`SRI_AUTHORIZE`) calls the shared logger directly (no express-winston — no `req`/`res` in a worker process) at each of its existing exit points, tagged with an `outcome` (`skipped`/`requeue`/`done`/`done_benign`/`failed_retry`/`failed_final`/`claim_error`), `durationMs`, and — when present in `effect.payload` (itself "ids only" by the outbox's own design) — `accessKey`/`documentId` as the correlation key back to the HTTP request that originally queued the effect (`POST /:key/send`/`GET /:key/authorize` return `202` immediately, so this is the only way to tie the async outcome back to a request).

`src/services/attempt-tracker.service.js`'s threshold-crossing line also goes through this same shared logger (`logger.warn(...)`, not `console.warn`) — same local-print-plus-optional-ship behavior, so a crossing becomes queryable/aggregatable here in addition to the immediate `Sentry.captureMessage` alert.

**Sandbox environment + SRI routing:** `APP_ENV` (`staging` | `production`) combined with `tenants.sandbox` (boolean, default `true`) controls which SRI SOAP endpoint is used and what `ambiente` digit is embedded in the access key and XML. `tenants.sandbox` is the **single source of truth** for a tenant's intended SRI environment — `true` means SRI test, `false` means eligible for SRI production (subject to the staging safety rail below). `issuers` no longer has an `environment` column (dropped in migration 049) — `issuer.sandbox` in all service code is a virtual field set by `resolveIssuer` middleware (`req.issuer.sandbox = req.tenant.sandbox`).

| `APP_ENV`    | `tenant.sandbox = true` | `tenant.sandbox = false` |
|---|---|---|
| `staging`    | SRI test, `ambiente = 1` | SRI test, `ambiente = 1` |
| `production` | SRI test, `ambiente = 1` | SRI production, `ambiente = 2` |

`document-creation.service.js` and `document-rebuild.service.js` compute `ambiente = (config.appEnv !== 'production' || issuer.sandbox) ? '1' : '2'` (where `issuer.sandbox` reflects `tenant.sandbox` via the virtual field) and pass an `effectiveIssuer` (with `environment` set to the computed value) to both the builder and `accessKeyService.generate()`. `sri.service.js` `getSriUrls(issuer)` applies the same logic. All tenants default to `sandbox = true` — safe mode until explicitly promoted.

**`SRI_MOCK_MODE` — skipping SRI entirely, not just routing to its test endpoint:** the table above still always contacts a real SRI SOAP endpoint (test or production) — `SRI_MOCK_MODE=true` is an orthogonal, deployment-wide override that makes `sri.service.js` never call SRI at all, for every tenant on that deployment. Useful for generating demo tenants/documents (e.g. fake businesses for a UI walkthrough) without depending on SRI's test environment being reachable or the fake data passing SRI's own validation. `sri.service.js`'s `isMockModeActive()` gates both exported functions (`sendReceipt`/`checkAuthorization`) and re-derives `config.appEnv !== 'production' && config.sri.mockMode` at every call — never cached — so it is structurally impossible to activate on a real production deployment even if the env var were left set there by mistake, the same discipline `getSriUrls()`'s ambiente derivation already uses. When active, `sendReceipt` fakes an immediate `RECIBIDA` and `checkAuthorization` fakes an immediate `AUTORIZADO` (using the access key as the authorization number) — everything downstream (the async queue, `document_events`, `sri_responses`, RIDE/XML generation, notifications) is unmodified, since all of it only ever consumes the plain object these two functions return. `authorizationXml` is left `null` in the fake response — `ride.service.js` already falls back to `document.signed_xml` when it's absent, so there's nothing to fabricate. The actual SOAP call happens inside `workers/worker.js` (via the `SRI_SEND`/`SRI_AUTHORIZE` effect handlers), not the API process — since both processes load the same `.env` file (locally, and via `deploy/docker-compose.yml`'s shared `env_file: .env`), setting it once covers both, but it's worth remembering the worker is the process that actually needs it in its environment.

**Sandbox PostgreSQL schema:** sandbox and production documents live in separate schemas (`sandbox` vs `public`) so sequential sequences are fully independent and test data can be truncated safely. The `sandbox` schema contains `documents`, `document_line_items`, `document_events`, `sequential_numbers`, and `sri_responses` with the same constraints, triggers, and RLS as `public`. **Every future migration that alters a tenant-scoped table must be applied to both schemas.**

**`updated_at` maintenance:** there is no ORM — `src/models/` is raw parameterised `pg` SQL — so a `BEFORE UPDATE` trigger (`set_updated_at()`, migration 051) bumps `updated_at = NOW()` on every row update for every table that has the column (`issuers`, `public.documents`, `public.sequential_numbers`, `tenants`, `notification_preferences`, `webhook_endpoints`, `webhook_deliveries`, `sandbox.documents`, `sandbox.sequential_numbers`). This is a DB-level backstop, not a substitute for application code — UPDATE statements may still set `updated_at = NOW()` explicitly (harmless; the trigger overwrites it with the same value) but no longer **must**. A new migration adding an `updated_at` column to a table must also add a matching `trg_<table>_updated_at` trigger in that same migration, or updates to that table will silently never bump it.

**Row-Level Security (RLS):** all issuer-scoped tables (`documents`, `document_line_items`, `document_events`, `sequential_numbers`) have RLS enabled via migration 031. The policy restricts every query to the current issuer by reading `app.current_issuer_id` — a transaction-local PostgreSQL setting. RLS was dropped from `api_keys` in migration 042 because authentication happens before any context can be set; `api_keys` queries filter by `tenant_id` explicitly at the application layer (reintroducing tenant-scoped RLS is noted in `NEXT_STEPS.md`). Two helpers in `src/config/database.js` manage this:
- `db.setIssuerContext(client, issuerId, sandbox)` — call after `BEGIN` on an existing transaction client; sets both `app.current_issuer_id` (for RLS) and `search_path` (`sandbox, public` or `public`), both rolled back automatically on abort.
- `db.queryAsIssuer(issuerId, sql, params, sandbox)` — wraps a single query in a mini BEGIN / set_config / SET LOCAL search_path / query / COMMIT for non-transactional reads.
All authenticated service code paths must use one of these two helpers. Only the Mailgun webhook, admin API, and health check are exempt — they authenticate by other means and operate without an issuer context (the policy's null bypass allows it). The application DB user must **not** be a PostgreSQL superuser; superusers always bypass RLS regardless of policies.

**Notification and webhook system (ADR-015, ADR-024):** tenant-level alerts delivered via webhooks (primary) and polling (fallback). `notifications` row creation is **unconditional for every type** — no preference gate at creation, so the table is a reliable "did X happen" ledger regardless of what a tenant has muted. Two creation paths:
- *Event-driven* — `document-transmission.service.js`'s `checkAuthorization` calls `notificationService.createDocumentAuthorized(document, issuer)` **synchronously** (not a queued effect — the in-app row is created inline) when SRI authorises a document. Multiple authorisations within a 60-second window are aggregated into one notification row (same `id`, incrementing `count`). `createPaymentReviewed(payment, subscription, decision)` (from `subscriptionService.reviewPayment()`) and `createSubscriptionRenewalDue`/`createSubscriptionPastDueWarning`/`createSubscriptionExpired` (from `subscriptionService.processDueRenewals()`) and `createPriceChangeAnnounced(tenant, tierPrice, previousPriceUsd)` (from `pricingService.notifyPendingPriceChangesForTenant`) all follow the same synchronous-creation pattern now — see the "Recurring renewals" / "Payment review notifications" / "Price history + 30-day change notice" entries above.
- *Scheduled* — `notificationService.runCertChecksForTenant(tenantId)` (no `prefs` parameter — bookkeeping is unconditional) checks certificate expiry for all tenant issuers and upserts `CERT_EXPIRING`/`CERT_EXPIRED` alerts. Called by `notification-scheduler.service.runAll()`, which is triggered by `POST /v1/admin/jobs/notifications` (called by external cron). Consumers do NOT call any sync endpoint.

Every `createX()` funnels through the shared `dispatchNotification(notification)` (`notification.service.js`, not exported — internal only), which (a) always durably enqueues a `WEBHOOK_FANOUT` effect (fans out to all active, subscribed webhook endpoints — failed deliveries retried by the admin job), and (b) if the type's `src/constants/notification-catalog.js` entry has `supportsEmail: true`, stamps `notifications.email_status = 'PENDING'` and enqueues one `NOTIFICATION_DISPATCH` effect (see "Async worker: pending_effects outbox" — this is the one remaining queued effect for notifications; 7 old type-specific `*_NOTIFICATION`/`*_EMAIL` effect types were consolidated into it, ADR-024). That effect's handler (`src/effects/index.js`) checks the tenant's `EMAIL` channel preference (`notificationPreferenceModel.isEnabled`, skips with `email_status = 'SKIPPED'` if disabled), resolves the tenant, renders via `notificationEmailTemplateService.render(type, language, notification)` (DB-backed templates — see "Notification email templates" below), sends via `emailService.sendNotificationEmail(tenant, rendered)`, and stamps `email_status` `SENT`/`FAILED`.

Consumers can fall back to `GET /v1/notifications?sinceId=<id>` for catch-up polling — this is where `IN_APP` channel preference actually takes effect: `notificationModel.findActiveByTenantId` filters out any type the tenant has disabled on that channel (visibility, not existence — the row still exists for webhook/audit purposes).

**Per-channel preferences (ADR-024):** `notification_preferences` has a `channel` column (`'IN_APP'` or `'EMAIL'`), PK `(tenant_id, type, channel)`. `GET`/`PATCH /v1/notifications/preferences` operate on `[{type, channel, enabled}]` (breaking change from the old flat `[{type, enabled}]` shape). `src/constants/notification-catalog.js` (`NOTIFICATION_CATALOG`, `isMandatory()`, `supportsChannel()`) is the single source of truth for which channels each `NotificationTypes` value supports and whether it's `mandatory` — a mandatory type (currently only `PRICE_CHANGE_ANNOUNCED`, the 30-day legal price-change notice) can never have a preference row and never appears in the preferences list on either side; `notificationService.getPreferences`/`updatePreferences` derive the full subscribable `(type, channel)` list from this catalog rather than a hardcoded array.

`notifications`, `notification_preferences`, `webhook_endpoints`, and `webhook_deliveries` tables use `db.query()` directly (not issuer-scoped; no RLS). Optional `X-Issuer-Id` filter on `GET /v1/notifications`: parsed by `parseOptionalIssuerId()` in the controller. When supplied, the query adds `AND (issuer_id = $2 OR issuer_id IS NULL)`. Adding a new `NotificationTypes` value requires updating the CHECK constraints in both `044_notifications.sql` (or a new migration) and `045_notification_preferences.sql`, plus entries in `NotificationTypes`/`NotificationSeverity` constants **and** a `notification-catalog.js` entry (`supportsInApp`/`supportsEmail`/`mandatory`) — a type with no catalog entry has undefined dispatch behavior.

**Notification email templates (ADR-024):** the 5 email-capable `NotificationTypes` (`PAYMENT_VERIFIED`, `PAYMENT_REJECTED`, `SUBSCRIPTION_RENEWAL_DUE`, `SUBSCRIPTION_EXPIRED`, `PRICE_CHANGE_ANNOUNCED`) render from `notification_email_templates` (migration 079) — versioned, immutable rows keyed by `(notification_type, language, version)`, `is_current` flag, same "newest current row wins" pattern as `agreements` (see "Legal documents and tenant acceptance" above). `src/services/notification-email-template.service.js`'s `publish(type, language, version, rawContent?)` reads content from `docs/email-templates/{type}.{lang}.txt` (three sections: `SUBJECT:`, `---HTML---`, `---TEXT---`, parsed by `parseTemplateFile()`) or an optional `rawContent` override — same DB-bypasses-filesystem escape hatch `agreements.service.js`'s `publish()` has, same reasoning (CLAUDE.md Common Mistake #34). Admin routes: `POST`/`GET /v1/admin/notification-email-templates`, `GET .../versions/:id`, `GET .../:type/:language/versions`, `PATCH .../:id/activate`. `render(type, language, notification)` resolves the current template (falling back to `DEFAULT_LANGUAGE`/`'es'` if the tenant's language has no published template — mirrors `src/locales`' own fallback), builds a values object from `notification.metadata` plus a small set of derived values (purpose/rejection-reason code→label lookups, formatted dates/amounts, and — for `SUBSCRIPTION_RENEWAL_DUE` only — `config.bankTransfer`, injected since it's static operator config, not per-notification data) and substitutes via `src/utils/template-placeholders.js` (`substitute()` for subject/text, `substituteHtml()` which HTML-escapes each interpolated value — extracted from `agreement.service.js`, now shared by both services). A template must be published for a type/language (or `'es'`) before that type can ever email successfully — `render()` throws `NOTIFICATION_TEMPLATE_NOT_FOUND` otherwise, which the `NOTIFICATION_DISPATCH` handler treats as a retryable failure, not a silent drop.

**Error monitoring (Sentry):** unexpected `5xx` failures are reported to Sentry via `@sentry/node`. `instrument.js` (project root) calls `Sentry.init({ dsn, environment, sendDefaultPii: false })` and is required at the very top of `app.js` — before any other module — so the SDK can auto-instrument `http`, `express`, and `pg`. `Sentry.setupExpressErrorHandler(app)` is mounted in `server.js` immediately before the central `errorHandler`, so it only reports errors with `statusCode >= 500` (or none) and then forwards unchanged; expected `AppError` 4xx responses (validation, not found, quota, etc.) are never sent. `environment` is always `staging` or `production` (mirrors `config.appEnv`), filterable in the Sentry UI. `SENTRY_DSN` is optional — when unset (e.g. local development), the client is a no-op and nothing is transmitted.

`workers/worker.js` also requires `instrument.js`, but Sentry's automatic uncaught-exception capture never fires there — every worker failure path is already caught by the worker's own code (per-message errors in `handleMessage`, consumer-registration failures, startup failures), so nothing is ever technically "uncaught." Two spots call `Sentry.captureException(err)` explicitly instead: the `registerConsumers(...).catch()` inside `start()` (worker is connected but not actually consuming — worse than fully down, since it looks alive) and the top-level `start().catch()` (the worker never came up at all). The latter also `await`s `Sentry.flush(2000)` before `process.exit(1)` — `captureException` only queues the event, it doesn't send it, so exiting immediately after would race the network request and could kill the process before Sentry ever receives it. Per-message failures inside `handleMessage` are deliberately left console-only, not sent to Sentry — they're expected/routine (network hiccups, a slow webhook endpoint, etc., already covered by `queue-reconciliation.service.js`'s re-publish), and reporting every one would just be noise for something the design already handles.

**Config validation:** critical environment variables are validated at startup in `src/config/validate.js` and called from `app.js` before `Server` construction. Always-required: `APP_ENV` (`staging` | `production`), `ENCRYPTION_KEY` (64-char hex format), `ADMIN_SECRET`, `INTERNAL_SERVICE_SECRET` (without it, `requireInternalService` rejects every call to `POST /v1/register`/`/recover`/`/resend-verification`/`/verify-email` — account creation is completely unreachable, ADR-035), `APP_BASE_URL`, `BANK_TRANSFER_BANK_NAME`/`ACCOUNT_TYPE`/`ACCOUNT_NUMBER`/`ACCOUNT_HOLDER`/`IDENTIFICATION` (without these, `POST /v1/subscriptions` hands a tenant an empty bank-transfer block with no way to pay), `ADMIN_NOTIFICATION_EMAIL` (without it, a payment proof submission raises zero notification to anyone), `RABBITMQ_URL` (without it the async send/authorize pipeline has no way to ever dispatch a queued document — see "Async worker: pending_effects outbox" above). Email-required when `EMAIL_PROVIDER` is set to anything other than `'none'`: `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_WEBHOOK_SIGNING_KEY`, `EMAIL_FROM`. If any are missing or malformed, the process throws immediately with a clear error message before accepting any HTTP requests. This prevents silent failures like unsigned webhooks, unencrypted P12 storage, or a subscription pipeline nobody's watching. `IVA_RATE` (default `0.15`, Ecuador's current rate — see `src/constants/subscription-tiers.js`'s comment) is separately configurable but not validated as required, since it has a safe default and Ecuador has changed this rate more than once historically — a rate change should be a config update + restart, never a code change. Deliberately **not** part of the `tier_prices` history/30-day-notice mechanism (see "Price history + 30-day change notice" above) — it's a government-mandated tax rate, not a Comprobify pricing decision, and every payment already snapshots the rate in effect at creation (`payments.iva_rate`) for audit purposes.

**RIDE PDF generation:** `ride.service.js`'s `generate()` builds the RIDE **from the immutable authorized document, never from mutable joins.** It parses `document.authorization_xml || document.signed_xml` — the exact same source `document-query.service.js`'s `getXml()` serves via `GET /:key/xml` — using `fast-xml-parser`, and derives every content field (issuer name/address/RUC, buyer, items, taxes, payments, `infoAdicional`/Campos Adicionales, the credit-note original-document reference) from the parsed XML. It does **not** read `document.request_payload`, does **not** re-join the live `issuers` row for anything but `logo` (presentation-only, not part of the legal document), and does **not** recompute `environment` from `config.appEnv`/`issuer.sandbox` — it trusts whatever `<ambiente>` the authorized XML actually declares. This is deliberate: a RIDE is a printed representation of a specific authorized document, and a document already `AUTHORIZED` can never transition again (`document-state-machine.js`), so its printed form must be equally frozen — sourcing from live data let the RIDE silently drift from what SRI actually authorized whenever an issuer was edited or a builder bug was fixed after the fact (a real shipped bug: the `RUC Proveedor` Campos Adicionales entry was reconstructed from live `config.operator.ruc` instead of the XML's own `campoAdicional`, so an old document's RIDE would start showing a *different* value than what was actually authorized, the moment the format was fixed for new documents). Throws `RIDE_XML_UNAVAILABLE` (500) if an `AUTHORIZED` document somehow has neither XML stored. `mapInvoiceXml`/`mapCreditNoteXml` (private to `ride.service.js`) mirror `invoice.builder.js`/`credit-note.builder.js`'s own element names in reverse — adding a new document type's builder (see `docs/guides/coding-guidelines.md`'s "Adding a new document type") needs a matching `mapXXXXml` here too, or its RIDE will throw trying to read `parsed.factura`/`parsed.notaCredito` for a root element that doesn't exist. `helpers/ride-builder.js` itself is unchanged by any of this — it only ever consumed a plain `rideData` object and has no idea where the values came from.

**Per-item additional details (`detallesAdicionales`/`detAdicional`):** SRI's schema allows up to 3 free-form `nombre`/`valor` pairs (≤300 chars each) per line item — a *per-item* sibling to the document-level Campos Adicionales box, for something like a serial number, color, or size attached to one specific line. Accepted as `items[].additionalDetails[]` on `POST /v1/documents` (validated in both `invoice.validator.js` and `credit-note.validator.js`, max 3 entries). `invoice.builder.js`/`credit-note.builder.js` write it into `<detalle>` as `<detallesAdicionales><detAdicional nombre="..." valor="..."/></detallesAdicionales>` — **element order matters for `xmllint`**: it must sit between `precioTotalSinImpuesto` and `impuestos`, exactly where both XSDs place it. `document-line-item.model.js`'s `bulkCreate()` also persists it to `document_line_items.additional_details` (migration 087, both schemas) — but that column is an **audit/query record only**; it is never read back to build the RIDE, which parses the authorized XML's own `<detallesAdicionales>` instead (see "RIDE PDF generation" above), consistent with that section's "never trust a live/stored copy when the authorized XML has it" principle.

## Document Lifecycle

All document endpoints require the `X-Issuer-Id` header (the issuer's UUID, returned by `GET /v1/issuers`).

```
POST /v1/documents             → SIGNED   (Idempotency-Key header optional, documentType required — no default)
POST /:key/send                 → PENDING_SEND (202 — queued; worker later moves it to RECEIVED | RETURNED)
GET  /:key/authorize            → 202 (queued; worker later moves it to AUTHORIZED | NOT_AUTHORIZED  +fires email)
POST /:key/rebuild              → SIGNED  (from RETURNED or NOT_AUTHORIZED)
POST /:key/void                 → VOIDED  (from AUTHORIZED only — manual, tenant attests SRI-side cancellation already happened)
GET  /:key/ride                 → application/pdf  (AUTHORIZED only)
GET  /:key/xml                  → application/xml  (authorization XML or signed XML)
GET  /:key/events               → audit trail for the document
GET  /:key/sri-responses        → raw SRI reception/authorization call outcomes (operationType, status, messages) for this document
GET  /:key/credit-notes         → sum of AUTHORIZED credit notes issued against this document + remaining balance
POST /email-retry               → batch retry all PENDING/FAILED emails
POST /:key/email-retry          → retry single email (?force=true to resend SENT)
POST /v1/mailgun/webhook       → Mailgun delivery event → update email_status (HMAC-verified)
```

`rebuild` corrects invoice content (taxes, items, buyer, payments) and re-signs using the same `access_key`, `sequential`, and `issue_date`. Used when SRI returns RETURNED or NOT_AUTHORIZED.

**Invoice generation steps:**
1. Idempotency check — if key seen + hash matches, return existing doc immediately
2. Issuer provided via `req.issuer` (set by `authenticate` middleware from API key)
3. `SELECT ... FOR UPDATE` → next sequential
4. Generate 49-digit access key (Module 11 check digit)
5. Build unsigned XML (`InvoiceBuilder`)
6. Validate against XSD (`xmllint`)
7. Sign XML (XAdES-BES, PEM private key + cert from `issuers` row)
8. Read `buyer_email` from `body.buyer.email` (required field)
9. `INSERT` into `documents` (with `idempotency_key`, `payload_hash`, `buyer_email`)
10. `bulkCreate` into `document_line_items` (including each item's `additional_details`, if any — see "RIDE PDF generation" below)
11. Log `CREATED` event to `document_events`

## Releasing

Every commit on `main` is a merged PR (often squash-merged, so the SHA on `main` differs from any local commit you made on the branch). That means **`npm version`'s built-in commit+tag step cannot run directly on `main`** — it would push a version-bump commit straight to `main`, bypassing review, and the tag would point at a commit that PR review never saw. Release the same way every other change ships, then tag the result:

1. Branch off `main`: `git checkout -b chore/release`
2. Bump the version **without** letting npm create its own commit/tag: `npm --no-git-tag-version version <patch|minor|major>` (updates `package.json` + `package-lock.json` only)
3. In the same branch, rename `CHANGELOG.md`'s `## [Unreleased]` header to `## [X.Y.Z] — <today's date>` (matching the version just written) and start a fresh empty `## [Unreleased]` above it
4. Commit (`chore: bump version to X.Y.Z`), open a PR, merge it like any other change
5. **After** that PR is merged, pull `main`, then tag the resulting merge commit directly — not the commit you made on the branch: `git tag -a vX.Y.Z -m vX.Y.Z && git push origin vX.Y.Z`

The tag still tracks `package.json`'s version — there's just a merge step between bumping it and tagging it, because the squash-merge changes the commit SHA.

Pushing the tag doesn't trigger any deploy by itself — staging tracks `main` continuously and directly (every merge auto-deploys via `deploy-staging.yml`, no tag involved), so by the time you tag a commit it's typically already been running on staging for a while. The tag is purely a naming/versioning marker: it records "this commit is vX.Y.Z," treated as an **immutable** snapshot. The only thing that acts on a tag is *publishing a GitHub Release from it*, which fast-forwards `production` — see the "Branching strategy" section of `docs/deployment.md`. Never push a follow-up commit to `main` that changes the version after a tag is created; that would leave the tagged commit's `package.json` permanently out of sync with its own tag name. If `package.json`'s version and the latest git tag ever drift apart, fix it with a manual one-off sync commit (`chore:`), then resume this sequence for every release after that.

## Common Mistakes to Avoid

1. Calling a model directly from a controller — always go through the service.
2. String-interpolating SQL — use `$1, $2` always.
3. Throwing `new Error()` instead of an `AppError` subclass — the error handler returns a generic 500.
4. Forgetting `asyncHandler` on a route — async errors are swallowed silently.
5. Forgetting `validateRequest` in the route chain — validator runs but errors are never checked.
6. Signing before XSD validation — signing is expensive; fail fast.
7. Retrying on HTTP-level SRI errors — only retry on `fetch` throws.
8. Not logging an `ERROR` audit event before re-throwing — leaves a gap in the document history.
9. Reading `process.env` directly in a service or model — use `src/config/index.js`.
10. Hardcoding Spanish identifiers in new code — use English everywhere except SRI XML elements.
11. Generating a new idempotency key on every retry — the key must be generated once and reused across retries for the same intended invoice.
12. Adding a new `document_events` event type without updating the `chk_document_events_event_type` CHECK constraint — the INSERT will fail silently if the constraint is not updated in a migration.
13. Calling `db.query()` directly in an authenticated service or model — use `db.queryAsIssuer(issuerId, sql, params, sandbox)` instead so both RLS and the correct `search_path` are set. `db.query()` (no issuer context) is only correct for the webhook, admin, and health code paths. Exception: even in the webhook path, queries against `documents` or `document_events` must use explicit schema prefixes (`public.documents` / `sandbox.documents`) because the webhook has no issuer context to set `search_path` — see `findByEmailMessageId` for the `UNION ALL` pattern.
14. Adding a migration that alters a tenant-scoped table (`documents`, `document_line_items`, `document_events`, `sequential_numbers`, `sri_responses`) without also applying the same DDL to the `sandbox` schema — the schemas must stay structurally identical.
15. Passing `issuer.environment` directly to `accessKeyService.generate()` or the XML builder — always derive `ambiente` from `config.appEnv` and `issuer.sandbox` first, then build an `effectiveIssuer` with the computed value. Using the raw DB field bypasses the staging safety rail and could embed `ambiente = 2` in a document sent to the test endpoint.
16. Using a plain `new Error()` in any request-path code — the error handler only formats `AppError` subclasses. Plain errors produce unformatted 500 JSON.
17. Throwing `new AppError(message, status)` with a generic HTTP-status code when a more specific code exists — clients need specific codes (`CERTIFICATE_EXPIRED`, `ISSUER_FORBIDDEN`, etc.) to react correctly without parsing `detail` strings. Always import from `src/constants/error-codes.js` and pass the code as the third argument.
18. Adding a new `AppError` throw without adding the code to `src/constants/error-codes.js` first — codes defined inline as string literals are not documented, not discoverable, and can silently diverge across call sites.
19. Adding a new notification type without updating **both** CHECK constraints (`chk_notifications_type` in migration 044 and `chk_notification_preferences_type` in migration 045) — the INSERT will fail at runtime. Also add the type to `src/constants/notification-types.js`.
20. Calling `notificationService.runChecksForTenant()` directly from a tenant request — cert checks are now API-owned and run by the admin scheduler (`POST /v1/admin/jobs/notifications`). No sync endpoint is exposed to tenants. `runCertChecksForTenant` is an exported function for the scheduler, not for controllers.
21. Creating or updating a `notifications` row without routing it through `notificationService`'s shared `dispatchNotification(notification)` — every new creation path must call it (directly, as every existing `createX()` does) so the notification durably fans out to webhook subscribers (`WEBHOOK_FANOUT`) and, for email-capable types, dispatches email (`NOTIFICATION_DISPATCH`). Calling `notificationModel.create()` directly and skipping `dispatchNotification()` silently drops both.
22. Returning the webhook secret in PATCH/list responses — the secret is shown **once only** at registration (in the `POST /v1/webhooks` response). Never include `row.secret` in any other response shape.
23. Relying on a multer instance's `limits.fileSize` to cap one specific field when the same instance handles other fields too — the limit applies to the whole request, not per field (e.g. registration's multer covers both the P12 cert and the logo with one 10 MB ceiling). When a field needs its own stricter cap, check `req.files.<field>[0].size` manually in the controller and throw `AppError` with `INVALID_FILE_UPLOAD`.
24. Adding a new column called `updated_at` to a table without also adding a `trg_<table>_updated_at` trigger (see migration 051, `set_updated_at()`) — there is no ORM, so without the trigger nothing bumps the timestamp and it silently drifts (this happened to `issuers.updated_at` via `updateLogo`/`updateCertificate` before the trigger existed).
25. Adding `isArray()` validation for a field on a route that accepts `multipart/form-data` (any route with a file upload) without a `customSanitizer` that JSON-parses string values first — multipart fields never auto-deserialize a JSON string into an array, so a client sending a JSON-encoded array (the only way to send one over multipart) always fails `isArray()`. See the `arrayFromJsonString` helper in `src/validators/issuer.validator.js` (mirrors the one in `registration.validator.js`) for the pattern; apply it to `documentTypes`/`initialSequentials`-shaped fields on any future multipart route.
26. Computing a subscription's next `current_period_start`/`current_period_end` from `new Date()` ("now") instead of the OLD `current_period_end` — an admin reviewing a renewal/upgrade proof a few days early or late would then drift the billing date forward or backward every cycle. Always anchor to the old `current_period_end` via the shared `addBillingPeriod()` helper in `subscription.service.js`, used by `applyVerifiedPayment`'s RENEWAL path and `applyScheduledTierChanges`'s period rollover. **Never hand-roll the month arithmetic** — `addBillingPeriod` delegates to `src/utils/add-months.js`, which clamps to month-end; a bare `Date.setMonth()`/`setUTCMonth()` silently normalizes an out-of-range day (Jan 31 + 1 month becomes "Feb 31" = Mar 3), which was a real shipped bug in both this helper and `tenant-quota.service.js`'s period rollover: a period anchored to the 29th–31st handed the customer a free extra month, and because each renewal anchors to the previous, already-drifted period end, the anniversary shifted permanently instead of self-correcting. Two legitimate exceptions where "now" IS the right anchor: `applyVerifiedPayment`'s INITIAL path (no prior period exists — this is the first cycle) and `resetPeriodOnPromotion` (deliberately restarting the clock at the moment the tenant enters production).
27. Calling `subscriptionService.processDueRenewals()` before `applyScheduledTierChanges()` in the admin subscriptions job — a downgrade that hasn't been applied yet still has its old (soon-to-be-stale) `current_period_end`, and `processDueRenewals`'s expiry check would wrongly flag it as having run out the grace period. `applyScheduledTierChanges()` must run first in the same job tick so its period rollover lands before the expiry check reads `current_period_end`.
28. Reading `subscription.tier`/`subscription.billing_interval` directly in any code that displays a `payments` row (email templates, notifications) — for a `TIER_CHANGE` payment, the subscription still reflects its CURRENT tier/interval, not what's being purchased, until the change actually applies. Always use `payment.target_tier || subscription.tier` and `payment.target_billing_interval || subscription.billing_interval` (the fallback correctly covers `INITIAL`/`RENEWAL` payments, which never set `target_tier`). Also always read `payment.total_amount` for a displayed dollar figure, never `payment.amount` — the latter is the pre-IVA base imponible, not what the tenant actually transfers. Every payment-display surface (`notification-email-template.service.js`'s value builder, `payment-proof-submitted.js`, `notification.service.js`'s `createPaymentReviewed`) follows this same pattern.
29. Treating `linkInvoice` as though it still drives subscription state. Since ADR-027 it is **pure bookkeeping** — it records which document settles which payment and stamps `payments.invoiced_at`, and triggers no transition at all. Activation, tier flips, and renewals all happen in `applyVerifiedPayment` at payment-verification time. The sandbox/production fork it used to need (`linkSandboxDocument`) is gone: sandbox documents simply skip both FK columns and still stamp `invoiced_at`. Do not reintroduce state changes here — a second path that grants a tier would silently double-apply alongside `applyVerifiedPayment`.
30. Adding a new authenticated route without deciding how it handles a `SUSPENDED` tenant. `authenticate` no longer blocks suspension itself — a new route in a router that applies `requireNotSuspended` per-route (currently `documents`, `subscriptions`, `tenants`, `payments`) is reachable by a suspended tenant unless you explicitly add the middleware to that route. A new router should default to `router.use(requireNotSuspended)` right after `router.use(authenticate)` unless it specifically needs a read-while-suspended exception.
31. Checking `subscriptionModel.findActiveByTenantId()` (ACTIVE only) instead of `findActiveOrPendingByTenantId()` (anything not `CANCELLED`/`EXPIRED`) before deciding whether to start a new subscription. `tenant.service.js`'s `promote()` used to do exactly this — a tenant who'd pre-subscribed but was still `PENDING_PAYMENT`/`PAYMENT_RECEIVED`/`INVOICE_PROCESSING` (payment uploaded, awaiting operator review) fell through the `ACTIVE`-only check and got a second subscription/payment kicked off on promotion, alongside the one already in flight. Any code deciding "does this tenant already have billing in progress" needs the broader in-flight check, not just `ACTIVE`.
32. Adding a file that's read from the filesystem at **runtime** (not just at build/authoring time) under a path `.dockerignore` excludes wholesale. `.dockerignore` excludes `docs` and `*.md` entirely (so documentation doesn't bloat the deploy image), but `agreement.service.js`'s `publish()` reads `docs/agreements/*.md` on every `POST /v1/admin/agreements` call — those files needed explicit `!docs/agreements` / `!docs/agreements/*.md` negation patterns or the built image silently ships without them, throwing an unhandled `ENOENT` in every deployed environment despite working locally (no Docker layer in the loop there). Any future runtime-read source file living under `docs/` needs the same carve-out.
33. Leaving Cloudflare's zone-wide Email Obfuscation enabled on a Cloudflare-proxied API hostname. `GET /v1/agreements/:type` and `GET /v1/tenants/agreements/:type` serve HTML with real embedded contact email addresses (`{{soporte.email}}`/`{{operador.email}}`, already substituted into the stored snapshot — see "Legal documents and tenant acceptance" above). Cloudflare's Email Obfuscation rewrites those addresses into `<span data-cfemail="...">` placeholders backed by a relative `/cdn-cgi/l/email-protection` decode script; when comprobify-web fetches this HTML server-side and proxies it to the browser, that relative script 404s against the frontend's own domain, so addresses render as `[email protected]`. Fixed via a Cloudflare Configuration Rule scoping Email Obfuscation → Off to just `api.comprobify.com` / `api-staging.comprobify.com` — see `docs/deployment.md`'s "Cloudflare configuration" section. Any new Cloudflare-proxied API hostname must be added to that rule's expression or its agreement pages silently break the same way.
34. Writing admin-submitted agreement edits back to `docs/agreements/*.md` (e.g. via `fs.writeFileSync`) instead of straight into `agreements.content_markdown`. Render's container filesystem is ephemeral and rebuilt from the git-committed image on every deploy (see the Releasing section) — a runtime file write is invisible to the next deploy and, if the admin API ever runs more than one instance, invisible to other instances too. `publish()`'s `contentMarkdown` parameter exists specifically so admin edits go straight to the DB and never touch the filesystem; any future "edit and republish" UI must keep using that path, not resurrect a file-write step.
35. Using `payments.invoice_document_id IS NULL` as a state signal for a payment. It is never set for a sandbox-linked document (both FKs reference `public.documents`, and `sandbox.documents` is an independent id sequence that can collide with it), so any check gated on it silently misreads every sandbox payment forever. Two different questions, two different columns: **"has this payment been applied?"** is `period_start IS NULL` (`findPendingTierChangeBySubscriptionId`/`findPendingRenewalBySubscriptionId`, and `subscription.model.js`'s `findDueForRenewalReminder` `NOT EXISTS` subquery) — the one column both environments stamp when `applyVerifiedPayment` runs; **"has an invoice been issued for it?"** is `invoiced_at IS NULL` (`findOldestUninvoicedBySubscriptionId`, `findPendingInvoice`), stamped by `linkInvoice` in both environments. Neither question is answered by `invoice_document_id`.
36. Writing `subscriptions.status = 'PAYMENT_RECEIVED'` or `'INVOICE_PROCESSING'`. Both are **legacy values** — steps in the invoice-gated activation flow ADR-027 removed. They remain in `chk_subscriptions_status` only so historical rows stay valid; nothing writes them any more, and `reviewPayment` now goes straight to `ACTIVE` via `applyVerifiedPayment`. Reintroducing either would strand the subscription outside `findActiveByTenantId`, silently breaking every flow gated on it (further tier changes, renewal reminders, expiry checks) — which is exactly the bug that made `reviewPayment` stop writing `PAYMENT_RECEIVED` for non-`INITIAL` payments in the first place.
37. Confusing `subscriptions.initial_invoice_document_id` (migration 072, renamed from `invoice_document_id`) with `payments.invoice_document_id` — two different FKs on two different tables with two different lifetimes. `subscriptions.initial_invoice_document_id` is **write-once**: it records the invoice that funded the subscription's original activation, and is now guarded structurally by `subscriptionModel.setInitialInvoiceDocument`'s `WHERE initial_invoice_document_id IS NULL` clause rather than by convention. Every subsequent funding event (`TIER_CHANGE`, `RENEWAL`) writes its own `payments.invoice_document_id` instead. Do not add code that repoints the subscription's column at a later invoice — it would erase the record of what actually started the subscription. Since ADR-027 neither column dispatches anything; both are audit records.
38. Calling `tenantModel.updateTier(id, tier)` without a matching `tenantQuotaService.setCap(id, tier)` call right after it (migration 073 split what used to be one `UPDATE tenants SET subscription_tier, document_quota` statement into two independent calls, one per table, since quota moved to `tenant_quotas`). `tenantModel.updateTier` only ever touches `subscription_tier` now — every one of its ~10 call sites (`admin.service.js`'s `updateTenantTier`, and 9 in `subscription.service.js`) must pair it with `tenantQuotaService.setCap` or the tenant's tier changes while their quota cap silently stays at the old tier's value.
39. Adding or changing a `documents.status` transition in `src/constants/document-state-machine.js` without also updating the `enforce_document_state_transition()` DB trigger function (migration 027, `CREATE OR REPLACE FUNCTION`, reused by both `public.documents` and `sandbox.documents` via `trg_..._state_transition`). This trigger hardcodes the identical transition graph **independently** of the JS state machine — it is not derived from it. Migration 074 (adding `PENDING_SEND`) had to update both in the same migration; updating only the JS side would pass `assertTransition()`'s check in application code but still get rejected by Postgres with `Invalid document state transition: X -> Y` at the `UPDATE` itself.
40. Reading `TIERS[tier].priceMonthlyUsd`/`priceYearlyUsd` directly for any real billing calculation — these keys were removed from `src/constants/subscription-tiers.js` entirely (migration 076, ADR-023). Always resolve through `pricingService.getCurrentPrice(tier, billingInterval)` or `getPriceAsOf(tier, billingInterval, asOfDate)`; a stale direct read would silently bypass the 30-day price-change protection.
41. Resolving a payment's price against "now" when it's actually funding a *deferred* billing period (a renewal, a deferred billing-interval change) instead of the period's own start date (`subscription.current_period_end`). This is the other half of Common Mistake #40 — using `getCurrentPrice` instead of `getPriceAsOf(tier, interval, subscription.current_period_end)` at `createRenewalReminder`/the deferred-interval-change branch of `requestTierChange` would silently reprice a renewal that was supposed to still be protected by an in-flight 30-day notice window. See "Price history + 30-day change notice"'s as-of-date principle above.
42. Building any single-use, security-sensitive token flow (email verification, password reset, invite acceptance, etc.) as one combined `GET` that both validates and consumes the token in the same request. Corporate email link-scanners (Microsoft Defender/Safe Links, and similar antivirus/proxy prefetchers) issue a plain `GET` against every link in an email *before* the user ever clicks it — a combined check-and-consume `GET` lets that automated prefetch silently burn the token, so the user's real, first-ever click then fails with an already-used/expired error. This actually happened to email verification: `GET /v1/verify-email?token=` used to both look up the token and call `tenantModel.activate()` (which nulls `verification_token` in the same statement) in one request. Fixed by splitting into a non-consuming read (`GET /v1/verify-email/check`, safe to prefetch repeatedly — see `registrationService.checkVerificationToken()`) and a consuming action gated behind `POST` (`POST /v1/verify-email`, body `{ token }` — a scanner's `GET`-only prefetch can never trigger it). Any new single-use-token flow must follow the same shape: the mutating step must require a verb/action a passive prefetch cannot produce.
43. Adding a new `express-rate-limit` limiter without wiring it onto the shared Redis store via `buildStore(prefix)` (`src/middleware/rate-limit.js`). A limiter left on express-rate-limit's default in-memory store silently reintroduces the exact per-instance-counter bug the shared store exists to fix, just scoped to that one route — a tenant/IP gets roughly `limit × N` instead of `limit` once more than one `api` instance is running. Always pass both `store: buildStore('rl:<name>:')` (a prefix distinct from the four already in use) and `passOnStoreError: true` (fails open on a Redis outage instead of 500ing every request through that limiter) on any new limiter.
44. Calling `ipKeyGenerator(req)` instead of `ipKeyGenerator(req.ip)` — `ipKeyGenerator`'s signature takes an IP address string, not a request object. Passing the whole `req` object makes its internal `isIPv6()` check return false, so it silently returns that same object back unchanged; string-concatenated into a store key (Redis or in-memory), it coerces to the literal `"[object Object]"` for every request regardless of source IP. This was a real, previously-shipped bug: `rate-limit.js`'s shared `keyGenerator` and both `adminLimiter`/`registrationLimiter` did exactly this from the very first rate-limiting commit, silently collapsing `adminLimiter`'s "20 req/min per IP" into 20 req/min shared globally across every IP hitting `/v1/admin/*` (and the same for `registrationLimiter`'s 5/hour) — one aggressive caller could exhaust the bucket for every unrelated IP. Fixed alongside wiring the same helper into `authenticate-admin.js`/`verify-mailgun-webhook.js` for `attempt-tracker.service.js` (see "Repeated-attempt detection" above) — always pass `req.ip`, never `req`, to `ipKeyGenerator`.
45. Adding a new sensitive-endpoint failure (or, per `RECOVERY_SUCCESS`, success) path without wiring `attemptTrackerService.recordEvent()` in, or hardcoding an event-type string literal instead of adding it to `AttemptEventTypes` (`src/constants/attempt-event-types.js`) first — mirrors every other enum-like constant in this codebase (`NotificationTypes`, `EffectTypes`, etc.), never inline string literals at call sites.
46. Trusting `express-winston`'s default `requestWhitelist`/`responseWhitelist` (`request-logger.js`). The defaults include `headers` and `originalUrl`/`query` — logging those as-is would ship the raw `Authorization: Bearer <token>` header and query-string secrets (e.g. a verification `?token=...`) straight to Betterstack. `request-logger.js` deliberately empties both whitelists and builds every logged field explicitly via `buildLogMeta`/`buildLogMessage` instead (`req.path`, never `req.originalUrl`/`req.url`) — any change to this middleware must preserve that, not fall back on express-winston's built-in field selection.
47. Parsing a header or query param with `parseInt()` and validating the result is "a positive integer" — a pattern that predates ADR-020's UUID primary key migration but lingered undetected in `notification.controller.js`'s `parseOptionalIssuerId()`/`parseSinceId()` long after every id in the schema became a UUID. `parseInt("019fb533-...", 10)` doesn't fail loudly — it silently reads only the leading decimal digits (e.g. truncates to `19`), which then fails a subsequent string-equality check, so the endpoint 400'd on every syntactically valid UUID it was ever given. This class of bug is easy to miss precisely because it doesn't crash or error at the parsing step itself — grep for `parseInt` near anything that touches an id/header/query value derived from this schema, and validate against a UUID pattern (`resolve-issuer.js`'s `UUID_PATTERN`) instead of an integer check.
48. Deriving a computed value from a field that doesn't actually exist on the object you're reading — `parseFloat(undefined)` doesn't throw, it silently returns `NaN`, and `NaN` propagates through arithmetic and `.toFixed(2)` into the *string* `"NaN"`, which Postgres happily accepts as a valid `DECIMAL` literal (`'NaN'::numeric` is a real, special value, not an error). `document-line-item.model.js`'s `bulkCreate()` computed each item's tax amount from `t.value` — a field that has never existed on a request-body tax object (only `code`/`rateCode`/`rate` do; the actual dollar amount is only ever computed inside the XML builders, from `rate`, and never passed back to this model) — so every `document_line_items.line_total` ever inserted was `NaN` until this was caught. Fixed by deriving it the same way the builders do (`subtotal * (rate / 100)`), not by reading a field that was never there. When a computed column looks suspicious (`NaN`, unexpectedly `0`, always the same value), check whether the source field the calculation reads actually exists on the object at that point in the code path — don't assume a field name is correct just because the code compiles and doesn't throw.
49. Adding a new key to a `TIERS[tier]` entry (`subscription-tiers.js`) without adding a matching entry to `tier-limit-scope.js`'s `TIER_LIMIT_SCOPE` — nothing enforces this at runtime, so a missed one just silently ships a cap through `GET /v1/tiers` with no declared owner (comprobify or comprobify-web). See "Tier limit scope: API vs WEB" above and ADR-031.
50. Calling `applyScheduledTierChanges()` before `applyScheduledSeatChanges()` in the admin subscriptions job. The tier job rolls `current_period_end` forward; the seat job's due-query is keyed on `current_period_end <= NOW()`, so a due seat decrease becomes invisible and silently slips a full period. Sibling of #27 — the whole job is ordered seats → tiers → renewals. See "Extra user seats" above and ADR-032.
51. Pricing a deferred period (a renewal, or `requestTierChange`'s billing-interval-change branch) off `subscription.extra_seats` directly instead of `effectiveSeatsAtPeriodEnd(subscription)` (`pending_extra_seats ?? extra_seats`). A scheduled seat decrease lands at the exact `current_period_end` these payments are priced *for* — pricing off the pre-decrease count overcharges for seats that are about to go away. Seat-flavored sibling of #41.
52. Gating `registration.service.js`'s `register()`/`recover()` key mints behind `effectiveApiKeyLimit()`/`TIERS[tier].maxApiKeys` (ADR-034). These two calls exist specifically so every tenant, on every tier including FREE/SOLO/LITE (`maxApiKeys: 0`), gets one fully-working key the instant they register or recover — before they've ever called `POST /v1/keys`, and regardless of the self-service pool being off. Routing them through the same tier-limit check `api-key.service.js`'s `createKey()` uses would leave a fresh entry-tier tenant with zero usable keys and no way to self-mint one either, since their own pool is 0. Since migration 102, `register()`'s mint is also always `isReserved: true` — don't flip that to `false`, it would make the key both bypass the tenant's own budget *and* be visible/revocable through their own `GET`/`DELETE /v1/keys`, which defeats the point of tagging it reserved at all.
53. Adding a new account creation/recovery/activation route (or a variant of an existing one) without mounting `requireInternalService` on it (ADR-035). `POST /v1/register`, `/recover`, `/resend-verification`, and `POST /v1/verify-email` are deliberately unreachable by anything but comprobify-web's own BFF — a new route in this family that skips the gate silently reopens direct API access to account creation, the exact thing ADR-035 closed. `GET /v1/verify-email/check` is the one deliberate exception (read-only, consumes nothing) — a new route needs the same justification to skip the gate, not just convenience.
54. Adding a new subscription/payment **mutation** route without mounting `requireInternalService` (ADR-035's addendum) alongside the existing `authenticate` + `requireScope('billing:manage')` chain. Unlike Common Mistake #53, the rationale here isn't anonymous-abuse prevention (these routes are already tenant-authenticated) — it's that every billing mutation must flow through comprobify-web's own checkout/proof-upload UX, not be directly callable by a tenant's own key. A new mutation in `subscriptions.routes.js`/`payments.routes.js` that skips the gate reopens direct billing control the same way a new registration route without it would reopen anonymous signup. A new **read**-only route in these two routers does not need the gate by default — mirror the existing 3 exceptions (`GET /v1/subscriptions/me`, `GET /v1/payments/:id/proofs`, `.../proofs/:proofId`), which stay on tenant-key auth alone.
