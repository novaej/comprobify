## [Unreleased]

## [0.15.0] — 2026-08-10

### Added
- **Certificate changes are now audited (migration 086), closing NEXT_STEPS' "Audit Certificate Changes" item.** Uploading a new P12 (self-service registration, self-service branch creation, admin issuer creation) logs a `CERTIFICATE_UPLOADED` `tenant_events` row; replacing an issuer's certificate in place (self-service and admin renewal) logs `CERTIFICATE_RENEWED`. Both carry `{ issuerId, certFingerprint, certExpiry }`. Branch/issuer creation that copies an already-audited certificate from a sibling issuer (no P12 supplied) does not log a duplicate event. Previously a certificate replacement — the thing that makes a signed invoice legally valid — left no trace beyond an inferable `issuers.updated_at` bump.
- **`api_keys.scopes` (migrations 084/085) — per-key permission scopes, closing NEXT_STEPS' "API Key Scopes" item.** A tenant can now mint a key narrower than "do everything this tenant can do" — e.g. one key per user role in a frontend's own RBAC, not just a single read-only/full-access split. 9-value vocabulary (`src/constants/api-key-scopes.js`): `documents:write` / `documents:read` (document mutations vs. every other document `GET`, unchanged from the original design), `issuers:read` / `issuers:write` (the `/v1/issuers` router split by verb, since every role needs to see issuers but not all need to mutate them), `keys:manage` (the entire `/v1/keys` router), `billing:manage` (`/v1/subscriptions` + `/v1/payments`), `webhooks:manage` (`/v1/webhooks`), `tenant:manage` (`PATCH /v1/tenants/language`, `POST /v1/tenants/agreements`), and `tenant:promote` (`POST /v1/tenants/promote` only, split out given it mints/revokes every key and flips sandbox→production irreversibly). New `requireScope(scope)` middleware factory (`src/middleware/require-scope.js`, the codebase's first factory middleware) throws `403 INSUFFICIENT_SCOPE`. `POST /v1/keys` accepts an optional `scopes` array (validated against the vocabulary) and now returns `{ apiKey, scopes }`; `GET /v1/keys` surfaces each key's `scopes`. **Privilege containment:** `api-key.service.js`'s `createKey()` now rejects (`403 SCOPE_ESCALATION_FORBIDDEN`) minting a key with any scope the requesting key doesn't itself hold, and omitting `scopes` clones the requesting key's own scopes rather than defaulting to full access — otherwise a `keys:manage`-only key could mint itself a broader one just by leaving the field out. Existing keys and any key created with no prior key to inherit from (registration, admin, account recovery) still default to all 9 scopes (full access) — fully backward compatible.
- **`api_key_daily_usage` table (migration 083) — persistent, daily-granularity usage tracking per API key, one write per request.** `authenticate` middleware fire-and-forgets a single upsert into today's row on every successful lookup; lifetime `lastUsedAt`/`requestCount` (surfaced on the tenant-facing `GET /v1/keys` and a new `GET /v1/admin/tenants/:id/api-keys` — admin previously had no way to list a tenant's existing keys at all, only blind create/revoke) are an aggregate over the same table, not a separately-maintained counter. New `GET /v1/keys/:id/usage` and `GET /v1/admin/tenants/:id/api-keys/:keyId/usage` (`?days=1-365`, default 30) return a zero-filled daily series ready to feed a chart. Closes NEXT_STEPS' "API Key Usage Tracking" item.

### Fixed
- **`campoAdicional`'s `Proveedor` entry sent the RUC concatenated with the operator's name; SRI Resolution NAC-DGERCGC26-00000027 expects a standalone RUC-only field.** `base.builder.js` and `ride.service.js` now emit a `RUC Proveedor` entry holding just `config.operator.ruc`, matching what SRI actually requires. Source-only change; no API surface affected (this field was never client-visible).
- **Every non-HTTP call site that minted an API key (registration's initial-signup and account-recovery keys, admin-minted keys, and the sandbox→production key-mirroring loop on both the tenant-facing and admin promote flows) omitted the now-required `scopes` field, which would have 500'd on a real database (`api_keys.scopes` is `NOT NULL` with no INSERT-time default when the column is named explicitly) — never hit in CI since these paths are unit-tested with a mocked model.** Caught by running migration 085 against a real local database rather than trusting mocks alone. All five call sites now pass `scopes` explicitly; the two promote-mirroring sites pass the sandbox key's own `scopes` (preserving whatever scoping it already had) rather than defaulting every mirrored key to full access.

## [0.14.1] — 2026-08-06

### Fixed
- **RIDE PDF omitted the `Proveedor` additional-info entry.** `base.builder.js` appends this entry (SRI Resolution NAC-DGERCGC26-00000027) at XML-build time, but the injection is never persisted back onto `request_payload`, so `ride.service.js` silently dropped it from the rendered RIDE even though it's present in the SRI-authorized document. `ride.service.js` now reconstructs the same entry when building RIDE data.

### Changed
- **Privacy policy discloses per-request IP logging.** Structured Request Logging (`request-logger.js`) began shipping the request `ip` field to Betterstack once `BETTERSTACK_SOURCE_TOKEN` was configured on staging, contradicting §6's "no per-request IP log" claim — a tripwire flagged in advance by the prior legal review. §4 now names Betterstack as a subprocessor and §6 discloses per-request IP logging with its 3-day retention. Source-only change; not yet published via `POST /v1/admin/agreements`.

## [0.14.0] — 2026-08-06

### Added
- **`INTERNAL_SERVICE_SECRET` (optional) + `src/middleware/trusted-forwarded-ip.js`.** Lets a trusted first-party BFF (comprobify-web) forward the real visitor IP for calls it proxies server-side (register, recover, agreements acceptance) via an `X-Forwarded-Visitor-Ip` header, authenticated by a constant-time-compared `X-Internal-Service-Secret`. Without it, `req.ip` for those calls resolves to the BFF's own shared hosting-platform egress IP — collapsing `registrationLimiter`'s per-IP rate limit across unrelated visitors, and recording the wrong IP in the `tenant_agreements` legal consent audit trail. Unset means the feature is inactive and `req.ip` resolution is unchanged. See NEXT_STEPS.md #8 for the full design rationale and the comprobify-web-side work this depends on.

## [0.13.5] — 2026-08-06

### Fixed
- **Found the actual reason `req.ip` never reflected any of the 0.13.1-0.13.4 fixes: Caddy was never reading the updated config at all.** `stat` on the running container's `/etc/caddy/Caddyfile` showed `Links: 0` and a July 29 mtime — the file had been unlinked from the filesystem since the very first deploy, kept alive only by Caddy's own open file descriptor. `docker-compose.yml`'s single-file bind mount (`./Caddyfile:/etc/caddy/Caddyfile`) pins to that file's specific inode at container-start time; the deploy tool replaces the host file via unlink+recreate rather than truncate-in-place, so every subsequent deploy silently updated a directory entry the running container could no longer see, while `caddy reload` kept re-parsing the same stale, orphaned inode (confirmed by its own `"config is unchanged"` log line every time). Now mounts the containing directory (`deploy/caddy/`) instead of the single file, so directory-entry updates are visible without needing container recreation. This doesn't change any Caddy config logic from 0.13.3/0.13.4 — it's what finally lets that config run for the first time.

## [0.13.4] — 2026-08-05

### Fixed
- **`req.ip` still resolved to Cloudflare's edge IP even after 0.13.3's `trusted_proxies` fix.** Caddy's `client_ip_headers` option defaults to `X-Forwarded-For` only, so `CF-Connecting-IP` was never actually read as a client-IP source regardless of `trusted_proxies`. Rather than iterate again on `X-Forwarded-For`'s automatic hop-counting/augmentation behavior, Caddy now resolves the real client IP once via its own `{client_ip}` placeholder (`trusted_proxies` + `client_ip_headers CF-Connecting-IP X-Forwarded-For`) and forwards it through a single dedicated `X-Real-Client-IP` header. New `src/middleware/resolve-client-ip.js` overrides `req.ip` from that header — safe to trust unconditionally, since `api` is only Docker-`expose`d and never reachable except through Caddy.

## [0.13.3] — 2026-08-05

### Fixed
- **`req.ip` still resolved to Cloudflare's edge IP even after 0.13.2 deployed with the Caddy reload fix.** Root cause: Caddy discards inbound `X-Forwarded-For` entirely by default without `trusted_proxies` configured, and 0.13.1's workaround (forwarding `CF-Connecting-IP` as a single-hop `X-Forwarded-For`, `trust proxy: 1`) didn't account for Caddy always appending its own peer IP regardless of an explicit `header_up` override. `deploy/Caddyfile` now lists Cloudflare's published IP ranges as `trusted_proxies`, so Caddy trusts and augments the already-correct inbound header instead of replacing it; `trust proxy` is back to `2` to match the real Cloudflare-then-Caddy chain.

## [0.13.2] — 2026-08-05

### Fixed
- **The 0.13.1 `CF-Connecting-IP`/`trust proxy` fix had no effect on the running staging deployment.** `docker compose up -d` only recreates a container when the service definition itself changes (image tag, env, volumes list) — `Caddyfile` is bind-mounted, so a content-only change on disk is invisible to Compose, and the running `caddy` container kept serving the old config it loaded at startup even after the file on disk was updated. The `api` container's `trust proxy` change took effect immediately (its image tag changes every deploy), but with Caddy still on the old config, `req.ip` kept resolving to Cloudflare's edge IP. `deploy-staging.yml`/`deploy-production.yml` now explicitly run `docker compose exec caddy caddy reload` after every deploy so a Caddyfile-only change actually takes effect.

## [0.13.1] — 2026-08-05

### Fixed
- **`req.ip` resolved to Cloudflare's edge IP instead of the real client IP on the staging deployment**, discovered via a structured log line showing a Cloudflare-range address (`162.158.x.x`) as the request's `ip`. Caddy (the droplet's reverse proxy in front of the API container) doesn't trust the inbound `X-Forwarded-For` from Cloudflare without `trusted_proxies` configured, so it replaced it with its own immediate peer (Cloudflare's edge IP) rather than forwarding the real client — combined with Express's `trust proxy: 2` (expecting a Cloudflare-then-Caddy chain that wasn't actually there), this silently pooled `adminLimiter`/`registrationLimiter`'s per-IP rate limits into one shared bucket across every caller going through Cloudflare. `deploy/Caddyfile` now forwards Cloudflare's `CF-Connecting-IP` header (always the true client IP, not spoofable) as `X-Forwarded-For` explicitly, and `trust proxy` is dropped to `1` to match the resulting single-hop chain.

## [0.13.0] — 2026-08-04

### Added
- **`GET /v1/documents/:accessKey` now includes a `dispatch` field (`{ status, attemptCount, lastError }`) while `status` is `PENDING_SEND` or `RECEIVED`.** Lets a client polling for the outcome of `send`/`authorize` tell "still auto-retrying" apart from "exhausted all 5 automatic attempts, needs `POST /:accessKey/send/retry`" — the two timescales don't match (reconciliation spaces automatic re-attempts 5 minutes apart, up to ~20+ minutes to exhaust all 5), so guessing from a typical short polling window's elapsed time alone would false-positive on "stuck" long before it actually is. Absent once the document reaches a settled status.
- **`POST /v1/documents/:accessKey/send/retry` and `POST /v1/tenants/retry-failed-documents`** — tenant-facing recovery for a document whose SRI send/authorize dispatch exhausted its automatic retry budget (5 attempts) and got permanently stuck. There was previously no way back from that state at all (`queue-reconciliation` only scans `PENDING`/`DISPATCHED` `pending_effects` rows, and the worker always `nack`s a failed message with `requeue: false`, so RabbitMQ never retries it either) — both endpoints reset the underlying effect to a fresh `attempt_count` budget and dispatch it immediately. The single-document endpoint lives under `/v1/documents/*` (issuer-scoped, like everything else there); the bulk variant lives under `/v1/tenants/*` and deliberately doesn't require `X-Issuer-Id`, covering every issuer/branch on the tenant in one call — meant for recovering from something like a multi-branch SRI-side outage without one call per document. New `pending_effects.document_id` column (migration 082) backs the lookup.
- **`hasPublishedAgreements: boolean`** on `GET /v1/tenants/agreements`'s response, alongside the existing `needsAcceptance`/`outdated` fields.
- **`GET /v1/verify-email/check`** — read-only, non-consuming check of whether a verification token is still valid. Safe to call repeatedly, including by automated email link-scanners.
- **`POST /v1/verify-email`** — the consuming verification action (moved off `GET`), taking `{ token }` in the request body. Activates the tenant; intended to be triggered only by an explicit user action.
- **Repeated-attempt detection** (`src/services/attempt-tracker.service.js`) — a small, reusable mechanism that flags a repeated-attempt pattern against the same `(eventType, key)` pair as a signal for the operator, not as brute-force prevention (every secret involved is already high-entropy). Wired into four call sites: repeated *successful* `POST /v1/recover` issuances for the same tenant (anti-enumeration means every non-match already looks identical, so success-repetition is the only signal), repeated invalid API keys against `authenticate`, repeated wrong `ADMIN_SECRET` values against `/v1/admin/*`, and repeated invalid Mailgun webhook signatures. Backed by the same Redis connection as the rate limiters (`REDIS_URL` — a no-op without it); on the exact count that crosses the configurable threshold (`ATTEMPT_TRACKER_THRESHOLD`/`ATTEMPT_TRACKER_WINDOW_MS`, default 5 within 15 minutes), fires both a structured log line and `Sentry.captureMessage` (tagged by `eventType`) so it's actually visible immediately. See [ADR-026](docs/adr/026-redis-shared-counter-store.md) and `docs/guides/repeated-attempt-detection.md` for the alert-response runbook.
- **Structured request logging** (`src/services/logger.service.js`, `src/middleware/request-id.js`/`request-logger.js`) — one structured JSON line per HTTP request (`timestamp`, `method`, `path`, `statusCode`, `durationMs`, `ip`, `requestId`, and `keyHash`/`apiKeyId`/`tenantId`/`issuerId` once authenticated), mounted ahead of everything else so every request gets a line regardless of whether it ever authenticates. Deliberately never logs the query string (`req.path`, not `req.originalUrl`) or the `Authorization` header — `express-winston`'s default whitelists would otherwise leak both to a third-party log platform. `X-Request-Id` is echoed back on every response and tagged onto Sentry's current scope (`Sentry.setTag`), so a captured exception can be correlated back to its exact log line — the two systems otherwise share no common id. A matching structured line is emitted per async effect processed by `workers/worker.js` (`pending-effect.service.js`'s `process()`), correlated back to the originating request via the document's `accessKey`/`documentId` when present, since `POST /:key/send`/`GET /:key/authorize` return `202` immediately and the actual outcome happens later, out of the request/response cycle. `attempt-tracker.service.js`'s threshold-crossing line now also routes through this same shared logger. Always prints locally (`Console` transport); ships to Betterstack when the optional `BETTERSTACK_SOURCE_TOKEN` is set. `BETTERSTACK_INGESTING_HOST` is a second, also-optional var for sources assigned a regional ingesting host rather than the shared default — omitting it when your source needs one means every sync attempt 401s. Every log entry also carries a `hostname` field (`os.hostname()`, set once via winston's `defaultMeta`) — the only way to tell apart log lines from different machines (local dev vs. the staging droplet, or staging vs. production later) when they all ship to the same Betterstack source; `deploy/docker-compose.yml` now sets an explicit `hostname: comprobify-api-${APP_ENV}`/`comprobify-worker-${APP_ENV}` on those two services instead of leaving Docker's default opaque per-container id.

### Changed
- **Rate limiters (`writeLimiter`/`readLimiter`/`adminLimiter`/`registrationLimiter`) now share a Redis-backed store instead of each defaulting to `express-rate-limit`'s per-process in-memory one.** Required for running more than one `api` instance correctly — previously each instance counted requests independently, so N instances let a tenant/IP burst to roughly `limit × N` before any single instance throttled them. `REDIS_URL` is optional (falls back to the in-memory store when unset, correct for today's single-instance topology); every limiter fails open (`passOnStoreError: true`) on a Redis outage rather than 500ing. Self-hosted via a new `redis` service in `deploy/docker-compose.yml`. See [ADR-026](docs/adr/026-redis-shared-counter-store.md).

### Removed
- **`RATE_LIMIT_MAX` environment variable.** It was parsed into config from the very first rate-limiting implementation but never actually read by `writeLimiter`/`readLimiter` — their request-count ceiling has always come from either a hardcoded literal (pre-tier-aware limits) or `TIERS[tier].writeRateLimit`/`.readRateLimit` (post-tier-aware limits, current behavior), never from this env var. It was documented in `.example.env`, CLAUDE.md, and the deployment docs as if it controlled the write-endpoint limit, which was never true. `RATE_LIMIT_WINDOW_MS` is unaffected and remains the one genuinely configurable rate-limit setting.

### Fixed
- **`GET /v1/notifications`'s `X-Issuer-Id` header and `?sinceId=` cursor always `400`'d, even with a perfectly valid UUID.** `notification.controller.js`'s `parseOptionalIssuerId()`/`parseSinceId()` still `parseInt()`'d these values and validated the result was "a positive integer" — leftover from before ADR-020's UUID primary key migration. `parseInt()` on a UUID string silently truncates to its leading decimal digits (e.g. `"019fb533-..."` → `19`), which then always fails a subsequent string-equality check against the original value. Both now validate against the same UUID regex `resolve-issuer.js` already uses elsewhere. `POST /v1/notifications/:id/read`'s `id` path param was never affected (it already validated correctly via `express-validator`'s `.isUUID()`) — only its endpoint documentation had the same stale "positive integer" wording, also corrected. While in the docs, the same stale wording was found and fixed on four unrelated issuer-endpoint pages (`activate-issuer`, `renew-issuer-certificate`, `upload-issuer-logo`, `issuer-sequentials`, es/en) — their underlying code already validated `id` as a UUID correctly; only the docs had drifted. See CLAUDE.md Common Mistake #47.
- **`adminLimiter`/`registrationLimiter` (and `writeLimiter`/`readLimiter`'s unauthenticated fallback) were not actually per-IP.** `rate-limit.js` called `ipKeyGenerator(req)` — the whole request object — instead of `ipKeyGenerator(req.ip)`. `ipKeyGenerator`'s IPv6 check silently returns a non-string input unchanged, and that object then string-coerces to the literal `"[object Object]"` wherever it's used as a store key — identical for every request regardless of source IP. In practice, `adminLimiter`'s "20 req/min per IP" was 20 req/min shared globally across every IP hitting `/v1/admin/*` (and the same for `registrationLimiter`'s 5/hour on `/v1/register`/`/v1/recover`/`/v1/resend-verification`) — one aggressive caller could exhaust the bucket for every unrelated IP. Present since the very first rate-limiting implementation; found while wiring the same `ipKeyGenerator` helper into the new repeated-attempt detection mechanism (above).
- **`tenant_agreements` acceptance no longer fabricates consent for superseded document versions.** `acceptAllPendingByTenant()` accepted every `PENDING` row for a tenant regardless of `template_version` — if a document type was republished more than once before a tenant re-accepted, every stale, superseded version got marked `ACCEPTED` too, stamped with the same `accepted_at`/`ip`/`user_agent` as the version the tenant actually read. Now scoped to only the row matching the currently-published version (`agreements.is_current = true`). See ADR-018's addendum.
- **A non-2xx HTTP response from SRI's reception/authorization SOAP service no longer discards the response body.** Previously only a generic `"SRI reception service returned HTTP 500"`-style message was logged (`document_events`), with no way to tell a transient server-side failure (e.g. a SOAP Fault from SRI's own persistence layer, `soap:Server`) apart from a malformed request on our end (`soap:Client`). The raw body is now also persisted as a `sri_responses` row (`status: "HTTP_<code>"`), the same table a business-level rejection already lands in — see `GET /:accessKey/sri-responses`.
- **`GET /v1/tenants/agreements`'s `needsAcceptance: false` was indistinguishable between "everything's accepted" and "no agreement templates have ever been published"** — `tenant-agreement.service.js#getStatus()` short-circuits to `{ needsAcceptance: false, outdated: [] }` before generating anything when `agreementService.listCurrent()` is empty, which is exactly what a fresh/pre-launch environment (no admin has visited `/admin/agreements` yet) returns for every tenant. A caller had no way to tell that apart from a tenant that's simply caught up, which caused `comprobify-web`'s "Documentos legales" settings card to show three dead links that all 404 with `AGREEMENT_NOT_FOUND`. Added `hasPublishedAgreements: boolean` to the response so callers can render "nothing to show yet" correctly instead of assuming templates exist.
- **Email verification links no longer get silently burned by corporate email link-scanners.** `GET /v1/verify-email?token=` both validated and consumed the token in one request, so a scanner's automated prefetch (e.g. Microsoft Defender/Safe Links on Outlook addresses) could invalidate the token before the user's real click, leaving them with `INVALID_OR_EXPIRED_TOKEN` on their first genuine attempt. Verification is now split into a non-consuming check (`GET /v1/verify-email/check`, safe to prefetch) and a consuming confirm (`POST /v1/verify-email`, which a `GET`-only prefetch can never trigger). The old combined `GET /v1/verify-email` is kept unchanged for backward compatibility — it's still the endpoint the verification email links to directly when no `verificationRedirectUrl` was configured at registration.

## [0.11.2] — 2026-07-28

### Changed
- **Operational note: staging droplet resized from `s-1vcpu-512mb-10gb` to `s-1vcpu-1gb`, plus a 1G swapfile.** The 512MB tier left ~60MB free after the `api`/`worker` container `mem_limit`s, causing swap pressure and OOM-driven disconnects under load (`write EPIPE`, unresponsive endpoints). Swap is a backstop against transient memory spikes (RIDE PDF generation, `xmllint` subprocess forks) on top of the resize, not a substitute for it. No API-facing behavior changes.
- **Operational note: the 4 admin cron jobs now log to plain files under `/opt/comprobify/logs`** (rotated weekly via a new `/etc/logrotate.d/comprobify-cron`) instead of `logger`/syslog. Reading the journal requires the `systemd-journal` group or root, and root SSH is fully disabled on the staging droplet by design — plain files are readable by the deploy user without ever needing root. No API-facing behavior changes.
- **Operational note: Terraform no longer manages the DigitalOcean Project's own lifecycle.** `digitalocean_project` is now a `data` lookup instead of a `resource` — Terraform only ever assigns the current droplet into the (permanent, externally-managed) project via `digitalocean_project_resources`, never creates/renames/destroys the project itself. No API-facing behavior changes.

## [0.11.1] — 2026-07-28

### Fixed
- **`DB_SSL_CA` now round-trips through the deployed `.env` file correctly.** The `v0.11.0` staging deploy failed with `docker compose`'s env parser rejecting a line inside the certificate (`unexpected character "+" in variable name`) — a raw multi-line PEM breaks the droplet's `.env` file, since the deploy workflow's heredoc substitution isn't quoted and a real newline mid-certificate produces a line that isn't valid `KEY=value`. `DB_SSL_CA` must now be set as a single line with real newlines replaced by literal `\n`; `src/config/index.js` converts it back to real newlines before passing it to `pg`'s `ssl.ca` option.

## [0.11.0] — 2026-07-27

### Added
- **Tier prices now have history, and a change gives at least 30 days' notice, per `docs/agreements/terms-of-service.md`.** New `tier_prices` table (migration 076) replaces the plain `priceMonthlyUsd`/`priceYearlyUsd` constants in `src/constants/subscription-tiers.js` — a price is created as a `DRAFT` and only starts its notice clock once confirmed via the new admin endpoints (`POST /v1/admin/prices`, `PATCH /v1/admin/prices/:id`, `POST /v1/admin/prices/:id/publish`, `GET /v1/admin/prices[/:id]`). `publishPrice()` rejects a notice shorter than `PRICE_CHANGE_MIN_NOTICE_DAYS` (default 30) and, on success, notifies every currently-`ACTIVE` tenant (in-app `PRICE_CHANGE_ANNOUNCED` notification + email). `PRICE_CHANGE_ANNOUNCED` is "mandatory" — a tenant can't opt out on any channel (see `src/constants/notification-catalog.js`; `GET/PATCH /v1/notifications/preferences` never show or accept it) — which is what makes checking `notifications` directly a safe idempotency source for `pricingService.notifyPendingPriceChangesForTenant`, no dedicated ledger table needed. The in-app notification is created synchronously (not queued); email dispatch rides the `pending_effects` outbox. This function is called from three places: the initial bulk blast, every tenant→`ACTIVE` transition (self-verify, admin verify, admin reactivate-from-`SUSPENDED`), and a new periodic reconciliation sweep (`pricingService.reconcilePendingPriceChangeNotifications()`, wired into `POST /v1/admin/jobs/notifications`) that catches an `ACTIVE` tenant silently skipped during the bulk blast. See ADR-023 and ADR-024 (the notification-system standardization this previewed, shipped below).
- Every real billing call site (`createSubscription`, `requestTierChange`'s upgrade/downgrade/proration/deferred-interval-change paths, `createRenewalReminder`) now resolves price via `pricingService.getCurrentPrice`/`getPriceAsOf` instead of reading a live constant — resolved **as of the date the resulting period actually starts** (now for immediate-effect changes, `current_period_end` for deferred ones), which is what makes a renewal or deferred interval change due before a new price's `effective_at` still bill the old price automatically.
- `GET /v1/tiers` response gains `upcomingPriceMonthlyUsd`/`monthlyPriceEffectiveAt`/`upcomingPriceYearlyUsd`/`yearlyPriceEffectiveAt` per tier — a published-but-not-yet-effective price change is visible to prospective tenants too, not just existing ones who got the notification.
- `pending_effects` gains a `notification_type` column (migration 080) — a denormalized snapshot of `notifications.type`, populated only for `NOTIFICATION_DISPATCH` rows, so admin/debug queries can see what kind of notification is pending/failed without joining out to `notifications`. Purely informational; the effect handler still re-fetches the real notification row.
- **Unified notification service, per-channel preferences, and DB-backed email templates (ADR-024, closes the notification-system standardization previewed by ADR-023).** Every `notificationService.createX(...)` function now creates its `notifications` row unconditionally (no preference gate at creation — preference now controls read-time visibility and send-time email dispatch instead) and routes through one shared `dispatchNotification()` that durably enqueues webhook fan-out and, for email-capable types, a single `NOTIFICATION_DISPATCH` effect. `NOTIFICATION_DISPATCH` replaces 7 old type-specific `*_NOTIFICATION`/`*_EMAIL` `pending_effects` types (`DOCUMENT_AUTHORIZED_NOTIFICATION`, `PAYMENT_REVIEWED_NOTIFICATION`/`_EMAIL`, `SUBSCRIPTION_RENEWAL_DUE_NOTIFICATION`/`_EMAIL`, `SUBSCRIPTION_EXPIRED_NOTIFICATION`/`_EMAIL`, `PRICE_CHANGE_EMAIL`) — 8 effect types total now, down from 15. `src/constants/notification-catalog.js` is the new single source of truth for which channels (`IN_APP`/`EMAIL`) each notification type supports and whether it's mandatory (currently only `PRICE_CHANGE_ANNOUNCED`), replacing the one-off `non-subscribable-notification-types.js` array. `notifications` gains an `email_status` column (migration 078, mirrors `documents.email_status`). Email content for the 5 email-capable types (`PAYMENT_VERIFIED`, `PAYMENT_REJECTED`, `SUBSCRIPTION_RENEWAL_DUE`, `SUBSCRIPTION_EXPIRED`, `PRICE_CHANGE_ANNOUNCED`) moved from JS/locale files to a new versioned `notification_email_templates` table (migration 079, mirrors the `agreements` pattern), authored in `docs/email-templates/{TYPE}.{lang}.txt` and published via new admin endpoints (`POST`/`GET /v1/admin/notification-email-templates`, `GET .../versions/:id`, `GET .../:type/:language/versions`, `PATCH .../:id/activate`). See ADR-024.
- **New `PAST_DUE` tenant status — a non-payment lapse now has a real, self-resolving consequence (ADR-025).** When a subscription's renewal grace period lapses unpaid, `subscriptionService.expireSubscription()` now flips `tenants.status = 'PAST_DUE'` (in addition to the existing FREE-tier downgrade), logging a `STATUS_CHANGED` tenant event (`reason: 'unpaid_renewal'`). `PAST_DUE` is deliberately distinct from `SUSPENDED` — it's assigned automatically and clears automatically: a new `src/middleware/require-past-due.js` (403 `ACCOUNT_PAST_DUE`) is mounted everywhere `requireNotSuspended` already is, **except** `POST /v1/subscriptions` and `PATCH /v1/payments/:id/proof` stay reachable while `PAST_DUE` — starting a fresh subscription and paying is the self-service recovery path, landing back on `ACTIVE` (`STATUS_CHANGED`, `reason: 'payment_recovered'`) the moment its first invoice authorizes. A new `SUBSCRIPTION_PAST_DUE_WARNING` notification type (+ email, same DB-backed template pipeline as ADR-024) fires partway through the grace window, ahead of the existing renewal-due reminder — distinct, more urgent, and specifically about the account becoming `PAST_DUE`. Migration 081. See ADR-025.
- `GET`/`PATCH /v1/notifications/preferences` gain `SUBSCRIPTION_PAST_DUE_WARNING` as a subscribable `(type, channel)` pair (not mandatory).

### Changed
- **`pg.Pool` size is now configurable per-process via `DB_POOL_MAX`** (default `5`, a conservative fallback), instead of a hardcoded `max: 20` in `src/config/database.js`. The API and worker are separate processes with separate pools drawing from the same provider connection ceiling — and so does any other database sharing that cluster (e.g. comprobify-web's database, planned to share the staging cluster) — so `deploy/docker-compose.yml` now sets them independently (`6` for `api`, `3` for `worker`) to leave headroom for that third consumer on small managed-Postgres plans (e.g. DigitalOcean's Basic tier, ~22 total backend connections).

See ADR-018 addendum.
- **Breaking: `GET`/`PATCH /v1/notifications/preferences` body shape changed from `[{type, enabled}]` to `[{type, channel, enabled}]`.** `channel` is `IN_APP` or `EMAIL`. A mandatory type (`PRICE_CHANGE_ANNOUNCED`) is rejected (400) if a caller tries to set a preference for it, and never appears in the `GET` response. - **`GET /v1/tenants/me`'s `status` field can now return a new value, `PAST_DUE`**, in addition to the existing `PENDING_VERIFICATION`/`ACTIVE`/`SUSPENDED`. Integrations that switch on this field should add a case for it — see ADR-025 for what it means and how a tenant recovers from it.

### Fixed
- **DB SSL connections now support a private CA** via the new `DB_SSL_CA` env var. The previous `ssl: { rejectUnauthorized: true }` config had no `ca` option, which fails with `SELF_SIGNED_CERT_IN_CHAIN` against a provider with a private CA (e.g. DigitalOcean managed Postgres) — providers with a publicly-trusted chain (e.g. Neon) were never affected, which is why this hadn't surfaced before. Wired into both `deploy-staging.yml` and `deploy-production.yml`.

## [0.10.0] — 2026-07-23

### Added
- **Generic `pending_effects` outbox replaces both the RabbitMQ async-SRI dispatch-tracking columns and most remaining fire-and-forget side effects in the codebase (notifications, webhook fan-out, transactional emails — 14 effect types total, tenant-scoped via a `tenant_id` column).** Previously, only `POST /:key/send`/`GET /:key/authorize` were durable (ADR-019); everything else was an unawaited promise with a `.catch(console.warn)` that silently lost work on a crash. Every producer call site now durably enqueues an effect row (tagged with its owning tenant) before best-effort dispatching it to RabbitMQ; a single reconciliation sweep against `pending_effects` (no more `public`/`sandbox` schema split) recovers anything left undispatched. `workers/sri-worker.js` is renamed to `workers/worker.js` and now consumes three queues (`sri.send`, `sri.authorize`, new `app.effects`) with independent prefetch, so slow side effects (e.g. a webhook fan-out to a sluggish endpoint) can never delay SRI message delivery. Migration 075 adds the table and drops `documents.send_dispatch_attempted_at`/`authorize_dispatch_attempted_at`, now superseded. Subscription activation/tier-change/renewal reconciliation deliberately does **not** use this mechanism — `linkInvoice()` already applies those synchronously when the linked invoice is already authorized (the common case), and the rare reverse ordering is instead caught by a new periodic scan, `subscriptionService.applyPendingInvoiceLinks()`, inside `POST /v1/admin/jobs/subscriptions` — firing a RabbitMQ effect on every document authorization system-wide wasn't worth it for a check relevant to a small fraction of tenants. See [ADR-022](docs/adr/022-effects-outbox.md) and its addendum. No API-facing behavior changes — this is purely a reliability/internals change.
- **Operational note: staging infrastructure migrated from Render to a Terraform-managed DigitalOcean droplet.** `render.yaml` and all active Render references are removed; the API, worker, and the four admin cron jobs (previously three separate Render primitives — web service, background worker, cron jobs) now run as `api`/`worker` containers plus a host `cron.d` schedule on one droplet behind Caddy. Provisioned via `terraform/` (module + per-environment state, remote state in DigitalOcean Spaces) and applied via a new `.github/workflows/terraform.yml` (`plan`/`apply` gated behind a required-reviewer GitHub Environment); deployed via the existing `.github/workflows/deploy-staging.yml`, now targeting the droplet over SSH instead of Render's own deploy mechanism. SSH is intentionally open to the internet with key-only auth, an unprivileged non-root deploy user, and `fail2ban` — see `docs/terraform-digitalocean-setup.md`'s "SSH access model" for the reasoning. Also fixes `trust proxy` (`1` → `2`) for the new two-hop Cloudflare+Caddy topology, which previously would have silently pooled all `adminLimiter`/`registrationLimiter` rate-limit buckets by `req.ip`. Production remains on standby, not yet migrated. See `docs/terraform-digitalocean-setup.md` and the updated `docs/infrastructure-costs.md`. No API-facing behavior changes.
- **`PATCH /v1/admin/tenants/:id/status` accepts an optional `reason` field**, recorded on the `STATUS_CHANGED` tenant event alongside `from`/`to`. Closes a gap flagged in NEXT_STEPS.md (account closure) — the product deliberately has no separate "terminated" status (`SUSPENDED` already blocks writes while letting a tenant keep viewing their own historical documents/payments, which is the right behavior for a closed account too), so `reason` is what actually distinguishes a voluntary closure request from a fraud/non-payment suspension in the audit trail.
- **New `POST /v1/recover` endpoint for regaining API key access.** `POST /v1/register` used to double as an implicit recovery mechanism (re-submitting the registration form with an already-registered email), which — even after requiring a matching certificate — still leaked whether an email was registered at all (a certificate mismatch returned a distinct error from a genuinely new email). Recovery is now a dedicated endpoint: any non-owning outcome (unregistered email, an account with no issuer, a mismatched certificate) returns the exact same generic `200` response, so none of those cases are distinguishable from one another. Only a certificate that actually matches the account on file — the same ownership bar fresh registration accepts — issues a key, synchronously. **As extra validation, the tenant is also demoted to `PENDING_VERIFICATION` with a fresh token** — a matching certificate proves possession of the P12, not control of the registered email inbox, so recovery now requires clicking a fresh verification link (durably enqueued, reusing the existing verification-email/`GET /v1/verify-email` machinery) before the account regains `ACTIVE`-gated privileges (branch creation, promotion, starting a subscription, minting additional named keys); the reissued key works immediately for sandbox document creation in the meantime, same restrictions as a freshly-registered tenant. See [ADR-021](docs/adr/021-account-recovery-flow.md)'s addendum. Also fixes a real bug in the process: the old recovery path always revoked/reissued a **sandbox** key regardless of the tenant's actual environment, so a tenant already promoted to production whose production key was the one they'd lost got back a useless sandbox key instead. Recovery now resolves environment from the tenant's actual `sandbox` flag.

### Changed
- **Breaking: `POST /v1/register` no longer accepts an already-registered email.** It previously treated a matching email as an implicit recovery request (see above); it now always rejects with `409 CONFLICT` pointing callers at `POST /v1/recover` instead. Any integration relying on the old dual-purpose behavior needs to switch to the new endpoint.
- **Breaking: every primary/foreign key across the schema is now a UUID (v7, time-ordered) instead of an auto-increment integer.** All `id` fields in API responses — `tenants`, `issuers`, `documents`, `subscriptions`, `payments`, `webhooks`, notifications, etc. — are now UUID strings, not integers. The `X-Issuer-Id` header must now be a UUID rather than a numeric id. `sourceIssuerId`, `initialSequentials.*.issuerId`, and every other id-shaped request field follow the same change. Business-numeric fields (SRI sequential numbers, pagination) are unaffected. See [ADR-020](docs/adr/020-uuid-primary-keys.md).

Both fixes are now wrapped in a single transaction (`document-rebuild.service.js`) so the document update, line-item replacement (`documentLineItemModel.deleteByDocumentId` + `bulkCreate`), and `REBUILT` audit event are atomic.
- **Bypass-mode writes on tenant-scoped tables could violate RLS if the issuer context was omitted** — `documentModel.updateStatus`, `documentLineItemModel.bulkCreate`, and `documentEventModel.create` now explicitly qualify the `sandbox`/`public` schema prefix in their `db.query()` (no client, no issuerId) bypass path, so a caller that omits the issuer context can no longer produce an RLS violation.
- **Mailgun webhook events for sandbox documents never updated `email_status`** — `findByEmailMessageId` queried `public.documents` only, so sandbox documents (created while `tenant.sandbox = true`) never transitioned from `SENT` to `DELIVERED`/`FAILED`/`COMPLAINED`. The query now `UNION ALL`s across `public.documents` and `sandbox.documents`, returns a `sandbox` boolean on the result row, and threads it through to both `updateEmailStatus` and `documentEventModel.create` so the update and audit event land in the correct schema. See ADR-010.
- **Mailgun webhook audit events violated RLS** — `documentEventModel.create` calls in the webhook path passed `issuerId = null`, routing through the no-context `db.query()` bypass, which the `document_events` RLS policy rejects for `INSERT`. `document.issuer_id` (available from the `findByEmailMessageId` result) is now passed through, routing the insert via `db.queryAsIssuer` so the RLS context is set correctly.

## [3.0.0] — 2026-03-01

### Breaking Changes

- **`documentType` is now required** on `POST /api/documents` — no silent default. Callers that previously omitted this field and relied on the implicit `'01'` default will receive a `400` validation error.
- **API routes renamed** from `/api/invoices/*` to `/api/documents/*`. All client integrations must update their base path.
